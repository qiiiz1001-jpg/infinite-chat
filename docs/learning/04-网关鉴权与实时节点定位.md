# 04：网关鉴权与实时节点定位

[返回导航](00-学习导航.md) · [实现进度](进度-原文与代码对照.md)

## 本篇目标

对应原文第 5、6 章。理解登录后的 HTTP 请求怎样经过网关，以及客户端怎样找到 WebSocket 节点。后续章节实现与讲义已补齐；本篇聚焦网关与定位，实际验证范围见验证记录。

## 业务场景与代码入口

```text
客户端 → 网关 10010 → 登录接口放行 → UserService 8104
  → 签发 Token → 节点定位
       ├─ 关闭发现：返回配置的单机地址
       └─ 开启发现：获取实例列表 → 一致性哈希选择节点
  → 返回 nettyUri
客户端 → nettyUri 建立 WebSocket（独立的 Netty 端口）
客户端 → 网关携带 Access-Token → JWT + Redis 校验 → 路由到业务服务
```

## 1. 先读 AuthorizeFilter：一条 HTTP 请求如何通过网关

打开 [AuthorizeFilter.java](../../GateWay/src/main/java/cn/qingliao/gateway/filter/AuthorizeFilter.java)，先看 filter，再看 authenticate、error、getOrder。下面根据当前源码补充答疑；只扩充讲解，不改变原文顺序或业务实现。

### 第一步：确定网关、业务服务与 WebSocket 的位置

```text
普通 HTTP 请求
客户端 -> Gateway 10010 -> AuthorizeFilter -> 后续过滤器、路由转发
                                           +-> UserService 8104
                                           +-> OfflineDataService 8101
                                           +-> AiService 8105
                                           +-> RedPacketService 8103

WebSocket 握手、聊天
客户端 -> 选定实时节点的 Netty 端口，例如 9101
       -> WebSocketAuthHeader -> WebSocket 协议升级 -> WebSocketHandler
```

本项目配置的 WebSocket 连接直接进入实时节点，不经过上图的 HTTP 网关路由。Gateway 过滤器与之前的 WebSocketAuthHeader 使用同一套 JWT/Redis 凭证规则，但处于不同入口。

路由配置在 [网关 application.yml](../../GateWay/src/main/resources/application.yml)：例如 `/api/message/**` 转发 OfflineDataService，`/api/user/**`、`/api/contact/**`、`/api/group/**` 转发 UserService。AuthorizeFilter 只决定是否继续，不在类中写死这些转发地址。

### 第二步：框架如何调用 filter

```java
public class AuthorizeFilter implements GlobalFilter, Ordered
```

@Component 让 Spring 管理此对象；GlobalFilter 把它接入 Gateway 的全局过滤器机制。请求匹配路由后，框架将全局过滤器与路由过滤器组成处理链，再调用 filter。可类比黑马点评的登录拦截器：项目重写入口，框架负责触发，但这里使用 WebFlux 的响应式 API。参考 [Gateway 4.3 全局过滤器说明](https://docs.spring.io/spring-cloud-gateway/reference/4.3/spring-cloud-gateway-server-webflux/global-filters.html)。

```java
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain)
```

| 对象或返回值 | 当前阅读需要掌握的含义 |
|---|---|
| exchange | 当前 HTTP 交互的上下文，可取得请求、响应和属性 |
| chain | 后续过滤器链，通过 chain.filter(...) 继续处理 |
| Mono<Void> | 表示异步处理完成或失败的发布者，不提供普通返回数据 |

不是返回 true 放行、false 拒绝：放行返回后续链的 Mono，拒绝返回写错误响应的 Mono。响应体内容写入 HTTP response，不会因为返回 Mono<Void> 就没有响应体。

### 第三步：清理外部伪造的身份信息

filter 开头使用 exchange.mutate、request.mutate 构造修改后的请求上下文 clean，删除两个头：

```java
headers.remove("X-User-Id");
headers.remove("X-Internal-Token");
```

```text
外部请求自己填写：X-User-Id=9999
    |
    v
网关清除外部身份头
    |
    v
按 Access Token 认证出的身份=1001
    |
    v
继续处理时添加：X-User-Id=1001
```

这里不会删除 Access-Token、Refresh-Token，因此下游仍可自行核对凭证。请求修改通过构造新 request/exchange 完成，后续必须使用 clean 或它继续构造出的上下文。

### 第四步：先阻止外部内部接口，再判断公开路径

```java
String path = clean.getRequest().getPath().value();
if (path.contains("/internal/"))
    return error(clean, ErrorCode.NO_AUTH_ERROR, HttpStatus.FORBIDDEN);
if (PUBLIC_PATHS.contains(path)) return chain.filter(clean);
```

PUBLIC_PATHS 包含验证码、注册、两种登录与 `/api/user/refresh`。这里“公开”表示不要求先通过网关的 Access Token 校验；登录密码、验证码、Refresh Token 等仍由具体接口校验。

采用完整路径匹配，所以：

```text
/api/user/refresh      -> 公开路径，由刷新接口自己校验刷新凭证
/api/user/refresh/uri  -> 受保护路径，需要 Access Token
```

不能把公开规则理解为所有带 refresh 字样的路径都放行。路径含 `/internal/` 的请求则在此过滤器直接返回 HTTP 403。

### 第五步：authenticate 做 JWT 与 Redis 双重核对

```java
private Mono<String> authenticate(String token, String prefix) {
    Claims claims = JwtUtil.parse(token);
    if (claims == null || claims.getSubject() == null) return Mono.empty();
    String userId = claims.getSubject();
    return redis.opsForValue()
            .get(prefix + userId)
            .filter(stored -> stored.equals(token))
            .map(stored -> userId);
}
```

prefix 用于选择 `access:token:` 或 `refresh:token:`。例如用户 1001 的 Access Token，查的是 `access:token:1001`。

```text
Token -> JWT 验签、检查有效期 -> subject 中取 userId
                                  |
                                  v
                        响应式查询 Redis 当前凭证
                                  |
                    +-------------+-------------+
                    v                           v
                 与 Token 相同               无记录 / 不相同
                    |                           |
                    v                           v
              发布 userId                   空完成
```

ReactiveStringRedisTemplate 是响应式 Redis 客户端，get 返回 Mono<String>，不是当场得到 String。这里不调用 block 等待 Redis；框架订阅处理链后按结果继续。

### 第六步：把 Mono 链读成三种结果分支

Mono 是 Reactor 提供的发布者，正常时最多产生一个值，也可以没有值地完成，或以错误结束。Mono.empty 表示正常空完成，不等于抛异常，也不是发布一个 null。参考 [Reactor Mono API](https://projectreactor.io/docs/core/release/api/reactor/core/publisher/Mono.html)。

filter 中几个操作符在这里的具体作用：

| 操作符 | 当前逻辑 |
|---|---|
| map | 把认证出的 userId 包装成 Authentication 结果对象 |
| switchIfEmpty | Access 认证结果为空时，订阅 Refresh 认证备选链 |
| defaultIfEmpty | 两种凭证均无法给出结果时，提供未登录结果 |
| onErrorReturn | 上游认证处理发生响应式错误时，提供系统错误结果 |
| flatMap | 按结果选择另一个 Mono：继续过滤器链或写错误响应 |

类末尾的 Authentication 是本类声明的 Java record，用于承载 userId/error，不是另一个认证框架。

```text
Access 有效
  -> Authentication(userId, null)
  -> 添加可信 X-User-Id
  -> chain.filter(修改后的 exchange)

Access 无效，Refresh 有效
  -> Authentication(null, TOKEN_EXPIRED)
  -> HTTP 401，业务 code=40103
  -> 客户端应请求刷新接口，再重试原业务

Access、Refresh 均无效
  -> Authentication(null, NOT_LOGIN_ERROR)
  -> HTTP 401，业务 code=40100

上游 Redis 等认证处理异常
  -> Authentication(null, SYSTEM_ERROR)
  -> HTTP 503，业务 code=50000
```

只有第一条分支允许继续；Refresh 有效只说明可尝试换发凭证，网关本身不签发新 Token，也不直接放行业务请求。客户端是否已实现自动刷新，需要另行看客户端，不能由这段后端代码推断。

这张图表达业务判定顺序。源码把 authenticate(refresh, ...) 作为 switchIfEmpty 的参数，因此构造备选 Mono 时可先执行其中的同步 JWT 解析；备选 Redis 发布者则在 Access 结果为空时才被订阅。不能直接将它描述为“Access 成功后 Refresh 的任何代码都绝对没执行”。

另外 onErrorReturn 位于 flatMap 之前，主要转换上游认证链的错误，不是兜底所有下游路由、业务处理异常。已有认证结果也不会让 Mono<Void> 被当成“认证结果为空”而误走刷新分支。

### 第七步：放行与返回错误分别写在哪里

Access 有效时，代码重新设置 X-User-Id，然后返回 chain.filter(...)。它表示继续后续网关处理；路由转发由后续框架过滤器完成。

error 方法设置 HTTP 状态、JSON Content-Type，将业务 code、message 编码成响应字节，通过 response.writeWith(...) 返回。这里有两套状态：

```text
HTTP 状态：401
JSON 响应体：{"code":40103,"message":"Access Token 过期"}
```

HTTP 状态表达请求层面的结果，JSON code 让客户端区分需要刷新、重新登录或系统异常。

getOrder 返回 -100，参与过滤器排序。数值较小的优先级较高，前置逻辑较早执行；它是排序值，不是错误码，也不表示每次链中都绝对第一个执行。

### 第八步：与之前的 WebSocket 鉴权放在一起看

| 对比项 | AuthorizeFilter | WebSocketAuthHeader |
|---|---|---|
| 入口 | Gateway HTTP 路由链 | Netty WebSocket 握手链 |
| Token 来源 | Access-Token、Refresh-Token 请求头 | Authorization，兼容 Bearer 前缀 |
| 当前成功结果 | 增加 X-User-Id，继续网关链 | 将身份保存在 Channel 属性，继续握手 |
| 不同机制 | 响应式 Redis、Mono | Netty Channel、处理器事件 |

HTTP 网关此处没有剥离 Access-Token 中的 Bearer 前缀，按当前代码应传裸 Token。WebSocket 的 Authorization 处理方式不能直接照搬成同一个请求头格式。

业务服务的 [AuthenticationConfig.java](../../Common/src/main/java/cn/qingliao/common/security/AuthenticationConfig.java) 还会校验 Access Token、Redis，并保存服务端用户身份；它没有仅凭外部 X-User-Id 就认可身份。服务间内部凭证由内部调用配置携带，网关不会替外部请求附加它。

## 2. 再看实时节点定位

### 2.1 先确定场景：登录时给用户哪个 WebSocket 地址？

假设启动三个 RealTimeService 实例，用户登录后需要知道连接哪个实例。这个逻辑发生在建立 WebSocket 之前，不是每发一条消息就重新选择节点。

```text
UserServiceImpl.createJwt：准备登录响应
    → NettyServiceLocator.getServiceInstance(userId)
         ├─ discoveryEnabled=false：直接返回 fallback，当前默认走这里
         └─ discoveryEnabled=true
              → DiscoveryClient 获取 RealTimeService 实例列表
              → UrlHashLoadBalancer.select(instances,userId)
              → ConsistentHash 构建环并 select(userId)
              → 读取选中实例的 ws-host、ws-port
              → 返回 ws://host:port/ws/netty
    → 登录响应的 nettyUri
客户端拿到地址后，才连接那个实时节点
```

入口：[UserServiceImpl.createJwt](../../UserService/src/main/java/cn/qingliao/userservice/service/impl/UserServiceImpl.java)、[NettyServiceLocator](../../UserService/src/main/java/cn/qingliao/userservice/loadbalancer/NettyServiceLocator.java)、[UrlHashLoadBalancer](../../UserService/src/main/java/cn/qingliao/userservice/loadbalancer/UrlHashLoadBalancer.java)、[ConsistentHash](../../UserService/src/main/java/cn/qingliao/userservice/loadbalancer/ConsistentHash.java)。UserServiceImpl 中 serviceInstanceUtil 是变量名，其实际类型是 NettyServiceLocator，不是另一个同名工具类。

默认关闭发现时，返回 `chat.netty-fallback-uri`，默认值为 `ws://localhost:9101/ws/netty`；不会调用多节点哈希选择。启用发现后，注册列表为空则报错，不会继续返回一个不存在的实例。

### 2.2 负载均衡是什么，为什么有多种算法？

负载是实例承担的工作，例如连接数量、每秒消息数、CPU 和网络开销。负载均衡是在多个能提供相同服务的实例中，按规则选择一个，尽量分散压力。只有一台机器一个实例时，选择空间很小；增加实例后才需要决定新请求或新连接交给谁。

```text
若所有用户只知道 N1 地址：用户A、B、C、D → N1；N2、N3没有接入流量

增加地址选择后：
    用户A → 选择器 → N1
    用户B → 选择器 → N2
    用户C → 选择器 → N3
    用户D → 选择器 → N1
```

图中的选择器是一段决策逻辑，不一定是单独服务器。本项目由 UserService 内的定位器选择地址，客户端拿到地址后直连；定位器不会一直夹在客户端与实时节点之间转发所有帧。

| 策略 | 怎样选择 | 主要特点与限制 |
|---|---|---|
| 轮询 | N1、N2、N3、N1…… | 简单，分散选择次数；不保证同一用户重连仍到原节点，也不代表负载一样 |
| 随机 | 随机取一个实例 | 大量选择时可能分散，小样本可能偏斜 |
| 加权 | 给高容量实例更大选择比例 | 能反映容量差异，需要合理权重 |
| 最少连接 | 参考实例当前连接数选择 | 更贴近连接分布，需要维护统计；连接数也不等于消息处理负载 |
| 用户哈希取模 | hash(userId)%节点数 | 节点列表稳定时，同用户稳定落点；节点数变化会大量重映射 |
| 一致性哈希 | 在哈希环上寻找后继节点 | 同用户稳定落点，并减少节点变化引起的重映射；不实时比较哪台机器最空闲 |

这里比较的是选址策略，不代表当前工程实现了表中全部算法。HTTP 常按请求分配，WebSocket 主要在建连前分配；一旦建立连接，后续帧本来就在这条连接上通信，不会每发一条消息重新轮询。

普通取模的例子中，假设实例顺序为 N1、N2、N3，扩容时末尾追加 N4：

| 示意哈希值 | 原来 %3 | 扩容后 %4 | 目标变化 |
|---|---|---|---|
| 1 | 1→N2 | 1→N2 | 不变 |
| 2 | 2→N3 | 2→N3 | 不变 |
| 3 | 0→N1 | 3→N4 | 改变 |
| 4 | 1→N2 | 0→N1 | 改变 |
| 5 | 2→N3 | 1→N2 | 改变 |
| 6 | 0→N1 | 2→N3 | 改变 |

变化不只把部分用户分给新 N4，还会让很多用户在旧节点之间换目标。一致性哈希的主要目标是缩小这个变化范围，不是证明自己在任何场景都比轮询好。“一致”在这里也不是数据库事务的强一致性。

### 2.3 环怎样选节点，什么叫环绕？

下面把位置缩小成 0—99，仅演示规则；当前源码实际使用 32 位非负哈希值。

先把每个节点身份算成位置，再把 userId 算成位置。用户“位置35”表示 `hash(userId)=35`，不要求用户 ID 就是35，也不是把用户注册到一个编号为35的物理节点。相同输入在相同算法下会得到相同位置。

```text
顺时针方向：0 → N1(20) → N2(60) → N3(85) → 99 → 回到0

用户哈希位置10 → 第一个 >=10 的节点20 → N1
用户哈希位置35 → 第一个 >=35 的节点60 → N2
用户哈希位置75 → 第一个 >=75 的节点85 → N3
用户哈希位置95 → 右边没有节点，回到最小位置20 → N1
```

节点负责的是它前面的那段区间：

| 节点 | 负责的用户哈希区间 |
|---|---|
| N1(20) | (85,99] 与 [0,20]，跨过首尾 |
| N2(60) | (20,60] |
| N3(85) | (60,85] |

例如35离20的绝对距离更近，但仍选择60，因为规则是沿固定方向找第一个节点，不是比较左右哪个数更近。

代码用 TreeMap 保存“哈希位置 → 实际服务实例”。`ceilingEntry(hash(userId))` 找不小于用户位置的第一个条目；没有则 `firstEntry()`，这就是环绕。环是有序数值加首尾衔接的查找规则，不需要真的建立一个环形链表。

### 2.4 新增节点为什么只影响部分用户？

仍用上面的简化环，增加 N4，位置40：

```text
原来：N1(20) ─────────────────→ N2(60)
新增：N1(20) ─→ N4(40) ──────→ N2(60)

用户35：原来走 N2，现在走 N4
用户50：原来走 N2，现在仍走 N2
用户75：仍走 N3
```

此例只有 `(20,40]` 区间改由 N4 承接。真实实现中每个节点有多个虚拟位置，新增节点会接管分散的多个小区间。移除节点则让原属它的区间转交各自顺时针后继。

用两名用户对比，扩容改变的是规则的查询结果：

| 用户 | 哈希位置 | 扩容前 | 扩容后 |
|---|---|---|---|
| U1 | 35 | N2 | N4 |
| U2 | 50 | N2 | N2 |

在包含 N4 的新环里，如果之后移除 N2(60)，则 `(40,60]` 转交 N3(85)，其他区间不需要跟着换。故障节点何时被移出，依赖发现列表的更新；哈希算法本身不探测机器是否宕机。

### 2.5 160 个虚拟节点是什么？

不是额外启动 160 个 JVM，而是给同一真实实例生成 160 个哈希位置。源码使用 `host:HTTP端口#0` 到 `#159` 计算位置，TreeMap 中这些位置的 value 都指回原实例。

```text
N1#0 ─┐
N1#1 ─┼─→ 同一个真实实例 N1
 ...  │
N1#159┘

环上可以交错：N1#0 → N2#4 → N1#8 → N3#2 → N2#7 → ...
```

目的在于让每个实例承接多个分散区间，改善少量实际节点造成的分配偏斜；不能据此保证当前活跃连接数、消息量或 CPU 负载绝对均匀。构建环前排序实例，配合稳定实例身份，避免发现列表的顺序变化影响结果。

为什么多位置可能更均匀？如果三个真实节点只有10、11、12三个位置，位置10会承接从12绕回10的一大段，另外两个区间极小。虚拟节点把同一实例分散到更多位置，减少只靠一个落点决定全部份额的偏差，效果仍受哈希分布影响。

再看一个“每实例仅画两个位置”的简化例子，真实代码是160个：

```text
位置： 8       21       33       47       66       82
条目： N1#0    N2#0    N3#0    N1#1    N3#1    N2#1
实例： N1      N2      N3      N1      N3      N2

用户位置40 → 找到47 → 虚拟条目N1#1 → 实际连接N1
用户位置70 → 找到82 → 虚拟条目N2#1 → 实际连接N2
用户位置90 → 环绕到8 → 虚拟条目N1#0 → 实际连接N1
```

虚拟条目不是用户连接，不占一人一个名额；160个位置不表示最多接160个用户。扩容的新实例也生成160个位置，分别从各自后继处接管小区间，并非只在环上插一个大位置。

### 2.6 它不负责哪些事情？

- **不搬迁已有连接**：用户已经连接 N2，环变化不会让 TCP 连接自动变到 N4；收益主要体现在后续登录、建连和重连分配。
- **不替代跨节点推送**：A、B 可以分配到不同节点，仍依赖独立推送消费组和本机 Channel 过滤来投递。
- **不等于 Kafka 分区路由**：此处用 userId 选实时节点，消息发布用 sessionId 选 Kafka 分区，是两件事。
- **不直接使用注册的 HTTP 端口建 WebSocket**：实例身份按 HTTP 地址计算，最终连接地址读取 ws-host、ws-port 元数据。

重连接口在 [UserController.refreshUri](../../UserService/src/main/java/cn/qingliao/userservice/controller/UserController.java)，使用已认证用户身份查询节点地址；当前没有完整客户端自动调用和连接迁移流程。

### 2.7 回到当前代码，怎样读这三个类？

| 类 | 负责什么 | 阅读重点 |
|---|---|---|
| NettyServiceLocator | 找候选实例、选择分支、返回连接地址 | 关闭发现用 fallback；开启后读取实例列表，再取 ws 元数据 |
| UrlHashLoadBalancer | 把实例列表与 userId 交给哈希选择 | 当前每次调用都构建一个 ConsistentHash，不是全局连接迁移任务 |
| ConsistentHash | 生成虚拟位置、存入有序 Map、查找用户后继 | identity 是 host:HTTP端口；hash 计算数值；ceilingEntry 查后继；firstEntry 环绕 |

```text
候选实例列表 → 为每实例计算160个位置 → TreeMap<位置,真实实例>
用户ID      → hash得到位置          → ceilingEntry/firstEntry
                                      ↓
                                 选中真实实例
                                      ↓
                             拼接WebSocket地址
```

同一候选集合、稳定实例身份及相同算法下，用户的选择可重复；不同 UserService 暂时看到不同发现列表时，结果可能不同，所以不能把它说成跨节点全局会话锁。

### 2.8 对这个 IM 项目，到底带来什么收益？

已经建立的 TCP 连接天然固定在某个节点，不需要一致性哈希再保证每条帧回到同一节点。此处收益主要是同一用户后续登录/重连的可重复选址，以及扩缩容时更少的目标变动；不代表一加节点就立即均摊全部存量连接。

当前方案还需要独立推送消费组覆盖不同节点。如果目标是让活跃负载尽量接近，应另外观测连接数、发送速率、群消息扇出和机器容量；不能根据虚拟节点数就推断实际吞吐。这里解释选型边界，不表示工程已经实现动态负载感知或存量连接迁移。

## 本篇自查

1. Gateway 和 Netty 分别承接什么请求？为什么不能连接 Nacos 返回的 HTTP 端口？
2. Refresh Token 有效，网关为什么仍不能放行业务请求？
3. 一致性哈希处理了什么变化？它是否会自动迁移长连接？
4. chain.filter 与 authenticate 分别负责什么？Mono.empty 是否表示系统异常？
5. 为什么要删除外部的 X-User-Id？下游服务现在是否只凭这个头认证？
6. 用户哈希位置35，节点位置20和60，为什么不选更近的20？
7. 有160个虚拟位置是否最多连接160个用户？新增节点会立即迁走现有连接吗？

## 自查解答

1. Gateway 承接 HTTP 业务路由，Netty 承接独立端口的 WebSocket。服务发现注册的是 HTTP 实例，需要元数据才能构建正确的 WebSocket 地址。
2. Refresh Token 仅用于换取新的 Access Token。网关返回专用错误码提示刷新，不赋予它直接访问业务的权限。
3. 哈希环减少节点变化时用户分配的变动范围，虚拟节点改善分布；它不会迁移已建立的 TCP 连接，仍需重连和路由更新。
4. chain.filter 继续网关过滤器链，authenticate 校验 JWT 与 Redis 后发布用户 ID 或空完成。Mono.empty 是正常无值完成，上游异步错误才由 onErrorReturn 转换。
5. 避免客户端伪造下游身份字段；当前公共鉴权仍校验 Access Token 与 Redis，不只信任 X-User-Id。
6. 规则是按固定方向找第一个不小于用户位置的节点，所以选60；不是比较绝对距离。
7. 不限制用户数，虚拟位置只是区间入口。新环改变后续选址结果，不自动搬迁现有 TCP 连接。
