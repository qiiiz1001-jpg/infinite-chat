## 自查解答

### A01．用 90 秒介绍这个项目，讲清楚核心场景和架构。

**参考回答：** 这是一个支持单聊和群聊的 IM 后端，围绕聊天提供好友申请、群成员管理、历史消息查询、离线补拉、文件上传、系统通知和测试红包。核心链路是用户完成登录后建立长连接，发送的消息经过身份与会话权限校验，再分别进入在线推送和持久化处理。

架构上，网关接收 HTTP 业务请求，用户服务处理账号、关系和会话，实时服务通过 Netty 承接 WebSocket，存储服务保存和查询消息，红包服务处理测试余额和红包账务，此外还有 AI 服务。Kafka 连接消息入口、在线推送和存储；MySQL 保存持久业务数据，Redis 保存当前登录凭证、近期消息索引和红包领取状态。

我会重点介绍消息如何跨节点推送、重连时如何保护连接映射，以及重复消息和红包入账如何幂等。普通消息通过服务端消息 ID 去重，好友申请通过条件更新控制处理资格，群成员修改锁定会话行，红包用 Lua 处理并发领取，再用数据库事务和唯一约束完成入账。这些机制分别保护各自的业务环节。

**追问补充：** HTTP 业务与 WebSocket 使用不同入口。登录、查询等请求经过网关；客户端拿到实时节点地址后直连 Netty。服务拆分允许连接处理、存储与普通业务分别承担负载，代价是需要处理网络调用、消费积压和不同环节的失败。

<a id="a02"></a>

### A02．Maven 多模块就等于微服务吗？Common 算不算一个服务？

**参考回答：** Maven 多模块描述的是源码和构建组织，微服务描述的是运行时服务边界。判断是否按服务拆分，要看应用是否分别启动、怎样通信、能否独立部署，而不是只看父工程下有几个文件夹。

这个项目的网关、用户、实时消息、存储、红包和 AI 应用各自有启动入口，通过 HTTP/Feign 或 Kafka 协作，属于服务化拆分。Common 则是各应用依赖的公共 JAR，存放模型、认证、异常和工具能力，不单独启动或监听端口，因此不算一个业务服务。

常规部署时，一个应用实例由一个 Java 进程承载，在自己的 JVM 中运行。两个实时实例有各自的线程组和连接 Map，即使部署在同一台机器上，内存也不直接共享。Kafka Broker 是另行运行的基础设施；业务服务使用 Kafka 客户端，不代表服务进程中又启动了一个 Broker。

**追问补充：** 同一台机器能运行多个实时实例，但监听端口和实例配置要区分。Common 中的静态变量也只在各自 JVM 内共享，不会因为多个服务依赖同一个 JAR 就形成跨进程共享内存。

<a id="a03"></a>

### A03．为什么既使用 JWT 又查询 Redis？登录、刷新、退出分别改变了什么？

**参考回答：** JWT 负责验证凭证的签名和有效期，Redis 负责判断它是不是服务器当前认可的凭证。只有 JWT 合法并且与 Redis 当前值一致，认证才通过。这样即使一个 JWT 还未到期，服务器也可以通过删除或覆盖 Redis 记录使它失效。

项目的 Access Token 有效期是 30 分钟，用于业务访问；Refresh Token 有效期是七天，用于换发新凭证。登录会生成一对 Token 并分别保存到 Redis；刷新会校验旧 Refresh 的签名、期限和当前值，再签发并覆盖一对新 Token；退出删除两类记录。普通请求和心跳只做校验，不会因为用户一直使用就自动延长有效期。

Refresh 的作用是让 Access 到期后仍能通过刷新接口取得新凭证，而不用再次校验账号密码。它不能直接代替 Access 访问业务。刷新成功后，新 Access 重新计算 30 分钟，新 Refresh 重新计算七天；这和读取 Redis 时顺便延长 TTL 是不同机制。

**追问补充：** 当前 Redis key 按 userId 保存一组凭证，所以同用户重新登录或刷新后，旧值会被覆盖。旧 JWT 即使签名仍合法，也会因为与当前值不符而被拒绝。认证因此依赖 Redis，并不是完全无状态；JWT 的签名也不等于加密载荷。

<a id="a04"></a>

### A04．friend、session、user_session 各表示什么？有好友关系就一定能读某个会话吗？

**参考回答：** friend 描述有方向的联系人关系及其状态，session 描述聊天会话，user_session 描述用户与会话的成员关系、角色等信息。单聊通常由两个人共享一个会话，群聊则由多个成员共享一个会话。拉黑规则有方向：A 拉黑 B 后，A 仍可发送给 B，B 不能发给 A；互相拉黑则双向拒绝，成员与会话授权仍需通过。添加好友时，业务会创建双向好友关系以及相应单聊会话和成员记录。

三者分开，是因为联系人关系和消息归属承担不同职责。好友关系回答“我和对方是什么关系”，会话回答“消息属于哪个聊天空间”，成员关系回答“哪些用户属于这个空间、各自是什么角色”。群消息属于一个共享会话，不需要为每对群成员分别建立聊天会话。

用户登录成功，只证明身份。发送或读取指定会话还要检查该用户的会话成员资格及相应业务权限，不能只凭请求里的 userId、sessionId 或一条好友记录放行。因此会话 ID 是资源定位信息，不是访问凭证；客户端修改 ID 也不能获得别人的会话权限。

**追问补充：** 认证回答“你是谁”，授权回答“你能对哪个资源做什么”。项目从服务端认证上下文取得操作者，并检查请求中的操作人字段是否一致；群角色与会话成员资格继续由业务数据决定。

<a id="a05"></a>

### A05．A 给 B 发一句话，从文本帧到在线显示、再到数据库，完整经过哪些环节？

**参考回答：** A 通过完成认证的 WebSocket 连接发送文本消息。实时服务检查连接凭证、消息格式和会话发送权限，使用连接绑定的用户身份覆盖发送者，再生成服务端消息 ID 和创建时间。这样客户端只能提交要发送的内容，不能决定自己是谁，也不能指定最终服务端消息 ID。

同一份消息以 sessionId 为 key，分别投递到存储和推送 Topic。推送消费者读取消息后，单聊分别查发送者和接收者的本机 Channel，向 A 回显并尝试向 B 推送；B 在另一个节点时，由那个节点自己的消费组读取同一推送消息并处理。存储消费者独立写入 MySQL，按服务端消息 ID 去重，提交后更新近期消息缓存。

B 不在线时，推送消费者找不到活跃连接就跳过，不会一直持有消息等待 B 上线。消息仍由存储链保存，客户端可以通过历史查询或离线补拉接口获取。A 的回显包含客户端请求标识和服务端消息标识，便于关联本地消息，但回显不表示存储已提交或 B 已收到。

**追问补充：** Kafka 发布失败时，入口向 A 原来的连接返回错误及 clientMessageId，不是通知 B，也不是数据库回滚通知。推送和存储分别推进，分析成功或失败时要明确说的是哪一段。

<a id="a06"></a>

### A06．WebSocket 怎样从 HTTP 升级？Pipeline 中为什么需要两个 Aggregator？

**参考回答：** 客户端先建立 TCP 连接，再发送带协议升级信息的 HTTP 请求。服务器检查请求路径、协议要求和身份凭证，接受后返回 101 Switching Protocols。随后双方复用原来的 TCP 连接，按照 WebSocket 帧格式持续通信，不需要为每条聊天消息重新建立 HTTP 请求和连接。

两个聚合器处于不同阶段。HTTP 聚合器把请求头和内容片段等组合成完整 HTTP 请求，供握手鉴权与升级处理；WebSocket 帧聚合器把一条消息的多个分片帧合成完整文本或二进制消息，供聊天业务处理。它们分别解决握手请求完整性与升级后消息完整性，不能互相替代。

TCP 传输的是有序字节流，不保留应用发送边界；WebSocket 帧头提供类型、长度和分片结束等信息，编解码器据此解析帧，聚合器再组合消息。项目因此按完整文本消息解析 JSON，不需要给聊天内容另加 TCP 分隔符，并对聚合长度设置上限。

**追问补充：** TCP 分段和 WebSocket 分片不是一回事。一个帧可以跨多个 TCP 段，一个 TCP 段也可能包含多个小帧的数据。HTTP 同样可以复用 TCP 长连接，WebSocket 的主要特点是升级后双方可以独立发送消息。

<a id="a07"></a>

### A07．Boss、Worker 和业务执行器各干什么？返回 CompletableFuture 就一定不阻塞吗？

**参考回答：** Boss 负责接受新 TCP 连接，Worker 的事件循环负责网络读写与协议事件，business 执行器组承接鉴权和消息业务。当前配置分别为 1、4、4，每个实时实例启动时初始化，各客户端连接共用这些执行资源，并不是每来一个用户就创建三组线程。一个 Worker 可以管理多条连接。

同步 Redis 和远程权限查询放在业务执行器上，避免长期占住网络 I/O 线程。CompletableFuture 则是表示未来结果的对象，不是线程；返回它不会自动把此前同步操作移到后台。Kafka send 本身也可能等待元数据或缓冲区，因此返回 Future 不等于整个方法完全不阻塞。

普通聊天登记回调汇总 Kafka 发布结果，方法不显式等待确认；红包部分链路调用 join 等待投递结果。两者都可以使用 acks=all，区别是获取结果的代码不同。当前聊天失败回调主要记日志并给发送连接写错误帧，不执行慢数据库入账。

**追问补充：** 不带 Async 的回调不固定运行在 business 组，可能由完成 Future 的线程执行，也可能在登记时结果已经完成而直接执行。join/get 则在结果未完成时阻塞当前线程，直到取得结果或抛出失败异常。

<a id="a08"></a>

### A08．ChannelManager 为什么用 ConcurrentHashMap？为什么删除连接时不能只 remove(userId)？

**参考回答：** ChannelManager 保存本节点的 userId 到当前 Channel 的映射，握手完成后登记，推送时查询，关闭时清理。建立连接、处理关闭和 Kafka 推送涉及并发访问，所以使用 ConcurrentHashMap。这个 Map 里的 Channel 是本 JVM 的连接对象，其他节点不能直接通过自己的内存访问它。

用户重连时，绑定流程先把映射从 C1 换成 C2，再关闭旧 C1。C1 的关闭回调随后执行，如果只按 userId 删除，就会误删已经更新为 C2 的映射。因此清理使用用户 ID 加旧 Channel 的原子条件删除，当前值仍为 C1 才删除；若已经是 C2，返回 false，保留新连接，也不记录用户离线。

并发 Map 保护单个操作，绑定还包含保存属性、替换映射、注册监听和关闭旧连接等步骤，因此绑定过程额外同步。同一连接的关闭监听与 channelInactive 都可能清理，属性取出并置空使重复清理直接退出。只有移除了当前连接才执行离线回调，旧连接断开不等于用户离线。

**追问补充：** old.close 由 Netty 发起底层连接关闭，关闭监听再调用解绑；解绑负责清理 Map 和业务属性，不是关闭 Socket。本地 Map 和锁只协调当前 JVM，不能解释成跨节点共享的连接表。

<a id="a09"></a>

### A09．ping/pong、读空闲和退出登录各自怎样影响连接？退出会立即踢掉 WebSocket 吗？

**参考回答：** 当前应用心跳由客户端发送文本 ping，服务端先校验连接绑定的凭证是否仍为 Redis 当前值，再直接回复 pong，不经过 Kafka。心跳说明连接仍有活动，不代表某条聊天消息已经送达或已读；它也不同于 WebSocket 协议自身的 Ping/Pong 控制帧。

服务端配置读空闲检测，默认距最后一次入站数据达到 60 秒就关闭连接。这里不要求服务端定期主动发送心跳，也不是从退出登录时固定等待 60 秒。连接关闭后清理当前映射，清理成功才记录离线时间；被新连接替换的旧连接不会因此把仍在线的用户记为离线。

退出接口删除 Redis 两类凭证，不会当场主动关闭已有 WebSocket。下一条入站文本心跳或业务帧会因凭证失效触发关闭；如果没有入站数据，由读空闲检测处理。推送侧主要检查 Channel 活跃状态，因此退出到真正关闭之间仍可能向旧连接写消息。

**追问补充：** 刷新同样会替换当前 Access，旧连接仍绑定旧值，后续文本帧检查也会失败并关闭。服务端关闭旧连接不会替客户端自动建立新连接；记录的离线时间是服务端清理时刻，不是客户端最后成功接收消息的位置。

<a id="a10"></a>

### A10．网关怎样认证？Refresh Token 有效为什么还返回 401？业务服务为什么再校验一次？

**参考回答：** 网关接收 HTTP 业务请求，先清理外部伪造的用户身份头和内部调用凭证头，拒绝外部访问内部路径，再根据完整路径识别登录、刷新等公开接口。受保护请求需要 Access 通过 JWT 验签、有效期和 Redis 当前值检查，成功后继续后面的路由链。

Access 无效、请求携带的 Refresh 有效时，网关返回 HTTP 401 和业务码 40103，表示当前业务不能直接放行，但凭 Refresh 可以调用刷新接口换发。刷新接口不要求先有有效 Access，但会自行验证 Refresh；Refresh 本身不能当作业务访问凭证。普通业务的 Access-Token 头在当前实现中传裸 Token。

下游业务服务也校验 Access，并把真实用户 ID 放到服务端请求上下文，供 CurrentUser 使用。操作人参数要与当前身份一致，目标会话、群角色和资源归属再由业务层检查。这样身份不只依赖一个可被外部填写的 X-User-Id，也不会把“已登录”直接当成“可以读取任意资源”。

**追问补充：** 网关返回 40103 不等于已经签发新 Token；真正换发发生在刷新接口。HTTP 网关与 Netty WebSocket 是不同入口，后者握手使用 Authorization 头认证，不能把两种头格式混为一谈。

<a id="a11"></a>

### A11．为什么使用一致性哈希选实时节点？虚拟节点、环绕和扩容分别如何理解？

**参考回答：** 登录响应需要告诉客户端连接哪个实时节点。启用发现时，用户服务取得 RealTimeService 实例列表，以 userId 在一致性哈希环上寻找目标，再返回该实例的 WebSocket 地址。节点集合不变时，同用户选址可重复；相比直接对节点数取模，增减节点时只改变部分区间的后续分配。

环可以理解为排序的数值位置。假设节点在 20、60、85，用户位置35就选择不小于35的第一个位置60；用户位置95右侧没有节点，就绕回最小位置20。新增位置40的节点后，原来交给60的部分用户改交给40，例如用户35会改变，用户50仍然交给60。

每个真实实例在代码中生成160个虚拟位置，都指向同一实际实例，使一个实例承接多个分散区间。虚拟节点不增加进程，也不限制只能连接160个用户。当前发现开关默认关闭，直接返回配置的单机地址；开启时才使用实例列表构建环，并从 ws-host、ws-port 元数据取得连接地址。

**追问补充：** 哈希选的是新建连接的目标，不会搬迁现有 TCP 连接，也不实时判断哪台机器最空闲。虚拟位置改善的是分配区间，不能直接等同于连接活跃度、消息量和 CPU 负载均匀。

<a id="a12"></a>

### A12．为什么用雪花 ID？多实例需要什么配置？为什么响应里的 Long 转字符串？

**参考回答：** 消息、红包和流水等记录需要生成服务端标识，项目使用雪花 ID，把时间、节点标识和节点内序列组合成长整型值，减少生成 ID 对数据库自增的依赖。相同时间下，不同节点和各自序列用于区分记录；ID 能标识消息，但不表示两次请求一定属于不同业务意图。

工程按服务名分配不同默认节点号，实时服务默认节点号为2，并提供 worker-id、datacenter-id 配置。同一服务启动多个实例时，需要为生成器配置不冲突的节点组合，不能让多个独立进程都使用相同默认值。这个要求来自分布式 ID 的生成规则，不是仅靠类内同步就能解决。

Java Long 范围超过 JavaScript 安全整数范围，所以 HTTP 和 Netty 输出把 Long 标识转成字符串，避免浏览器解析成数字后丢失低位。服务端内部仍以长整型存储和比较；字符串化主要保护网络传输后的精度。

**追问补充：** 唯一 ID 与请求幂等不是同一个问题。普通消息每次进入都可能得到新 messageId，即使每个 ID 都唯一，同一客户端请求的重发仍可能形成两条记录。雪花 ID 也不等于跨节点严格业务顺序。

<a id="a13"></a>

### A13．为什么使用 Kafka 解耦存储和推送？为什么不收到消息后先落库再直接推送？

**参考回答：** 当前长连接入口负责认证、格式和发送权限校验，再把消息投递到 Kafka，不同步执行聊天消息落库。存储和推送各自消费，使网络入口与后续处理分开；数据库写入变慢时可以观察存储积压，推送也不需要把整个落库耗时放在同一条同步调用链中。

两类工作有不同资源特点。推送依赖实时节点的本机连接，存储依赖数据库，两边可以分别部署和分配消费能力。Kafka 保存日志并允许消费组独立推进，也能承接一定范围的短时流量波动；持续生产快于消费时仍会积压，并不意味着下游容量无限。

先落库再推送更容易表达“保存成功后再展示”，但会让入口直接等待数据库结果。项目选择存储、推送两个 Topic 独立处理，因此接受两边进度不同，可能回显先到、数据库后提交，也可能一路发布成功另一路失败。理解这个取舍，才能正确解释回显和历史查询的差异。

**追问补充：** 两个 Topic 都按 sessionId 发布，但发布动作和消费进度不属于一个共同事务。一个 Topic 成功不会自动保证另一个成功；失败回调报告的是发布异常，不是要求所有已完成业务一起回滚。

<a id="a14"></a>

### A14．两个实时节点为什么不能共用同一个推送消费组？存储实例为什么反而要共用组？

**参考回答：** 实时连接只保存在建立它的节点内存中，而 Kafka 同组消费者分摊的是分区。如果 B 连在 N2，消息却被同组分给 N1，N1 查自己的 Map 找不到 B，就不能完成这次推送。Kafka 分配分区时并不知道目标用户的 Channel 在哪个 JVM。

项目用包含节点 ID 的独立推送消费组，让每个实时节点各自读取推送日志，再只给本机在线连接写消息。各组保存自己的消费位置，读取的是共享 Topic 日志，不是每个组复制一个 Topic。并发实例需要不同 CHAT_NODE_ID，否则它们会意外成为同组成员并分摊消息。

存储消费者使用固定共享组，因为各实例面向共享数据库执行同一种落库工作，任意实例都能处理，所以按分区分摊即可。同一事件重读时，再由数据库按消息 ID 幂等。分区是组内分配单位，一个分区同一时刻只交给正常组分配中的一个消费者，一个消费者可以负责多个分区。

**追问补充：** 代码为推送和存储 Topic 声明三个分区，因此同组增加消费者时，有效分摊并发受三个分区限制；三个分区本身不等于当前监听已经启动三个线程。不同节点独立组的消费进度可以快慢不同。

<a id="a15"></a>

### A15．用 sessionId 作为 Kafka key，就能保证同一会话所有消息按用户期望顺序出现吗？

**参考回答：** 在分区策略、序列化方式和分区数量稳定时，相同 sessionId 在同一 Topic 内进入同一分区，消费者按分区追加的 offset 顺序读取。同一用户通过同一 WebSocket 连接正常连续发送两条消息时，当前入口按序处理和发布，推送消费者也没有再把两条消息交给另一线程池并行处理，因此正常路径可以保序。

这个保证指的是分区日志顺序，不是不同客户端点击按钮的真实先后。例如 A 先点击但网络慢，B 后点击却先到 Broker，分区就可能先记录 B。不同连接可以在入口并发执行，Kafka 不会根据客户端主观时间重新安排已追加记录。

存储与推送是两个独立 Topic，也没有共同的相对顺序。并发时，可能 M1 先发到存储 Topic，而 M2 先发到推送 Topic。历史查询另外按创建时间和消息 ID 排序，不能把查询顺序、推送顺序和两个 Topic 的 offset 当成同一个全局序号。

**追问补充：** 正常组分配中，一个分区只交给组内一个消费者，不会让两个消费者各抢同会话的一条消息。不同组独立读取各自消费位置之后的记录，进度可以不同。分区数变化后相同 key 的新消息可能换分区，旧新分区之间不共享顺序。

<a id="a16"></a>

### A16．acks=all、生产者幂等、record 确认分别保证到哪里？为什么仍可能重复消费？

**参考回答：** acks=all 是生产者配置，决定 Broker 按当前 ISR 同步副本集合等规则确认发布。ISR 包含 Leader 和当前跟得上复制的副本，不是集群里的全部 Broker。项目 Topic 代码声明单副本，按此创建时并没有多副本容灾。acks 决定什么条件算发布成功，join 或回调则由业务代码选择获取结果的方式。

生产者幂等通过生产者身份、分区序号等信息识别协议重传。例如 Broker 已保存消息但确认丢失，客户端重试同一批次时，可以避免重复追加。业务主动再次 send 属于新发送，不会仅因内容相同就自动去重；生产者幂等也不阻止消费者重读同一条日志。

消费端关闭客户端定时自动提交，使用 Spring 的 record 模式，在监听方法正常返回后提交对应消费位置。例如处理 offset42 后提交43。数据库事务和消费位置提交分开，如果数据库已提交、位置尚未提交时进程退出，恢复后仍会重读42，所以消费者还要保证重复执行不重复产生业务效果。

**追问补充：** record 看的是监听方法返回，不会自动等待客户端接收。捕获异常后正常返回可能被视为已处理；重新抛异常则交给错误处理器。红包可重试入账错误配置持续重试，过期消费者当前捕获异常后主要由定时补偿恢复，两者处理方式不同。

<a id="a17"></a>

### A17．A 已看到回显，但历史查询没有消息。或者客户端重试后出现两条消息，怎么解释？

**参考回答：** 回显和历史查询分别依赖推送链与存储链。A 已看到回显，说明推送消息已经走到 A 的连接，但存储消费可能仍在积压、写库失败，或者存储发布失败而推送发布成功。因此回显不等于数据库提交，排查时要根据服务端消息 ID 独立检查存储发布、消费进度和数据库记录。

这里的客户端重试，指调用方把请求再次提交给后端，不表示工程已有完整聊天客户端自动重发代码。clientMessageId 由调用方传入，用于关联回显或错误；messageId 由服务端每次处理有效请求时生成，用作消息存储主键。当前入口没有根据客户端标识复用上次结果。

例如调用方第一次带 clientMessageId=c1，服务端生成1001并已存库；如果调用方又提交同一份请求，入口会生成1002。两个主键不同，数据库就保存两条记录。相反，同一个 Kafka 事件重投或重复消费时，携带的服务端 messageId 不变，主键冲突不会再次插入。相同正文或客户端标识，不会单独触发当前数据库去重。

**追问补充：** 发布异常回调只给 A 返回错误及 clientMessageId，没有再次发送；生产者配置的 retries 则是 Kafka 客户端内部重试，不重新进入 WebSocket 消息入口，也不重新生成 messageId。发布异常不代表数据库已回滚，一次请求可能已经在某条链成功。

<a id="a18"></a>

### A18．消息写 MySQL 与更新 Redis 是什么顺序？Canal 在这里又承担什么职责？

**参考回答：** 当前以 MySQL 作为消息持久化的事实来源，先在本地事务中按消息 ID 幂等写入数据库，再在提交成功后更新 Redis 的会话消息 ZSET。ZSET 以创建时间作为 score，保存近期消息数据。数据库回滚时不会执行正常提交回调，避免未提交消息先进入查询缓存。

缓存更新发生在数据库提交之后，所以 Redis 更新失败不会撤销已经成功的消息记录。当前会记录缓存异常。历史查询近七天先查 Redis，满足一页且没有页尾排序歧义就直接返回；不足或异常才按原始游标回源 MySQL，不会直接跳到七天前。缓存命中确实减少消息表查询，但异步更新仍有延迟。

Canal 是另一条基于 MySQL binlog 的异步变更同步路径，应用可以根据已提交的数据变化更新缓存。它不负责把 Kafka 消息首次写入数据库，也不是 MySQL 和 Redis 的共同事务。当前 Canal 默认关闭，开启后由独立处理线程读取、处理并确认变更批次。

**追问补充：** 先提交数据库再更新缓存，解决的是未提交数据暴露和回滚残留。数据库提交后进程退出、Redis 暂时失败仍会使缓存缺项，当前缓存不足会回源，但缓存够一页时不会再查消息表；够条数不等于已证明数据完全同步，不能承诺强一致。

<a id="a19"></a>

### A19．历史消息为什么使用 createdTime 和 messageId 两个游标？只传时间有什么问题？

**参考回答：** 一毫秒内可以产生多条消息，时间不能唯一定位页边界。倒序翻页时，下一页取创建时间早于末条的记录，或者创建时间相同但消息 ID 更小的记录，并按创建时间、消息 ID 倒序排列。游标条件和排序规则保持一致，才能继续取到同一时刻剩下的数据。

例如同一毫秒有105、104、103三条消息，第一页只返回105和104。下一页如果只判断时间严格小于末条时间，就会漏掉103；如果只用时间小于等于，又会重复返回105和104。加上 messageId 小于104的条件，就能在同时间记录中继续定位。

当前历史接口要求提供时间边界，限制每页条数，并结合可选的消息 ID 边界向前查询。和不断增大的 offset 相比，它直接表达从上一页末条继续查，更符合聊天记录向前翻页的模式。缓存分支按消息 ID 去重后排序；ZSET 同毫秒并列组若在页尾截断，会回源数据库保证 ID 排序，回源直接返回数据库这一页。

**追问补充：** 复合游标解决的是查询边界，不是推断真实发送先后。雪花 ID 是同时间下的唯一比较项；历史展示采用时间和 ID 排序，不等于直接使用 Kafka 分区 offset 排序，也不表示多页查询属于同一数据库快照。

<a id="a20"></a>

### A20．Redis 存最近消息，是否意味着热查询完全不访问 MySQL？离线补拉还有什么限制？

**参考回答：** 不会每次都查消息表。2026-10-31 已恢复原文“七天内先 Redis，够一页直接返回；不足再 MySQL”的主线。缓存不足、Redis 异常、坏数据或页尾同毫秒截断时，用原始 (beforeTime,beforeMessageId) 回源，避免跳到七天前漏掉热区缺口；七天前直接查询 MySQL。授权 RPC 仍执行，不能把消息表零查询说成所有服务零查库。缓存命中会减少查询，但没有同步完整性证明，仍是异步缓存。

离线补拉使用另一条查询逻辑：从当前登录身份取得用户和所属会话。近七天离线消息读 Redis；离线时间更早则合并 Redis 热区和 MySQL 冷区，按时间和 ID 正序返回。Redis 为空或异常时从原始 offlineTime 回源。登录按原文 getAndDelete 取走离线时间；重复登录不会再得到旧值。它不是让 Kafka 消费组倒退重读，也不是维护一条等用户上线才继续消费的队列。

offlineTime 来自连接清理时记录的服务端时间，登录响应会返回这项信息，客户端携带它调用接口。当前补拉没有分页，查询的是该时间后的会话消息，不等于一张精确的每用户未读清单。服务端检测断线存在延迟，记录时刻也不等于客户端最后成功保存消息的位置。

**追问补充：** 如果客户端早已停止接收，服务端稍后才清理并记录离线时间，中间消息可能没有被客户端保存，又早于补拉起点。消息仍可能在 MySQL 中由历史查询找到，漏的是按这个时间划定的补拉范围，不能直接判断为数据库丢失。

<a id="a21"></a>

### A21．同一好友申请被重复提交、由两个用户服务实例并发处理，怎样防止重复建关系和会话？事务在哪里生效？

**参考回答：** 这里指同一申请的两个处理请求，例如重复点击产生两次 HTTP 提交，在多实例部署下可能分别落到不同用户服务，并不是网关把一个请求广播给两台。单实例的两个线程也可能并发处理；一条 WebSocket 不限制 HTTP 请求数量。先查状态再处理会有竞争，因为两边可能都读到待处理。项目把申请 ID 和当前可处理状态一起放进数据库更新条件，只有成功更新状态的请求才能继续建立双向好友关系、单聊会话和双方的会话成员记录。

数据库条件更新裁决的是处理资格。一个事务成功修改后，另一个请求不能继续以原待处理状态更新；如果前一个事务回滚，状态和关联修改一起恢复，重试才能重新处理。判断受影响行数是关键，不能更新失败后仍然创建关系。

处理申请的外层业务入口开启本地事务，覆盖申请状态、关系、会话和成员数据。单 JVM 的 synchronized 不能协调两台服务实例，而数据库条件更新和事务作用于共享数据。这里共同提交的是数据库修改，Kafka 通知不因此自动加入相同事务。

**追问补充：** Spring 默认通过代理应用事务，类内自调用不会仅因内部方法带注解就额外开启事务。当前正常入口已经有外层事务覆盖处理链，因此不能把自调用直接等同于整条业务没有事务。

<a id="a22"></a>

### A22．群主和管理员同时邀请、踢人，怎样防止权限和成员状态互相穿插？

**参考回答：** 群成员变更涉及操作者角色、目标角色、已有成员和人数限制，不是单独增删一行。例如两个邀请请求都先查到人数未超限，再分别添加成员，就可能让判断和最终状态不一致；并发踢人、退群也会影响角色和成员资格判断。

当前邀请、踢人、退群等修改在数据库事务中先锁同一会话行，再读取角色和成员、执行校验与变更。遵守同一锁入口的同群修改会串行执行，锁直到提交或回滚释放；不同会话锁不同记录，避免把所有群的修改放进一个全局互斥区。

操作者来自认证上下文，角色来自数据库。群主可踢管理员和普通成员，管理员只能踢普通成员，普通成员不能踢人，群主不能直接退出。成员变更提交后才发系统通知，接收方据通知获知会话变化，业务事实仍由数据库保存。

**追问补充：** 会话行相当于这个群成员修改的共同协调点，但只有采用同一加锁约定的写入才能得到相应串行保护。请求体中的 operatorId、role 不能替代真实身份和数据库角色，隐藏前端按钮也不能替代后端授权。

### A23．afterCommit 发系统通知是不是就保证通知不丢了？为什么通知和聊天消息分开存？

**参考回答：** afterCommit 解决通知发送时机：先提交成员变更，再发通知，避免客户端先看到入群或退群通知，查询数据库时却看不到已经发生的变化。数据库回滚时不执行成功提交回调，因此不会按这条回调发布一项已回滚的群成员变更。

它仍然不是数据库和 Kafka 的共同事务。数据库提交后、通知发送完成前可能出现网络失败或进程退出；此时已提交的群成员不会因为后续通知失败而回滚。当前联系人部分通知与群通知的发送时机也有区别，不能把所有通知都概括成同一个提交后流程。

通知与聊天消息分开，是因为它们有不同业务语义。聊天消息属于会话历史，系统通知通常面向接收用户，携带事件类型和载荷，并有独立的已读状态与字符串 ID。独立 Topic 和通知表支持按用户查询和标记已读，也避免把通知字符串 ID 当成长整型聊天消息 ID 处理。

**追问补充：** 通知表保存的是已经产生并落库的通知记录，不负责代替好友或群成员表做变更。通知已存库、连接已推送和用户已读是不同状态；标记系统通知已读也不等于普通聊天已经有已读回执。

<a id="a24"></a>

### A24．图片和头像如何上传？为什么不把图片字节直接塞进聊天消息？预签名 URL 是否等于公开写权限？

**参考回答：** 当前采用 MinIO 预签名直传。服务端根据当前登录用户生成 users/用户ID/随机文件名的对象路径，返回上传地址和访问地址；客户端使用有时效的 PUT URL 直接上传对象，聊天内容保存文件地址或引用，而不是把整张图片字节放进聊天消息。

这样文件传输由对象存储承担，长连接、Kafka 和数据库主要处理消息及地址信息。预签名限定请求对象、方法和有效期，持有者可以在授权范围内使用，但这不是整个桶的永久公开写权限，也不会因为拿到一个地址就有权修改其他用户的对象。

头像修改还核对请求用户和当前身份，并把规范化后的 URL 与当前用户对象路径前缀比较。通过后更新用户头像地址，其他账号路径会被拒绝。对象上传与数据库头像地址修改是两项操作，文件传输成功不等于头像字段已经修改成功。

**追问补充：** 当前归属校验判断对象路径是否属于用户，预签名校验请求授权；它们不等于图片内容真实性检查。随机文件名主要减少对象名碰撞，容器内部连接 MinIO 的地址与客户端可访问的签名地址也分别承担不同用途。

<a id="a25"></a>

### A25．发红包时怎样保证不超扣、金额守恒？为什么 Redis 池已经生成却还不能领取？

**参考回答：** 金额从 BigDecimal 元精确转换成整数分，数据库、Redis 和分配算法都按分运算。算法验证份数及单份1分至200元的范围；普通红包先整除得到基础金额，再分摊余数，例如1000分分三份为334、333、333分。随机红包每次给剩余份额留出合法上下界，最后一份接收剩余金额，保证总额守恒。

扣余额使用带余额足够条件的数据库原子更新，把判断与扣减放在一起。扣款、红包记录和发送流水处在同一事务，避免并发请求先查都足额、后续共同超扣，也避免只扣款却没有相应红包记录。

Redis 提前准备金额池、授权信息和成员快照，但 ready 初始为0，领取脚本拒绝未开放的红包。数据库提交后才设为1并发布红包消息，回滚时尝试清理临时缓存。这样未提交的数据库红包不会仅因金额池已经存在就被正常领取。

**追问补充：** ready 表示可以领取，published 表示相关消息已经完成投递流程，两者不是一个状态。三秒防重复提交提供短时保护；已创建红包的消息补发复用红包 ID，不会重新执行发送扣款事务。

<a id="a26"></a>

### A26．抢红包为什么用 Lua？具体哪些操作必须放在同一脚本里？它是否等于分布式事务？

**参考回答：** 领取先判断身份资格和用户是否已经领取；已有记录优先返回，不再取钱。新的领取再判断既有终态、到期和 ready 门禁，通过后才取走金额并记录结果。如果拆成多次 Redis 请求，同一用户的并发请求可能同时通过未领取判断，分别取走一份。因此项目把检查、LPOP金额池、记录用户金额和时间、判断是否最后一份放在一次 Lua 执行中。

单聊只允许指定接收者，群聊以发红包时保存的成员快照判断资格。ready 为1才开放领取，脚本自身检查到期时间，所以即使到期调度稍晚，也不会因此继续允许正常领取。金额在发送时已经分配，领取时只是从池中取一份，并不重新随机计算。

脚本执行期间其他 Redis 命令不能插入这些步骤之间，保护检查和修改的整体性。但这个范围只在 Redis，不包含随后 Kafka 发布和 MySQL 入账；脚本运行错误也不等于数据库事务式的自动回滚。领取结果保留在 Redis，后续事件驱动入账，补偿扫描再对照入账确认检查结果。

**追问补充：** 已领取用户再次请求时，不再弹出金额，服务端可以读取原领取结果返回；grant 过期不能遮蔽仍在的领取记录，已有“已领完”终态也不会被后来的时钟到期覆盖。最后一份被取走时，脚本返回领完标记，业务另外发布领完事件；给用户加余额和把整个红包改成领完状态是两个处理职责。

<a id="a27"></a>

### A27．Redis 已防重复领取，为什么数据库还要唯一索引？Kafka 重复投递怎样不重复加钱？

**参考回答：** Redis 保护用户只从金额池取一份，数据库保护领取金额只入账一次。两者处在不同阶段：Lua 已确定领取结果后，事件还要通过 Kafka 交给消费者，重投、补偿或消费位置未提交都可能让数据库业务再次执行，不能只靠 Redis 的抢领检查保证不重复加钱。

当前领取表对红包 ID 与接收者 ID 建立组合唯一索引。入账事务先插入领取记录，只有首次插入成功才增加余额并写领取流水；记录已存在就跳过加钱。领取记录、余额和流水共同提交，流水失败则整笔回滚，之后重试仍能首次插入并完成一次入账。

提交后再写 Redis 入账确认，补偿任务用它跳过已完成用户。确认缓存写失败可能让事件再次发送，但数据库唯一约束仍会拦住重复余额副作用。可重试入账异常会抛出，交给账务消费错误策略持续重试。

**追问补充：** 唯一约束不是先查询是否存在，而是在并发插入时由数据库裁决。项目启动检查领取唯一约束，避免只写了去重逻辑却缺少数据库条件；幂等既依赖唯一记录，也依赖只有首次插入者执行加钱且三项修改同事务。

<a id="a28"></a>

### A28．红包过期如何退款？为什么先删金额池再处理退款，会在重试时出错？过期与领完竞争怎么处理？

**参考回答：** 创建红包后，把红包 ID 和创建时间加24小时登记到 Redis ZSET；调度取出到期 ID 后发送过期事件。消费处理先用数据库未结束状态条件争取处理资格，再在 Redis 写过期标记，封盘剩余金额，给发送者退款并写流水。状态、退款余额和流水在一个 MySQL 事务中提交。

关键是 Redis 不随 MySQL 回滚。如果第一次删金额池后数据库退款失败，第二次对空池计算就会错误得到零。封盘脚本先保存应退款金额七天，再删除池；后续重试优先读已保存结果。例如第一次算出400分，数据库回滚后仍能取得400分再次完成退款。

领完和过期都用未结束状态的条件更新竞争数据库终态，已提交的重复退款不能再次通过条件加钱。Redis 终态标记区分领完与过期，避免把过期删池误认为刚被领完；领取脚本本身也检查 expiresAt，不完全依赖调度及时关闭领取。

**追问补充：** 当前过期消费者失败时只记日志，定时补偿直接扫描数据库中已到期且状态仍为0的红包，再调用退款处理。补偿还扫描未完成发布的 grant，以及有领取记录但缺入账确认的用户；正常发布与补偿可能重叠，各业务按原稳定 ID、唯一约束和状态条件承接重复。

### A29．线上现象题：A 有回显但 B 收不到，你如何逐段排查？Redis 或 MySQL 故障时怎么判断影响范围？

**参考回答：** 我会先判断影响范围是单用户、单节点还是全部会话，再用客户端请求标识、服务端消息 ID 和会话 ID 串起处理链。A 有回显，只能说明推送链至少走到了 A 这一侧，不能直接认定 B 的网络有问题，也不能证明消息已经持久化。

先检查 B 的凭证、连接活跃状态和所在节点，以及重连后 Map 是否仍指向当前 Channel；再确认消息是否发布到推送 Topic、B 所在节点的消费组是否独立、是否有积压，群成员查询与连接写出是否报错。服务端写出成功和客户端展示完成仍是不同环节，需要按实际日志和接收情况区分。

存储侧独立检查 store 发布、存储组进度、数据库消息和历史查询条件。Redis 故障影响认证、连接凭证检查、缓存和红包领取；MySQL 故障影响关系授权、持久化和账务。Kafka 中已有记录只能说明日志里有消息，不代表数据库已经完成处理。

**追问补充：** 区分发布失败、消费失败和查询范围不匹配。例如数据库有消息但早于 offlineTime，是补拉范围问题；数据库没有记录则继续查存储链。错误处理也要看具体消费者，不能把红包入账的持续重试概括为所有消息都一定持续重试。

### A30．你怎样证明这些设计有效？如果面试官问 QPS、连接数、项目最大不足，怎么回答？

**参考回答：** 我会用现有验证记录说明机制，而不是只报技术名词。真实本机 Netty 测试覆盖握手、心跳、双端消息、连接替换和关闭；H2/MyBatis/Spring 事务测试覆盖重复消息、同毫秒分页，以及红包并发重复事件只入账一次、流水失败回滚后重试等场景。网关还有真实 HTTP 上游和认证边界测试。

截至2026年10月28日的验证记录，全工程为54项 Java 测试通过，另有12项隔离 MySQL 8.0.43 检查通过。MySQL 检查验证建表、初始化和唯一约束等实际 SQL；Redis、Kafka和部分远程调用在业务测试中使用模拟，因此这两类证据不能扩大成整套真实中间件链路都已验收。本次整理答案没有重新运行这些测试。

项目没有可证明的 QPS、最大连接数或性能提升数据，面试时会直接说明没有压测结果。就当前消息链看，最明显的边界是投递、持久化和客户端接收分别推进：回显不代表落库，写出不代表收到，离线时间也不等于已确认消息位置。这些都能结合现有处理流程解释具体影响。

**追问补充：** 证明幂等应看重复执行后的业务结果，例如多次重复领取事件最终只有一次余额增加，而不是只看方法被调用几次。功能测试、SQL检查和性能测试证明不同事情，不能把已通过用例数量换算成并发承载能力。
