## 1. B 不在线，消息去哪了？上线怎样补拉？

- 推送消费者查不到 B 的活跃 Channel 就跳过，不等待 B 上线，也不因离线反复重试。
- 存储是独立链路，不论 B 是否在线，都尝试把消息保存到 MySQL；推送成功不能证明落库成功。
- 连接清理时记录离线时间，登录响应返回 offlineTime。客户端调用 `POST /api/message/offline`，后端按当前用户所属会话查询 `createdTime > offlineTime` 的消息，按时间、ID 升序分组返回。

```text
A 发消息 ─┬─ 推送：B 不在线，跳过
          └─ 存储：保存到 MySQL

B 上线 → 客户端调用补拉接口 → 查 MySQL → 合并展示
       → WebSocket 同时接收实时消息，按 messageId 去重
```

后端不必在握手后主动补发，但客户端需要在登录或重连后触发补拉。当前只有后端接口，没有完整客户端流程；纯重连时也要有可用的补拉起点。当前无分页，离线时间不等于最后确认收到的消息游标，尚不能保证所有故障下完整补齐。

**退出到检测断线之间可能漏补拉。** 当前不是服务端定期发心跳：客户端发送约定的文本 ping，服务端检查当前凭证并回 pong；退出删除凭证后，下个文本 ping/业务帧会触发关闭。若不再有入站数据，读空闲检测兜底，默认阈值是距最后一次入站 60 秒，不是退出后固定等待 60 秒。

```text
t1：退出，客户端停止接收/保存，但服务端连接暂未关闭
t2：新消息已存库；旧 Channel 仍 active，推送却未被客户端可靠接收/保存
t3：服务端关闭并清理连接，记录 offlineTime=t3
下次补拉：只取 createdTime>t3 → t2 的消息被排除
```

这不是必然每次发生；若客户端实际接收并保存，或及时关闭连接，可能没有缺口。但当前没有客户端送达确认，Channel 活跃、服务端写出成功均不能证明客户端已保存，因此这是一种真实的设计风险。消息可能仍在 MySQL，可由历史查询找到，漏的是按断线时间划定的补拉范围。

更可靠的同步要从客户端最后连续确认接收并保存的位置补拉，配合会话序号/可靠游标、分页和消息 ID 去重，而不是仅依赖服务器检测断线时刻。主动踢连接、退出时尽早记录时间能缩小窗口，不能替代完整确认与补齐协议；这些改进当前未实现。

当前普通聊天有分段结果，没有端到端送达确认：

| 已有机制 | 表示什么 | 不能证明什么 |
|---|---|---|
| Kafka 发送 Future/ACK | Broker 按配置确认投递 | 不证明消费者入库或 B 收到 |
| 消费组位移确认 | 记录该组的处理进度 | 不证明客户端已接收；推送监听可以先提交异步写出再返回 |
| 向 A 回显消息及 clientMessageId/messageId | A 可关联本地发送消息和服务端消息 | 不证明 B 收到，也不证明存储链提交 |
| Netty 写出 Future | 服务端连接写操作的结果 | 不证明 B 应用已解析、保存或阅读 |

尚无“B 保存消息后回 ACK → 服务端维护已确认位置 → 从此位置可靠补拉”的闭环，也无普通聊天已读回执。当前组合是在线推送、发送者回显、独立存库和按离线时间查询；系统通知已读与红包 credit-ack 属于其他业务，不能当作聊天送达确认。

## 2. 两个聚合器分别聚合什么？

| 聚合器 | 阶段 | 作用 |
|---|---|---|
| HttpObjectAggregator | HTTP 握手 | 将请求头、内容片段等组合成完整 HTTP 请求 |
| WebSocketFrameAggregator | 升级后通信 | 将一条 WebSocket 消息的多个分片帧合成完整消息 |

两者都是 Netty 提供的处理器。聚合以一条请求或消息为边界；不能把多条独立聊天消息随意拼成一条。项目均配置了聚合大小上限。

## 3. TCP 字节流、TCP 分段、WebSocket 分片有何区别？

- **TCP 字节流**：提供有序字节，不保留应用发送边界。应用先发 ABC、再发 DEF，接收端可能一次读到 ABCDEF，也可能先读 AB、再读 CDEF。
- **TCP 分段**：TCP 根据传输需要把字节切成段，处理丢失、重传与排序。应用一次读取也不一定对应一个 TCP 段。
- **WebSocket 分片**：一条应用消息可以由一个文本/二进制数据帧和后续续传帧组成，帧头标明类型、长度和结束位置。

一个 WebSocket 帧可能跨多个 TCP 段；一个 TCP 段也可能包含多个小帧的数据。TCP 字节先经 WebSocket 解码器识别成帧，再由帧聚合器组合消息。

## 4. 发送时 WebSocket 变 TCP，接收时反过来？

可以理解为逐层封装和解析，WebSocket 数据通过 TCP 传输：

```text
发送：聊天对象 → JSON → WebSocket 帧 → 字节交给 TCP
接收：TCP 有序字节 → WebSocket 解码 → 分片聚合 → JSON → 聊天对象
```

TCP 不认识 JSON 或聊天业务；上层协议负责解释这些字节。客户端和服务端双向通信都遵循这套过程。

## 5. TCP 和 HTTP 什么关系？

TCP 属于传输层，负责可靠、有序地传送字节；HTTP 属于应用层，规定请求、响应的格式和含义。

```text
握手时：HTTP 请求/响应 → TCP
升级后：WebSocket 帧   → 原来的 TCP 连接
```

HTTP/1.1、HTTP/2 通常基于 TCP；HTTP/3 使用基于 UDP 的 QUIC，因此“所有 HTTP 都基于 TCP”不准确。

## 6. WebSocket 是长连接，HTTP 是一次请求一条连接？

一次 HTTP 请求结束，不等于 TCP 连接关闭。HTTP/1.1 默认支持持久连接，可在同一 TCP 连接上继续发送后续请求。

| 比较点 | HTTP | WebSocket |
|---|---|---|
| 主要交互方式 | 请求—响应 | 握手后双方可独立发消息，全双工 |
| 连接 | 可以保持并复用 | 通常长期保持 |
| 本项目用途 | 登录、查询、补拉等 | 实时聊天、心跳、在线推送 |

不能只用连接长短区分两者。WebSocket 的关键是建立双向消息通道，服务端可以及时主动推送。

## 7. boss、worker、business 和节点、JVM、进程是什么关系？

可以把它们理解为三组不同职责的线程：boss 接受新 TCP 连接，worker 处理连接 I/O 和协议事件，business 执行被分配过去的鉴权及聊天业务。严格说是 Netty 的事件循环组/执行器组，不是 Java 的 ThreadGroup 类。当前配置分别为 1、4、4。

常规部署下，一个实时服务节点就是一个运行中的 RealTimeService 实例，由一个 Java 进程承载，该进程运行一个 JVM。机器不等于节点，同一机器可启动多个实例，配置不同监听端口和节点 ID。

```text
一台机器
    ├─ Java 进程1 / JVM1：实时节点 N1
    │     ├─ boss：1
    │     ├─ worker：4
    │     ├─ business：4
    │     └─ 本机 ChannelManager、Kafka 客户端等
    └─ Java 进程2 / JVM2：实时节点 N2
          └─ 自己独立的线程组、连接索引与客户端
```

每个实例启动时，Spring 初始化 NettyService 并调用其 `@PostConstruct start()`，创建这三组执行资源。后续客户端连接共用本实例的线程组，每条连接创建自己的 Channel 和 Pipeline；不会每来一个用户就新建三组线程。一个 worker 可以管理多条连接，应用还包含 Spring、Kafka、JVM 等其他线程，总线程数不只是 1+4+4。

## 8. CompletableFuture、等待结果和回调线程怎么区分？

CompletableFuture 是代表将来结果的对象，不是一条线程。先在当前线程执行的 Redis 查询、Feign 调用，不会因为后面返回 Future 就自动变成后台任务。

| 写法 | 当前线程做什么 |
|---|---|
| `future = kafka.send(...)` | 调用发送方法，拿到表示投递结果的 Future；发送方法本身仍可能等待元数据、可用缓冲区 |
| `future.join()` 或 `future.get()` | 结果尚未完成时，当前线程等待；已完成则无需继续等 |
| `future.whenComplete(callback)` | 登记完成时执行的处理逻辑，不靠当前线程一直等待；若结果已完成，回调也可能立即执行 |
| `future.whenCompleteAsync(callback, executor)` | 将回调安排到明确指定的执行器，不会自动使用本项目 business 组 |

```text
当前业务线程 B：同步权限检查 → send → 拿 Future → 注册回调 → 返回处理后续任务
Kafka 后台线程 K：                  发送、接收确认 → 完成 Future → 可能直接执行回调

若 B 改为 join：拿 Future → B 等待…… → Future 完成后 B 才继续
```

普通聊天用 allOf 汇总几路发送，再 whenComplete 处理失败；allOf 创建汇总 Future，不是阻塞等待。红包部分链路调用 join，当前线程会等待投递结果，不等消费者数据库入账。

项目对照入口：[WebSocketHandler.channelRead0](../../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/websocket/WebSocketHandler.java) 的 `allOf(store, push, ai).whenComplete(...)` 是回调处理；[RedPacketServiceImpl.publishPending](../../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/service/impl/RedPacketServiceImpl.java) 的三次 `send(...).join()` 是逐次等待，全部返回成功才写 published=1。任何一次 join 抛异常，后续发送和完成标记都不会在本次调用中继续执行；前面已成功投递的消息也不会撤销。

不带 Async 的回调可能在完成 Future 的线程运行，也可能在注册时就由当前线程执行。因此回调里进行很慢的数据库或远程操作，可能拖住 Kafka 发送等关键线程。需要耗时处理时，应明确安排执行器；仅加 Async 也不代表自动进 business 组。

指定 executor 通常是选择“由哪个线程池/执行器负责调度”，不是固定指定某一条线程；具体由执行器安排。标准 CompletableFuture 的 Async 方法不传执行器时，通常使用公共 ForkJoinPool.commonPool()，不会识别项目变量名 business。只有显式传入 business 执行器，才交给它调度。

选择原则是按任务性质隔离资源，不是按“业务重要不重要”挑线程。网络读写、Kafka 收发线程应尽快返回；慢数据库/RPC 回调可以交给适合阻塞任务的业务执行器。耗时操作仍会占用执行它的线程，只是避免拖住网络等关键线程。线程池还要限制容量、配置超时和拒绝策略，不能认为换个池就不会积压。

异步只改变等待与执行方式，不增加下游容量。假设每秒进入 10 个任务、只能完成 5 个，待处理任务仍会持续增加，最终占满缓冲、内存或触发超时，因此线程池、任务队列和连接写缓冲都要控制。

参考：[JDK CompletableFuture](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/CompletableFuture.html)、[KafkaProducer](https://kafka.apache.org/39/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html)。

## 9. 聊天发布失败回调通知谁，会自动重发吗？

`whenComplete` 当前失败分支只记日志，并用收到原消息的 `ctx.channel()` 向发送端写错误帧。例如 A 给 B 发消息，错误返回 A 发消息时使用的那条连接，不是给 B，也不是经 Kafka 的系统通知；连接已不活跃则跳过写出。

返回内容类似 `{"error":"MESSAGE_DISPATCH_FAILED","clientMessageId":"c1"}`。客户端 WebSocket 消息监听逻辑可按 clientMessageId 找到本地待发送消息，显示失败/待确认并决定重试；这属于客户端应实现的流程，当前没有完整聊天客户端自动重试闭环，后端回调也没有直接重新调用发送。

NettyService 注册的 WebSocketHandler 在服务端运行，处理客户端发来的消息；它不是客户端的接收监听器。客户端通常自行注册 `socket.onmessage` 或 message 事件监听。当前仓库未找到 IM 客户端错误展示和重试实现；已有 MessageFlowTest 读取出站错误帧并断言错误码，只验证服务端会发错误。上述 JSON 是普通 WebSocket 文本消息，应在客户端 onmessage 中识别 error 字段，不会因为内容是业务错误就自动触发 onerror。

失败表示未能确认所有发布成功，不代表所有 Topic 都没收到。客户端重发仍可能生成新 messageId，造成重复；不能把错误提示当作可无限自动重试的依据。当前回调主要是日志和异步提交错误帧写出，没有慢数据库/RPC 处理。

## 10. 执行器和线程池是什么关系？

- 任务（Runnable）：要执行的一段代码，例如回调。
- 线程（Thread）：实际运行代码的执行单元。
- 执行器（Executor）：接收任务、决定怎样执行的接口。
- 线程池（如 ThreadPoolExecutor）：一种执行器实现，管理线程复用、任务排队和拒绝等。

```text
回调任务 → executor.execute(任务)
              ↓ 若 executor 是线程池
           排队/调度 → 池中的某条线程执行
```

因此回调参数名叫 callbackExecutor，并不代表新建了一条专属线程；它可以引用某个已有线程池。执行器也不一定是线程池，接口允许使用调用线程执行等实现。项目 business 则是 Netty 的执行器组，内部管理多个执行器/线程，也可以接收并调度任务。

参考：[JDK Executor](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/Executor.html)。

## 11. 聊天 Kafka 投递失败，会回滚数据库吗？

不会自动回滚。普通聊天入口发布 Kafka，另一个服务的存储消费者收到事件后才开启自己的 MySQL 本地事务写消息；它们没有共用事务，store 与 push 两次发布也不是一个 Kafka 原子事务。

```text
实时服务：send(store)、send(push) → Future 反映各次投递结果
                       ↓ store 事件
存储服务：消费 → 开始 MySQL 事务 → 插入消息 → 提交或回滚
```

`MESSAGE_DISPATCH_FAILED` 表示入口未能确认所有 Kafka 发布成功，不表示数据库一定已回滚。例如 store 成功、push 失败，消息可能已经存库，入口仍返回发布错误，不能撤销已提交记录。反过来，两路 Kafka 都成功、存储消费者写库失败，则回滚消费者的 MySQL 事务，原发送 Future 不会因此重新失败，也不会触发入口的这个回调。

同样，红包先提交扣款再在 afterCommit 发布，后续 Kafka 失败也不能撤销已提交扣款。`@Transactional` 在这里管理本地数据库事务，没有自动把 Kafka、Redis 和其他服务纳入其中。

## 12. ChannelManager 为什么要并发 Map、条件删除和同步绑定？

[ChannelManager](../../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/websocket/ChannelManager.java) 是本节点的连接索引，`userId → 当前 Channel`，Channel 属性反向保存用户 ID。握手成功后 bind，推送时 get，连接关闭时 unbind。绑定、关闭回调、Kafka 推送会并发访问，所以用 ConcurrentHashMap；它不共享到其他 JVM。

JDK 17 的 ConcurrentHashMap 自己实现并发控制，不是依赖业务 bind 上的锁才安全：空桶插入用 CAS，已有桶的更新用 synchronized 等机制协调，读取通常不加锁，通过 volatile/原子内存访问保证可见性。锁的范围通常是桶，不是每次都锁整张 Map；`remove(key, expectedValue)` 在内部把值匹配与删除一起完成。多个 Map 调用拼出的业务流程仍需另行协调。

```text
原来：B → C1
重连：put(B,C2)，Map 变成 B → C2，然后 close(C1)
稍后：C1 关闭回调执行 unbind(C1)
    ├─ remove(B)：误删 C2 的映射，C2 连接还在但推送查不到
    └─ remove(B,C1)：当前值是 C2，不匹配，不删除
```

`remove(userId, channel)` 原子完成“比较当前值并删除”；不能先 get 比较、再单独 remove，中间仍可能被新绑定插入。只有 removed=true 才执行离线回调，所以被替换的 C1 不会因为旧关闭回调而把 C2 当作离线。

ConcurrentHashMap 保护它提供的原子操作，bind 中的“设置属性 → 发布映射 → 注册关闭监听 → 关闭旧连接”则是多个步骤。`static synchronized bind` 用类锁让同 JVM 的 bind 调用串行，不会自动锁住未加同一锁的 get/unbind；清理仍依赖条件删除。关闭 Future 和 channelInactive 都可能清理，同一 Channel 用 `USER_ID.getAndSet(null)` 让重复清理退出。

这里有两层回调，不要混成一个：

```text
握手完成 → WebSocketHandler 调用 bind(userId, channel, 离线回调)
    → 离线回调存入 channel.attr(ON_DISCONNECT)
    → Map 发布 userId → channel
    → 注册 closeFuture 监听：关闭后执行 unbind(channel)

连接关闭 → Netty 通知关闭监听（channelInactive 也会调用 unbind）
    → unbind 取出并清空 Channel 的 USER_ID
    → 原子条件删除 Map 映射
    → 取出并清空 ON_DISCONNECT
    → 仅删除成功才 callback.run()
    → 取得断线时间，向 ctx.executor() 提交记录任务
    → ConnectionStateService.disconnected 写 Redis user:offline:{userId}
```

bind 是“登记当前连接并准备清理动作”；unbind 是“解绑并按条件通知离线”，本身不等于关闭 Socket。`closeFuture()` 只是取得连接关闭通知的 Future，`addListener` 登记回调；主动关闭由 old.close()/ctx.close() 等触发，网络断开被服务端检测后也会走清理。

实际区分两种关闭情况：

| 情况 | 关闭与监听 | unbind 的结果 |
|---|---|---|
| 旧连接被新连接替换 | bind 先把 Map 改为 B→C2，再 old.close() 关闭 C1，触发 C1 当初注册的监听 | remove(B,C1) 不匹配，不删除 C2，也不执行 C1 的离线回调 |
| 当前连接真正断开 | C2 关闭，触发 C2 自己的监听 | 若 Map 仍为 B→C2，删除成功，执行离线回调并记录时间 |

**旧连接断开不等于用户离线。** C1 被 C2 替换后关闭，`remove(B,C1)` 匹配失败，返回 removed=false，因此不执行离线回调：用户 B 仍通过 C2 在线。只有当前连接也断开、且条件删除成功时，才记录用户离线。

两种情况都走“连接关闭 → 关闭监听 → unbind”；差别是关闭的连接是否仍为当前映射。`close()` 实际关闭连接，随后由 Netty 通知该连接的监听，不是直接调用一个同名业务回调。“真正断开”包括客户端主动关闭、网络断开被检测到、空闲超时被服务端关闭等；退出登录删除凭证不等于瞬间关闭现有连接。

被替换时，旧 Map 映射在 bind 的 put(B,C2) 就已替换；old.close() 发起底层网络连接关闭，相关资源由 Netty 管理。后续 unbind(C1) 清理 C1 的业务属性并尝试条件删映射，不负责执行 Socket 关闭，也不会删除 C2。Channel 是 Java 对象，不会被 remove 直接销毁；不再被引用后由 JVM 垃圾回收，与显式关闭网络资源是两件事。

参考：[JDK ConcurrentHashMap](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html)、[OpenJDK 17 实现](https://github.com/openjdk/jdk17u/blob/master/src/java.base/share/classes/java/util/concurrent/ConcurrentHashMap.java)。

多节点各有自己的 Map 和锁，所以只能说本节点一人保留一个当前映射。支持多设备需引入设备/会话维度；跨节点即时踢旧连接还需共享登录会话或在线路由及关闭通知，当前未实现完整闭环。

## 13. 双 Token 会因持续使用自动续期吗？Refresh 有什么价值？

当前没有“每次访问自动延长”的滑动续期，也没有完整客户端自动刷新闭环。Access 为 30 分钟，Refresh 为七天；普通 HTTP 认证和 WebSocket 心跳只校验当前值，不重置 TTL，也不重签 JWT。延长 Redis TTL 本身也不能修改已签发 JWT 的 exp。

已有能力是 `GET /api/user/refresh`：携带 Refresh-Token，验证 JWT 和 Redis 当前值后，签发并覆盖一对新凭证，重新计算 Access 的 30 分钟、Refresh 的七天。因此 Refresh 的价值是“Access 过期后仍可免重新输入账号密码换发”，不是自动处理续期。Refresh 泄漏也有风险，双 Token 不自动解决凭证保护。

```text
客户端持续使用 → Access 不会自动延长，仍会到期
    → 客户端主动调用刷新接口（到期前，或按认证失败结果处理）
    → 保存新 Access、Refresh → 重试原业务请求
```

网关不会直接签发新 Token；Access 无效且请求携带有效 Refresh 时，返回 401 和专用业务码提示刷新。两类凭证都不可用则需要重新登录。上述自动调用、保存和重试由客户端实现，当前未完成。

刷新也会替换 Redis 中的 Access，旧 WebSocket 仍绑定旧凭证，后续文本帧校验会关闭旧连接，客户端需配合新凭证重连；仅收到服务端推送不能让凭证续期。当前还没有原子刷新、设备级独立会话或额外的绝对登录期限，不应把这些说成已实现。

**一个 Token 也能做登录。** 例如单个随机 Token 配 Redis 会话和滑动过期，可以支持撤销及持续使用；双 Token 是把短期业务访问与较长期换发权限分开，不是无感续期的唯一办法。Refresh 也要保护，两种 Token 一起泄漏时不能仅靠“双 Token”保证安全。当前已有 Redis 状态，不能因为用了 JWT 就宣称完全无状态或一定比单 Token 更适合。

**有刷新接口，不等于无感体验已经完成。** 后端已有换发能力；还需客户端自动触发、只发起一次并发刷新、保存新值、按规则重试和处理刷新失败。业务重试需考虑接口幂等，不能任意重放所有请求。

```text
当前行为：刷新 A1→A2 → 旧连接仍绑定 A1
    → 下一条文本 ping/聊天消息校验失败
    → ctx.close() 并 return
    → 这条聊天消息没有进入 Kafka，也没有返回专用刷新提示
    → 服务端不会替客户端自动新建连接
```

建议优先补客户端刷新及新凭证重连、暂停并暂存尚未发送的消息、明确关闭原因，以及后端原子比较旧 Refresh 并整对更新。已发但结果不确定的消息需请求幂等与确认配合，不能直接盲目补发。更进一步可把连接绑定到稳定登录会话，再校验会话过期/撤销状态，避免每次 Access 轮换都断开；不能简单删除凭证检查。以上是优化方向，当前未实现，本次只讲解与记录。

参考：[RFC 6749：Refresh Token 的职责](https://www.rfc-editor.org/rfc/rfc6749.html#section-1.5)。

## 14. 这里说的客户端是前端吗？当前有吗？

聊天场景的客户端是用户侧应用：网页版就是浏览器前端，也可以是手机或桌面应用。它负责界面、HTTP 请求、WebSocket 连接与监听、Token 刷新和重连；Netty WebSocketHandler 运行在服务端 JVM 中。

当前 IM 工程没有完整聊天前端；只有 AI 服务中的 [qwen.html](../../../AiService/src/main/resources/front/qwen.html) 和 [gpt.html](../../../AiService/src/main/resources/front/gpt.html) 演示页面，不能代表已有好友/群聊、消息确认和自动重连等完整客户端。现有后端测试客户端也不等于用户界面。

前端可以放在同仓库独立目录（例如未来新增 frontend），也可单独仓库开发，运行时通过 HTTP/WebSocket 访问后端。当前没有创建该目录或实现上述客户端流程；不需要把浏览器监听逻辑写进服务端 Java Handler。

## 15. 一致性哈希是在选什么，虚拟节点是什么？

登录时为 userId 选择 RealTimeService 实例，返回 nettyUri，客户端据此建 WebSocket。当前默认关闭发现，直接用单机地址；开启后才获取注册实例并走哈希环。完整流程见[第 04 篇实时节点定位](../04-网关鉴权与实时节点定位.md#2-%E5%86%8D%E7%9C%8B%E5%AE%9E%E6%97%B6%E8%8A%82%E7%82%B9%E5%AE%9A%E4%BD%8D)。

哈希环就是按数值排序的节点位置，选择不小于用户哈希位置的第一个节点，没有则回到最小位置。例如 N1=20、N2=60、N3=85，用户35走 N2，用户95绕回 N1；新增 N4=40 后，用户35改走 N4，其他区间不用整体重分配。数字仅作示意。

每个实例生成160个虚拟位置，value 都指向同一真实实例，不会额外启动进程。多位置改善区间分布，不保证负载绝对均匀；扩容不搬迁已有连接，只影响后续选择。userId 选实时节点与 sessionId 选 Kafka 分区是不同层次，跨节点推送仍需原消费组方案。

负载均衡是从多个实例中分配请求/连接，轮询、随机、最少连接、一致性哈希都是选址策略。这里优先考虑同用户选址稳定和扩缩容少重映射，不会实时选择最空闲机器。环按固定方向找后继，不是找绝对距离最近的位置；虚拟节点不占连接名额，160不等于160用户上限。

## 16. Nacos 是什么，项目在哪接入？

Nacos 是独立运行的基础设施，提供服务注册发现、配置管理等能力。这里主要使用注册发现：实时实例登记服务名、地址及元数据，UserService 按 RealTimeService 名称获取候选实例，再由项目的一致性哈希选择一个。Nacos 不替本项目决定用户落点，也不转发每条 WebSocket 消息。

```text
实时实例 N1、N2 → 注册到 Nacos
UserService → 获取 RealTimeService 实例列表 → 一致性哈希 → nettyUri
客户端 → 按返回地址直连实时实例
```

接入位置：

- [RealTimeService/pom.xml](../../../RealTimeService/pom.xml) 和 [UserService/pom.xml](../../../UserService/pom.xml)：引入 nacos-discovery starter，启用后由框架完成注册发现，不需要业务手写 register。
- [实时服务 application.yml](../../../RealTimeService/src/main/resources/application.yml)：服务发现地址、开关、ws-host/ws-port 元数据；用户服务也配置发现地址及开关。
- [NettyServiceLocator](../../../UserService/src/main/java/cn/qingliao/userservice/loadbalancer/NettyServiceLocator.java)：注入 Spring Cloud DiscoveryClient，调用 getInstances("RealTimeService")，具体发现能力由 Nacos 集成提供。
- [deploy/compose.yml](../../../deploy/compose.yml)：定义独立 Nacos 服务及镜像，属于部署配置，不是 Nacos 源码。

当前 NACOS_ENABLED 默认 false，定位直接返回单机 fallback；没有声称已启动 Nacos 并完成真实注册验证。HTTP 注册端口与 WebSocket 端口不同，连接地址由元数据生成。Nacos 自身还有配置中心功能，不代表本工程已使用它集中加载所有配置。

## 17. A15：sessionId 作 Kafka key，能保证聊天展示顺序吗？

当前 [WebSocketHandler](../../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/websocket/WebSocketHandler.java) 把 sessionId 转字符串，作为 store-topic、message-topic 的 key；两个 Topic 在代码中分别声明三个分区。策略和分区布局稳定时，同会话在同一 Topic 内进入同一分区，按追加的 offset 顺序读取；一个分区仍可容纳多个会话。

当前默认有 key 的分区选择基于序列化 key 的哈希再对分区数取模（内置实现使用 Murmur2 等处理），不是选实时节点的那套一致性哈希环。相同 key 字节、相同 Topic 和稳定布局才能这样讨论；不同 key 也可能映射到同一分区。

**同组分配的是分区，不是让两个消费者轮流抢同一分区的消息。** 正常组协调下，一个分区同一时刻只分配给组内一个消费者：

```text
同一消费组：P0 → C0；P1=[M1,M2] → C1；P2 → C2
    → M1、M2 都交给 C1，正常同步处理时先处理 M1，再处理 M2

不同消费组：G1.C1 → P1 的 M1、M2
            G2.C2 → P1 的 M1、M2
    → 各组各读完整序列，进度可以不同，不是各组只分一条
```

消费者是 KafkaConsumer 客户端实例，不是线程本身；Spring Kafka 常见并发容器里，一个消费者由一个消费线程驱动。多个消费者可在同一个 JVM 的不同线程，也可在不同进程。concurrency=3 可以创建三份消费并发，但当前推送监听未显式设置这个值，三个分区不等于自动创建三个线程。

如果 C1 读出 M1、M2 后再交给另一个线程池并行处理，M2 确实可能先完成；这是额外业务并发造成的，不是同组两个消费者正常共享一个分区。当前推送消费者没有这段额外分发。参考：[Kafka 消费组与线程模型](https://kafka.apache.org/39/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)。

**同一用户、同一 WebSocket 连接，向同一会话连续发 M1、M2，在正常投递且布局不变的路径下可以保序。** 当前 Netty 对同一处理器上下文串行执行，按次序发布到同分区，推送消费者没有另行并行分发，向同一接收连接按次序写出。A15 不能理解为日常连续发送都会随机颠倒；讨论的是多连接并发、跨 Topic、重连重试、分区变更等更宽范围的保证。参见 [Netty Pipeline 的执行顺序说明](https://netty.io/4.1/api/io/netty/channel/ChannelPipeline.html)。

需要区分用户点击先后、Broker 追加顺序、业务完成顺序和客户端展示顺序。A 先点击但网络慢，B 后点击却先到 Broker，分区可以先记录 B；Kafka 保留自己的日志顺序，不会还原客户端点击时刻。

两个 Topic 也不共享排序。来自不同连接的消息并发进入时，可以出现以下调用交错：

```text
线程A发 store(M1) → 暂停
线程B发 store(M2) → 发 push(M2)
线程A继续发 push(M1)

存储 Topic：M1 → M2
推送 Topic：M2 → M1
```

各 Topic 内分区仍有序，但两路顺序可能不同，不只是进度快慢不同。历史查询按 createdTime、messageId 排序，也不等于采用 Kafka offset 作为会话统一序号。

当前推送消费者没有显式把每条消息再交给另一业务池并行处理；“读完再并行执行，可能先读后完成”是设计边界，不能说成当前必然存在该处理方式。扩充分区数也可能让相同 key 的新消息换分区，旧新分区之间没有统一顺序，需另做过渡控制。

更强的会话顺序需要定义会话级序号，并协调分配、发布和处理顺序，客户端据序号排序、去重和发现缺口后补拉；仅生成序号不够。当前未完整实现，严格串行还可能带来大群热点。Kafka 有序范围参考[官方介绍](https://kafka.apache.org/41/getting-started/introduction/)。

## 18. A16：acks=all、生产者幂等、record 确认各保证什么？

当前[实时服务配置](../../../RealTimeService/src/main/resources/application.yml) 使用 acks=all、enable.idempotence=true、enable-auto-commit=false、ack-mode=record。它们分属不同环节，不是一个共同事务：

acks 是生产者配置，决定 Broker 需要满足什么确认条件，进而影响发送 Future 何时成功；它不替业务选择 join、get 或回调。获取结果的方式由代码决定：普通聊天显式 whenComplete，红包部分链路显式 join。即使设置 acks=all，也可以注册回调后继续执行，不必在业务线程原地等确认。

生产者和消费者都是 Kafka 客户端角色，运行在业务服务一侧。KafkaTemplate 包装生产者发消息，Spring Kafka 监听容器管理 KafkaConsumer 拉消息；ConsumerOfflineService 是业务监听 Bean，不是 Broker，也不等于底层 KafkaConsumer 对象。一个应用可以同时包含生产者和消费者。

| 机制 | 保证范围 | 不包含什么 |
|---|---|---|
| acks=all | 按当前 ISR 同步副本集合等规则确认 Kafka 发布 | 不等 MySQL 入库或客户端接收 |
| 生产者幂等 | 通过生产者身份、分区序号等识别协议重试，避免重复追加 | 不识别业务主动再次 send，也不阻止消费者重读 |
| record 确认 | 监听方法正常返回后，Spring 容器按记录提交消费进度 | 不自动等待异步业务结束，不是客户端 ACK |

ISR 包含 Leader 和当前跟得上进度的同步副本，不是 Kafka 所有 Broker，也不一定包含全部配置副本。acks=all 还需结合 min.insync.replicas 判断是否接受写入；当前 Topic 代码声明 replicas(1)，按此创建时只有一个副本，没有多副本容灾。

生产者重试示例：Broker 已追加 M1，确认响应丢失，客户端重传同一批次；幂等协议可识别已有序号，避免再追加。业务代码再次 send，即使 JSON 相同，也不是这类协议重传。当前普通消息客户端重发还可能得到新 messageId，数据库按服务端 ID 去重不能代替请求幂等。

**消费进度什么时候提交、存在哪里（2026-11-07 补充）：** 这里指消费组已提交的 offset，按“消费组 + Topic + 分区”分别记录，含义是恢复时下一条从哪里读，不是业务 messageId，也不是整组只有一个计数。当前存储组是 infinite-chat-store-group，订阅 store-topic。

- 提交时机：存储服务关闭 KafkaConsumer 定时自动提交，使用 Spring Kafka 的 record 模式。正常成功路径是 consume 调用存储服务，MySQL 本地事务提交，consume 正常返回，再由监听容器提交下一条 offset；不用在业务代码里手写 acknowledge。监听异常则进入错误处理流程，不能概括成永远不提交。
- 保存位置：消费者向 Kafka 的组协调器提交，最终记录在 Broker 端内部 Topic __consumer_offsets，协调器也有查询缓存；不在业务 MySQL 消息表、Redis 或消费者本机文件中。概念上可看作 (infinite-chat-store-group, store-topic, 分区0) → 43，表示该组此分区下次从 offset43 读。
- 区分内存位置：KafkaConsumer 当前已拉取位置可以先向前移动，不能当作已经提交的持久恢复点。消费者重启或分区重新分配时，在有效提交仍存在且无显式重置等前提下，以已提交位置恢复。
- 重复窗口：MySQL 提交与 Kafka 位移提交是两个独立动作，写库完成后、位移提交前退出，就会重读下方 offset42 的例子，因此需要消息主键幂等。位移提交不会删除 Broker 中的消息，也不等于接收人收到或已读。

存储语义依据：[Spring Kafka record 提交](https://docs.spring.io/spring-kafka/reference/3.3/kafka/receiving-messages/message-listener-container.html)、[Kafka 消费位移保存](https://kafka.apache.org/40/implementation/distribution/)。这是配置与源码核对，没有新增真实 Kafka 故障演练结论。

**同组为何能并行而不正常抢到同一分区的同一条消息：** 常规消费者组先分配分区，再各自拉取；同一分区同一时刻通常只由组内一个消费者负责，一个消费者可以负责多个分区。因此不是全组只有一个工作，而是同分区不分给多个成员同时读。每个分区的已提交 offset 各自推进，P0 的 offset42 与 P1 的 offset42 不是同一条 Kafka 记录。

例如当前[Topic 声明](../../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/config/KafkaTopicConfig.java) 为 store-topic 配置三个分区，若 Broker 按此建立，同组可以由 C1 负责 P0、C2 负责 P1、C3 负责 P2，并行处理与提交各自分区。只订阅该 Topic 且有五个组成员时，部分成员没有分区；若只有一个分区，才只能由组内一个成员负责。实际 Broker 分区数仍需运行查询核实。

“同组分区分工”不消除提交窗口：C1 写库后、提交位置前退出，P0 转交给 C2，C2 从 P0 旧的已提交位置恢复，仍会重复处理。这个重复来自故障恢复与提交边界，不是因为正常情况下全组无分工地同时读取。不同消费组则各有进度，可以分别读到同一条记录。依据：[KafkaConsumer 消费组与分区分配](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)。

```text
组已提交位置=42，表示下次从 offset42 读取
    → 读取 offset42 的 M1
    → MySQL 插入并提交成功
    → 此处进程退出，尚未提交消费位置43
重启：仍从42读取 M1 → 再次处理同一条记录
```

因此消费者副作用仍需幂等。当前聊天存储靠[MessageMapper](../../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/mapper/MessageMapper.java) 中 messageId 主键冲突不重复插入；红包靠首次领取记录的唯一索引与同事务余额、流水控制。Broker 只追加一次，也可能被消费者处理多次。

`spring.kafka.consumer.enable-auto-commit=false` 是关闭 KafkaConsumer 自带的定时自动位移提交；`spring.kafka.listener.ack-mode=record` 是 Spring Kafka 容器的提交策略，二者由不同层解释。关闭前者不是完全不提交，也不要求这里手动 acknowledge，而是交给容器管理。

定时自动提交并非必然早于业务完成：若每次 poll 后同步处理完全部记录，再下一次 poll 或关闭消费者，也能做到至少一次处理。风险在于提交依据是已拉取位置，不是业务成功回执；若只放入内存/异步队列就继续拉取，可能进度已提交而工作未完成。record 则明确以监听返回作为正常提交边界，但异常被吞或异步任务未完成仍可能误判。不能把 Kafka 定时自动提交与 Spring 的其他 AckMode（如 BATCH/TIME）直接混为一谈。

“监听方法”就是框架收到消息后调用的业务方法。例如[ConsumerOfflineService.consume](../../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/consumer/ConsumerOfflineService.java) 标注 `@KafkaListener(topics="store-topic", groupId="infinite-chat-store-group")`。方法名 consume 可自定义，注解才把它注册为该 Topic/组的处理入口；[存储服务配置](../../../OfflineDataService/src/main/resources/application.yml) 同样关闭自动提交并使用 record。

```text
Spring 启动 → 根据 @KafkaListener 创建并启动监听容器
    → 容器管理 KafkaConsumer、消费线程和 poll 拉取
    → 对每条记录调用 consume(message)
    → JSON 解析 → saveMessageToMySQL → 数据库事务提交
    → consume 正常返回
    → record 模式提交该条记录后的消费位置
```

幂等是同一业务操作重复执行，最终业务效果与执行一次相同，不要求第二次连方法都不进入。Broker 重传去重和数据库幂等属于不同阶段；例如重复处理相同 messageId，数据库保持一条消息，或重复领取事件只加一次余额。

幂等是目标，乐观锁/条件更新是可能用到的并发控制手段。单纯“查不存在再处理”有竞争窗口；应由唯一约束插入或带旧状态条件的 UPDATE 原子裁决，再把资格记录和业务副作用放在同一事务。退款 `WHERE status=0` 成功后改为2，可防相同退款重复生效；普通版本号乐观锁不一定防重，重复事件重新读取新版本后仍可能再次加余额。关键是识别同一业务事件，并保证它只产生一次副作用。

catch 后正常返回可能让容器认为已处理；抛异常则走错误处理器，是否持续重试由配置和异常类别决定。红包可重试入账错误有持续重试策略，过期消费者当前捕获异常后不重抛，主要依赖补偿任务。

普通 store-topic 与 message-topic 的消费者都配置 record，但两个应用没有像红包入账那样配置无限重试错误处理器，采用框架默认处置。默认 DefaultErrorHandler 对可重试失败累计尝试十次后记录错误并恢复跳过，某些不可重试异常直接恢复处理。因此不能推导“处理失败就永远不提交、必定一直重读到成功”。生产者 retries=3 不控制消费者重试次数。依据：[Spring Kafka 默认错误处理](https://docs.spring.io/spring-kafka/reference/3.3/kafka/annotation-error-handling.html)。

| 当前情况 | 监听结果与消费进度 |
|---|---|
| 两边 JSON 解析等同步异常 | 从 consume 向外抛，交给各自容器默认错误处理器；机制相同 |
| 推送查询群成员的同步 RPC 异常 | 同样抛给容器，不是所有推送错误都只打印日志 |
| 存储写库抛异常 | 异常传给容器，错误处理器安排重投；重试耗尽仍可能跳过 |
| 存储提交后更新 Redis 缓存失败 | cache 内捕获并记日志，数据库已提交，监听可正常返回并提交进度 |
| B 不在线，查不到 Channel | 正常返回，进度可提交，不等待 B 上线 |
| 推送异步写出失败 | 写出回调只记日志；监听可能早已正常返回，进度可已提交，不会据此自动重投 |

所以要比较的是异常传播方式，而不只是消费者名称：异常从监听方法抛出时，两边都交容器处理；仅在异步回调或内部 catch 中记录的失败，不会自动变成监听异常。存储有 MySQL 本地事务与消息主键去重，推送没有可撤销已发送帧的事务；重新消费时已经写出的消息不会被撤回，仍可能重复推送。

**推送成功、消费位移未提交就退出，会不会推两遍？** 会。当前[ConsumerMessageService](../../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/consumer/ConsumerMessageService.java) 重新处理同一 Kafka 事件时，会沿用原 payload 的 messageId 再写 WebSocket 帧，没有完整的推送去重。存储主键只防重复落库，不会拦截另一路推送。应区分网络收到两份与界面显示两条。

完善方案是客户端按 messageId（或会话加 messageId）对消息模型去重：首次接收插入，重复接收不再新增，可按业务合并状态；历史补拉与实时推送走同一套规则。只给渲染项设置 key 不等于完成数据去重，跨重连也要考虑去重依据的保留。当前完整客户端尚未完成，不能把该方案说成已经验收。

若进一步要求可靠送达，还需业务 ACK、未确认重试和补拉协议，但 ACK 丢失仍可能触发重发，所以接收端仍需幂等；送达 ACK 与已读又是不同状态。单独加 Redis“已推送”标记不能消除窗口：先标记后发送，宕机可能漏发；先发送后标记，宕机仍可能重发。Kafka 位移与 WebSocket 副作用没有统一原子提交。机制参考：[Kafka 外部系统交付边界](https://kafka.apache.org/42/design/design/)。

“未提交位置”也不表示下一次 poll 必然自然重读：poll 后内存读取位置可能已经前进，失败重投由容器 seek/重新提交记录等机制安排；进程恢复才依据已提交位置重新读取。record 是提交时机，不等于业务结果、无限重试或不漏消息的完整保证。

当前推送监听提交异步 writeAndFlush 后即可返回，record 不会替它等待客户端确认。以上 Kafka 确认均不能当作 B 已收到或已读；提交消费进度也不是删除 Broker 日志。

异步写出失败后，当前只记录日志，没有自动重发该条推送、登记接收方未送达或触发补拉，也不会因此给发送者返回入口的 MESSAGE_DISPATCH_FAILED（那个错误针对生产者发布）。因此 A 已看到回显而 B 界面少一条消息是可能的。若存储链成功，消息仍可从历史查询获得，但不会因这次失败自动显示；按 offlineTime 补拉也不能兜住全部缺口，例如失败消息早于稍后记录的断线时间。不能说“存在补拉接口，所以失败推送必定恢复”。

参考：[Kafka 生产者配置定义](https://github.com/apache/kafka/blob/3.9.0/clients/src/main/java/org/apache/kafka/clients/producer/ProducerConfig.java)、[生产者幂等边界](https://kafka.apache.org/39/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html)、[Spring Kafka 提交模式](https://docs.spring.io/spring-kafka/reference/3.3/kafka/receiving-messages/message-listener-container.html)。

## 19. A17：两个消息 ID 与三种重试怎样区分？

| 标识 | 来源 | 当前用途 |
|---|---|---|
| clientMessageId | 调用方放在请求中，DTO 声明字段不等于后端生成它 | 原样带回回显/错误，关联调用方发出的消息；不用于入口去重 |
| messageId | WebSocketHandler 校验通过后调用 ids.nextId() 生成 | 服务端消息标识、数据库主键与存储去重依据 |

```text
调用方请求：clientMessageId=c1
服务端处理：生成messageId=1001
返回回显：clientMessageId=c1 + messageId=1001
```

当前没有完整 IM 客户端的超时重发、重试按钮或接收错误后自动重发代码。参考答案描述的是条件场景：如果调用方因没收到回显、断线或收到错误而再次提交请求，后端每次都会重新分配 messageId，不是在声称项目已有自动重试流程。

| 重试/重复发生位置 | 会重新进入消息入口吗 | messageId 是否改变 |
|---|---|---|
| 调用方再次提交同一请求 | 会 | 当前重新生成，例如1001变1002 |
| Kafka 生产者内部重试，配置 retries=3 | 不会 | 仍是原消息1001 |
| 消费者恢复重读或重复处理同一事件 | 不会 | 仍是原消息1001 |

发布失败代码在 WebSocketHandler 的 whenComplete：只记日志并给原发送连接返回 MESSAGE_DISPATCH_FAILED 和 clientMessageId，没有重新调用 send。这个错误码不会自动执行客户端逻辑；内部生产者重试由 Kafka 客户端按可重试异常及超时/次数约束处理，不是客户端重发。

因此同一1001重复入库可由主键去重；调用方重发产生1002，则两个主键都可入库。客户端没收到回显也不代表1001没成功，双 Topic 可能部分成功。这里只解释当前行为，不展开其他发布设计。

## 20. Canal：为什么数据库写完了还需要另一条缓存同步路径？

Canal 是读取、解析 MySQL binlog（数据库变更日志）的组件。Canal Server 是独立服务；工程内的 [CanalClient](../../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/client/CanalClient.java) 从它拉取变更，再执行 Redis 更新，不是定时查询整张消息表。

client 表示调用/连接某个服务的一方，不专指前端或微服务间 Feign 调用。这里 CanalClient 是 OfflineDataService 同一 JVM 内的 Spring 组件，启用后由 CommandLineRunner 启动 canal-consumer 后台线程，持续拉取变更并处理缓存同步；不是独立微服务，也不是 Controller 接口。[CanalConfig](../../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/config/CanalConfig.java) 创建 Canal 官方库的 CanalConnector 负责连接与拉取，项目自定义的 CanalClient 负责消费循环、业务转换、Redis 写入与确认。client 包名只是代码组织约定，不会自动赋予功能。

Canal Server 由[部署配置](../../../deploy/compose.yml)中 canal 服务声明，使用 canal/canal-server:v1.1.7 镜像、11111端口和 cdc profile；启用该 profile 后由 Docker 启动独立容器中的服务进程，不是 CanalConfig 创建了服务端。一个 Canal 服务实例不等于独占一台机器，可与其他服务部署在同一台机器；当前部署文件只声明一个 Canal 服务，不是每个实时节点各带一份。

与实时推送相比，两者都有“消费事件、处理、失败重试”的结构，但推送消费 message-topic 后写用户 Channel，Canal 消费数据库变更后写 Redis；Canal 不会再次向 A/B 推送消息。实际业务重叠在缓存更新：afterCommit 与可选 Canal 都会尝试更新同一会话缓存，因此启用 Canal 后存在重复写缓存的工作；不表示客户端会因此收到两次 WebSocket 推送。

重复 ZADD 是否安全取决于 member 是否完全一致，不取决于 JSON 里面 messageId 是否相同。2026-10-31 已修复此前两条写入路径的差异：afterCommit 与 Canal 共用 [MessageResponses](../../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/utils/MessageResponses.java) 和 Hutool JSON，顶层 content、body、replyId 与时间戳一致；文本及红包的双路径 member 相同已通过测试。ZSET 仍按完整 JSON 去重，不是按 messageId；历史遗留的旧格式成员不会自动清理，查询会按 ID 去重，不足或格式错误时回源。真实 Canal 仍未联调。

```text
store-topic → 存储消费者 → MySQL 提交
                              ├→ afterCommit → Redis（已有默认路径）
                              └→ binlog → Canal Server → CanalClient → Redis（可选）
```

若数据库已提交，应用却在 afterCommit 更新缓存前退出，数据库记录不会随之撤销。启用 Canal 后，可以通过独立的 binlog 路径再次尝试同步；仍受日志保留、消费进度和服务可用性等条件限制。Kafka 负责把聊天事件交给存储消费者写库，Canal 负责从已发生的数据库变更更新缓存，两段职责不同。

当前客户端只处理 message 表的 INSERT，将消息写入会话 ZSET，以消息时间为 score，清理七天前记录并设置八天 TTL；没有处理该表 UPDATE/DELETE。[配置](../../../OfflineDataService/src/main/resources/application.yml) 的 canal.enabled 默认 false，关闭它不会关闭原有 afterCommit 缓存更新。

Canal 批次处理成功才 ack，失败 rollback(batchId) 后重试；这里 rollback 是回退 Canal 批次消费位置，不是回滚已提交的 MySQL 事务，也不会撤销已执行的 Redis 写入。数据库提交到 Redis 更新有时间差，属于异步同步，不能称为强一致；当前真实 Canal 环境尚未联调。

## 21. A20：每次历史查询都查 MySQL，Redis 还有缓存收益吗？

此前实现确实没有挡住消息表查询：先查 MySQL，再读 Redis 合并。这偏离了原文 9.6.6 的缓存优先主线，不能称为已完成的冷热查询优化。2026-10-31 已修正源码，完整流程见[第 05 篇](../05-消息存储查询与AI链路.md)。

现在先校验会话权限；七天内查 Redis，够一页且页尾无同毫秒排序歧义直接返回，消息表 SELECT=0。缓存不足、异常、坏数据或并列组截断时按原始游标回源 MySQL；七天前直接查 MySQL，不读 Redis。相关用例明确验证了命中不查消息表、冷查询不读 Redis，测试使用真实 H2 与模拟 Redis。

原文不足时将 MySQL 边界推进到七天前，会漏掉七天内尚未缓存的记录。当前保留原文主线，只修正回源边界：数据库查完整一页，不再先查库或无条件合并。没有改成按页缓存，也没有引入覆盖区间协议。

**面试第 27 题：游标就是上一页取到哪里。** 这里是聊天历史翻页参数，不是 Kafka 消费 offset。向上翻历史时，将上一页最后一条的时间和消息 ID 一起带回来，在同一会话中继续向更早的位置取。下面是简化毫秒值的示意数据，不是运行结果：

| 时间 | messageId | 每页两条时的位置 |
|---|---|---|
| 1003 | 106 | 第一页 |
| 1002 | 105 | 第一页末尾 |
| 1002 | 104 | 第二页 |
| 1002 | 103 | 第二页末尾 |
| 1001 | 102 | 第三页 |
| 1000 | 101 | 第三页末尾 |

第一页后游标是 (1002,105)。下一页若只查时间 <1002，会漏掉 104、103；若只改为时间 <=1002，又会重复取到 105。正确范围是“时间 <1002，或者时间 =1002 且 ID <105”，再按时间倒序、ID 倒序取两条，得到 104、103。时间定主要顺序，唯一 ID 打破同毫秒并列。

“按原始游标回源”是查询位置不变、数据来源切回 MySQL：例如仍从 (1002,105) 继续取，而不是缓存不够就跳到七天前。当前数据库重查完整一页，不是拿缓存若干条再从七天前凑剩余条数。ZSET 同分按成员字符串排序，而当前成员是完整 JSON；截取到的同分片段不一定就是业务 ID 最大的那几条，无法确认页边界时需要回库。排序依据参考：[MySQL LIMIT 与确定排序](https://dev.mysql.com/doc/refman/8.0/en/limit-optimization.html)、[Redis ZSET 同分排序](https://redis.io/docs/latest/develop/data-types/sorted-sets/)。

**只拿 ID 分页可不可以？** 可以，若统一以 messageId 倒序，就可在限定 sessionId 后用“ID 小于上一页末尾 ID”继续查。唯一 ID 足以形成这种排序，不代表该顺序必然与当前 createdTime 排序相同；当前选择时间为主、ID 打破并列，并配合按时间查热区与裁剪。不是所有分页都必须双游标，修改时要一起调整查询、索引和缓存约定，而不是保留时间排序却只传 ID。雪花 ID 大体随时间增长，也不能仅凭不重复证明与消息时间严格同序。

**Redis 实际怎么存：** 当前聊天历史缓存按会话共用一个 ZSET，写入见[MessageServiceImpl.cache](../../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/service/impl/MessageServiceImpl.java)，前缀见[CommonConstant](../../../Common/src/main/java/cn/qingliao/common/constant/CommonConstant.java)。

| 部分 | 当前内容 |
|---|---|
| key | 字符串 session: 加 sessionId，例如 session:123 |
| Redis 类型 | ZSET（有序集合） |
| score | createdTime 对应的毫秒时间戳 |
| member | 整个 MessageResponse 序列化的 JSON 字符串，内部含消息 ID、发送者、正文等 |

同一会话的多条消息是这个 ZSET 的多个 member，不是每条消息单独一个 key。ZSET 的唯一性按整个 member 字符串判断，不按 JSON 内部 messageId 字段判断；相同 ID 若产生不同 JSON，仍可能成为两个 member。七天热区通过按 score 裁剪管理，整个会话 key 在写缓存时设置八天 TTL，这两个时间用途不同。

MySQL 用 BIGINT 按 ID 分页可行，但不能直接把完整雪花 long ID 换成 ZSET score 而忽略精度：score 是 double，整数精确表示范围为正负 2^53，较大的雪花 ID 可能丢精度。[Redis score 精度与成员唯一性](https://redis.io/docs/latest/commands/zadd/)。这是当前结构与可选方案的解释，没有修改业务实现。

边界：授权仍可能让用户服务查库；异步缓存即使够一页，也不能证明没有同步缺口。恢复缓存收益不等于实现强一致，不能把“够条数”解释成完整性证明。

## 22. A21：只有一条 WebSocket，为什么还能并发处理同一个好友申请？

好友申请和接受/拒绝走 HTTP，不经 WebSocketHandler 转发：客户端 → 网关 /api/contact/** → UserService 的 ContactController → ApplyFriendServiceImpl。创建申请 POST /api/contact/{A}/friend/{B}；B 处理申请 POST /api/contact/{B}/application/{status}，通过状态为1。UserService 发布系统通知到 Kafka，实时服务 SystemNotificationConsumer 再通过 B 的 Channel 推送，这是通知通道，不是业务请求入口。

一条 WebSocket 不限制客户端发起多个 HTTP 请求，也不把 HTTP 绑定到某个 UserService。默认网关固定转发 localhost:8104；启用服务发现的部署覆盖配置后才使用 lb://UserService，在多个实例间分配各个 HTTP 请求。正常单次转发选一个实例，不会把一个 HTTP 请求广播给两台。

A21 指“同一申请的两个处理请求”，不是“同一 HTTP 请求天然执行两次”。例如客户端连点通过发出 R1、R2（条件场景，不表示工程已有前端重试代码），多实例部署时可分别落到 U1、U2；单实例也可能由两个请求线程并发处理。即使两边都已查到申请待处理，UPDATE WHERE apply_friend_id=? AND status IN (0,3) 也只允许一方把状态改为通过1；事务提交后另一方条件不再匹配，不能重复创建好友关系和会话。保护针对共享业务记录，不取决于 WebSocket 连接数量。

## 25. 面试第 29 题：领取入账补偿在补什么？

领取 Lua 成功只代表占到份额并写了 Redis 记录，余额还要经过 Kafka 与 MySQL。当前[补偿任务](../../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/scheduler/RedPacketRepairJob.java) 默认每轮结束后间隔 30 秒执行，扫描 redpacket:*:records；逐个用户检查 redpacket:{红包ID}:credit-ack 的对应 field，缺失时按原红包、用户、金额和领取时间重建领取事件，再发 Kafka，继续走原入账逻辑，不再次取一份金额。

以红包 888、用户 20、金额 200 分示意：records 的 field20=value200 表示已领取，records:times 保存时间；credit-ack 的 field20=value1 表示该份数据库账务已提交。这里的 credit-ack 是 Redis 业务标记，和 Kafka 消费 offset 不同。

缺确认可能是事件未发布、数据库回滚，也可能是数据库已提交但确认没写。重放靠[入账服务](../../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/service/impl/RedPacketServiceImpl.java) 的“红包ID+领取人”唯一约束裁决：首次插入才加余额、写流水，三者同一本地事务；重复则不再加钱，提交后补写确认。确认必须在提交后写，避免账务失败而补偿误判成功。

Kafka 重试处理已进入 Kafka 的事件，业务扫描还覆盖 Lua 成功但消息尚未发布的窗口。任务还包含未发布红包与终态修复，不全等于领取入账重试。恢复依赖 Redis 持久化、七天领取证据保留及外部依赖可用，不能当作完整灾难恢复；以上为源码核对与示意，没有新增真实环境验证。完整业务链仍见[红包与异步账务](../07-红包与异步账务.md)。

## 26. 面试第 30 题：退款重试与最后一份领取并发

**过期触发链：** [DelayTaskEnqueuer](../../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/consumer/DelayTaskEnqueuer.java) 消费创建事件，将红包 ID 注册到 redpacket-expire-zset，score=创建毫秒时间+24小时。[ExpirationDispatcher](../../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/scheduler/ExpirationDispatcher.java) 每秒分批调用 Lua，以 Redis TIME 得到现在，取并删除 score<=现在 的本批 ID，再异步投递 redpacket-expiration-topic；[ExpirationTaskExecutor](../../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/consumer/ExpirationTaskExecutor.java) 收到后执行过期、封盘、退款。score 是绝对到期时间，不是“已过期”枚举；Kafka 收到的是已到期任务，不再等待到期。

取删与 Kafka 发布之间仍有窗口，不能说 Lua 保证任务可靠到达；过期消费异常当前也被捕获。约 30 秒间隔的补偿任务另扫数据库中过 24 小时仍未结束的红包，再调用同一过期处理，和每秒 Redis 到期扫描是不同职责、不同入口。

退款重试指后台再次处理同一笔过期退款，不是用户重新领红包。示例：1000 分红包已取走 700 分，池余 300 分；过期处理在数据库事务内条件更新状态，Redis 立过期标记，再由[freeze-refund.lua](../../../RedPacketService/src/main/resources/lua/freeze-refund.lua) 保存 refund-amount=300、删除池。随后若数据库退款失败，状态、余额与流水回滚，Redis 不随之回滚；补偿再处理时从快照读回 300，不会因池为空就误算为 0。

状态改为已过期与退款余额、流水同一本地事务。上次回滚，可再次争取处理资格；上次提交，重复处理的条件更新失败，不再退款。并发两个退款事务也由同一行更新锁和条件协调，不能把刚执行但未提交的状态更新当成永久成功。当前过期消费者捕获异常，失败恢复依赖补偿任务等，不是承诺 Kafka 原消息无限重试。

最后一份领取与封盘的金额竞争在 Redis：领取脚本通过到期/状态检查后先 LPOP，就留下领取记录，封盘仅计算余下金额；过期先立标记并封盘，则新领取拒绝。领取的检查、取钱、记录为一段 Lua，封盘的读剩余、保存快照、删池为另一段 Lua，在同一 Redis 节点不互相穿插，防止同一份既取走又计入退款。

数据库的未领完→已领完/已过期条件更新另管终态。领取 Lua 已取走最后一份，但领完事件还未处理时，过期事务仍可能先取得终态，此时退款基数可为 0，原领取继续入账。不要把 Redis 金额归属和异步数据库终态混成同一个先后。完整流程见[退款实现](../../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/service/impl/RedPacketServiceImpl.java)和[第 07 篇](../07-红包与异步账务.md)；仍受快照七天保留与跨系统失败窗口限制，本次没有新增实机并发验证。

## 28. 面试第 40 题：题集来源与四项评测怎么通俗地说？

Ragas 是用于评估大模型应用的 Python 框架，类似按规则批改问答的工具。当前脚本先读题集、调用 Java 评测接口得到回答和实际检索资料，再连同问题、参考答案交给 Ragas。脚本配置 qwen3-max 作为裁判模型，部分评分计算还用 text-embedding-v4，最终输出逐题分数与 CSV。框架负责组织评估与计算，自动分数仍需结合人工检查。参见 [Ragas 官方评测入门](https://docs.ragas.io/en/stable/getstarted/evals/)。

AI 根据知识库生成问题和参考答案，再人工对照原文修正，是可行的制作方式；“我自己检查过”应对应实际检查。当前工程 181 题来自课程附件，其中 15 题是无答案负样本，不能把使用现成题集说成自己生成并逐题审核。

评测同时看实际检索资料和模型回答：context precision 看找来的资料是否有用、相关内容是否靠前；context recall 看回答所需信息有没有找全；answer relevancy 看回答有没有跑题；faithfulness 看回答有没有资料依据。例如问红包多久过期、剩余金额怎么办，应找到“24 小时”和“退回发送者”两部分，回答不能编成 48 小时。

资料里没有答案的问题另外看是否明确拒答，有答案的题还要看是否误拒。当前评测检查文档、切分、检索、重排、提示词和模型配合后的问答效果；接口是检索加单次回答，不经过工具调用与多轮会话，不能代表整个 Agent 所有能力。

效果不理想时先看具体错题：原文没有答案就补资料；有答案但未检索到，就查入库、切分与候选数量；候选有但最终上下文没有，就查重排与过滤；正确资料已给模型却答错，再查提示词和生成。切分调整后需重新入库并处理旧索引数据。增加候选数或上下文片段数可能提升覆盖，也可能引入干扰、增加耗时，不是越大越好。

评测脚本不会自动调参。每次尽量只改一个因素，以同一套题、文档和其他设置复测，比较分数、错题和耗时，再决定保留或恢复；最后用没参与调参的新题检查。“合格”要结合关键问题、拒答和耗时要求，没有通用及格分。以上为定位与调优方案，没有真实测试结果时不声称提升比例。

## 31. 简历 MySQL 一行具体是什么意思？

简历表述：“理解索引、联合索引与事务隔离，了解执行计划分析及 SQL 优化思路。”这是知识与分析能力的描述，不代表已经做过生产慢查询治理，也不代表掌握全部数据库底层。

- **索引：**帮助数据库按一定顺序组织和定位数据，类似目录；常见 InnoDB 索引用 B+ 树组织。索引可以减少不必要的扫描，也需要空间和写入维护成本，不能给每列都无条件加索引。
- **联合索引：**一个索引按多个字段依次组织，不是各建一个单列索引。假设查询某会话的消息并按时间、消息 ID 排序，可以考虑 `(session_id, created_time, message_id)`，先定位会话，再利用后续字段的顺序。实际是否适合，还要结合 WHERE、ORDER BY、查询列和执行计划；这里是说明设计思路，不是声称已调整工程索引。
- **事务隔离：**多个事务同时读写时，规定它们能看到哪些数据。红包的领取记录、余额、流水一起成功或回滚，主要体现原子性；另一个事务会不会读到尚未提交的余额，属于隔离性问题。隔离级别、MVCC 与锁需要区分，单靠“用了事务”不能消除重复领取和重复入账，仍要业务约束。
- **执行计划：**在 SQL 前加普通 `EXPLAIN`，看数据库预计采用哪条访问路径，例如 `key` 选用什么索引、`rows` 估计扫描多少行、`Extra` 是否出现额外排序等。估计不等于实际耗时，不能只凭一个字段判定 SQL 好坏。
- **SQL 优化思路：**先找慢查询及其业务场景，结合执行计划检查扫描和排序，再考虑索引、条件表达、返回列数和分页方式，最后比较结果是否正确、耗时是否改善。例如连续历史翻页可考虑复合游标，减少大 OFFSET 丢弃前面记录的成本；这不直接支持任意页跳转。

面试先准备到能解释“为什么这样查、索引怎样组织、并发时会怎样”，不要只背术语或没有依据的性能提升数字。简历中的“了解执行计划分析”表示具备基础判断思路，不等于做过生产级优化。

## 知行：RAG、偏好与 PDF 解析

- RAG 是“检索增强生成”：先按当前问题检索少量资料，再把片段加入生成模型的上下文，不是重新训练模型，也不等于系统提示词。
- 当前知行项目没有独立 Skill 机制：角色通过固定 SystemMessage 提示词配置，由 LangGraph4j 路由执行，配合 MCP 工具、RAG 和三层记忆。没有技能包注册、选择及按需加载流程，不能把角色提示词文件直接称为 Skill 编排。
- 明确偏好放当前 State 或用户档案，必须遵守的规则由提示词与代码保证；大量好友攻略、游记和避雷经验适合按需检索。
- 文字型 PDF 用 Tika/PDFBox 等解析库提取文字；扫描件需 OCR。提取文字、Embedding 转向量和模型生成是三个不同步骤。
- 知行当前在相关 Agent 调用模型前检索私人资料；缺项追问、未受影响分支和同版本相同请求复用时不检索。没有个人资料就跳过检索模型调用。
- 三层记忆各有范围：Redis 保留近期角色原话，PostgreSQL 摘要压缩同会话老消息，长期偏好档案跨会话提供明确保存的默认值；本次 State 和最新纠正优先。
- SQL 保存用户可见的业务消息，Redis 保存各 Agent 实际调用窗口，包含角色输入、回复与工具消息，两者不是完全相同的一份聊天记录。
- 重新打开会话加载 SQL 历史供页面展示；再次发消息时，Redis 角色窗口命中就复用，过期或缺失则按身份、偏好版本和摘要边界从 SQL 回填近期已完成业务消息，并设置 7 天 TTL。原有 SQL 摘要、近期背景和偏好注入继续保留；没有持久化的工具调用轨迹不伪造恢复。
- 回填排除本轮刚落库但未回答的问题；用 NX 写入防止覆盖恢复期间的新窗口，空历史也缓存一次。删除长期偏好或新建行程后，旧边界之前的原话不能重新灌回。
- 摘要只推进实际处理完成的消息序号与偏移；调用失败不推进。长期偏好删除后切换角色消息范围并重建摘要范围，不能把旧原话重新压回去。
- 原始本次需求与有效需求分开保存。长期默认值改变只有在本次仍继承该类默认值时才重跑；只更新摘要不触发规划。完整链路见 [三层记忆与偏好规划](../../../../zhixing-travel/docs/learning/04-三层记忆与偏好规划.md)。
- 完整实现见 [私人资料上传与 RAG 检索](../../../../zhixing-travel/docs/learning/03-私人资料上传与RAG检索.md)。

## 知行：多级记忆是做什么的，要不要增加？

多级记忆不是统一的固定三层规范。按使用范围可以区分会话内短期记忆与跨会话长期记忆；工程上也可以进一步采用“近期消息窗口 + 会话摘要 + 用户长期偏好”。参考 [LangChain 记忆概念](https://docs.langchain.com/oss/python/concepts/memory) 和 [LangChain4j ChatMemory](https://docs.langchain4j.dev/tutorials/chat-memory/)，前者用于理解概念，不代表其 Python API 可以直接用于当前 Java 工程。

- **近期消息窗口：**保存最近对话，理解“刚才那个”“第二个方案”。限制消息数量不等于限制 Token，一条很长的消息或工具结果也可能占满上下文。
- **会话摘要：**在对话变长时，把窗口外仍有价值的信息压缩后与近期消息共同提供给模型。当前已实现按覆盖范围增量更新和分类摘要；摘要可能遗漏信息，出发日期、目的地等明确任务字段仍以结构化 State 为准。
- **长期偏好：**按用户保存跨会话可复用的信息，例如偏好高铁、不吃辣；当前已实现自然语言记住、忘记及页面管理，使用 PostgreSQL 档案保存三类偏好，不依赖向量检索来读取明确默认值。

当前知行已有角色窗口、增量摘要和长期偏好三层记忆，也有结构化需求、PostgreSQL 检查点和私人攻略 RAG。检查点用于恢复任务，资料库提供参考知识，三层记忆用于管理对话与偏好；职责不同，不能仅凭数据库保存时间长就将某份数据称为长期记忆。当前实现说明见 [三层记忆与偏好规划](../../../../zhixing-travel/docs/learning/04-三层记忆与偏好规划.md)。

例子：用户第一趟明确说“以后推荐都尽量不辣”，保存为可查看、修改的长期偏好后，下一次去另一座城市也可以沿用；上次旅行的具体日期则不应默认成为长期偏好。本轮说“这次想尝试辣菜”，当前明确要求优先，是否永久修改偏好还需区分。

记忆功能仍要分别检查来源、更新与删除、用户隔离和生成时的使用情况。代码能力、替身测试与真实模型效果应区分，不根据“有三层”直接宣称记忆质量或个性化效果已经提高。

## IM：定时执行为什么还要 Lua？

Lua 负责把“查到期任务 + 从调度集合移除”合成一次 Redis 原子操作，不负责等待到点、调用模型或发送 Kafka。当前入口是 [AgentActionScheduler.dispatch](../../../UserService/src/main/java/cn/qingliao/userservice/agent/AgentActionScheduler.java)，由 Spring 定时触发。

任务保存在 `agent-action:due` ZSET，member 为 `任务ID:版本`，score 为下一次应执行的时间戳。脚本读取 Redis TIME，查询 score 不大于当前时间的至多 100 个成员，逐个 ZREM，最后返回取到的列表。Java 收到列表后再投递 `agent-action-due-topic`。

如果查询与删除分成两个普通命令，调度器 A 查到任务后还没删除，调度器 B 也可能查到同一任务；两边若都按查询结果发送，就会重复分发。Lua 避免其他 Redis 命令插进这一小段取出过程。

这不等于全链路只执行一次：脚本删除后、Kafka 投递前可以崩溃；当前 dispatch 会按数据库待执行记录重新补入 ZSET，repair 也会补偿任务。甚至另一轮扫描重新加入仍为待执行的任务，也可能产生重复事件。最终执行见 [AgentActionDelivery.execute](../../../UserService/src/main/java/cn/qingliao/userservice/agent/AgentActionDelivery.java)：使用版本、状态及执行租约条件争取执行资格，已完成或旧版本事件退出；重试复用稳定消息编号，分别记录存储和推送 Topic 的投递结果。

三层职责：定时扫描决定何时检查，Lua 原子取出 Redis 到期项，数据库状态/幂等与补偿处理重复和失败。Lua 的原子性不覆盖 MySQL 或 Kafka。

## 知行：上下文设计是什么意思？

上下文是一次模型调用所能看到的信息，包含任务规则、本轮输入、相关历史、结构化需求、偏好、检索片段、工具描述及工具返回。上下文设计就是决定这一步给模型哪些信息、怎样组织、哪些需要压缩或排除，以及信息变化后怎样更新。

例如美食 Agent 生成杭州餐厅建议时，需要当前目的地、人数和有效口味，可能还需近期指代、公共背景与美食摘要，以及有权限的相关攻略。当前 [EffectivePreferences.plannerInput](../../../../zhixing-travel/src/main/java/com/wuxi/zhixingtravel/memory/EffectivePreferences.java) 会复制有效需求，加入公共与对应类别摘要、近期业务消息及偏好来源。它并不是已经将全部需求字段都严格裁剪成角色专属字段，不能过度描述隔离范围。

需要考虑的几个判断：

- **选择：**模型看不到任意数据库内容，需要后端读取、检索或执行工具后提供；只使用当前用户有权限的数据。
- **冲突：**本次明确“想尝试辣菜”优先于长期默认“不辣”，旧摘要不能复活被清除的条件；确定性合并由代码处理，模型再组织建议。
- **组织：**分开标记当前需求、历史摘要、资料和工具结果，资料正文不能当作系统指令。角色摘要可按类别提供，不必把所有原始内容都反复加入。
- **长度：**近期窗口、增量摘要、片段筛选和工具结果裁剪共同控制输入规模；消息条数与 Token 数不是一回事。
- **更新：**偏好、资料和本次需求发生变化时，重新判断哪些上下文与旧结果仍有效。

三层记忆、RAG、需求 State 和工具调用都能为上下文提供信息；上下文管理负责让这些信息在具体调用中正确配合。简历中的这项能力应能用输入构成、冲突处理与实际验证来说明，不仅是泛称“会设计提示词”。本次仅补充讲解，未修改功能实现或新增模型效果测试。

1. 不会。推送消费继续推进，客户端调用 HTTP 接口按冷热分区补拉（热区 Redis、冷区 MySQL，空缓存或异常回源），并与实时消息去重合并。
2. 都不是。帧边界与 TCP 分段、应用读取边界不同；HTTP 可以复用已有 TCP 连接。
3. 不会，连接共用节点已有线程组，各自创建 Channel/Pipeline。一台机器可以启动多个独立实例，需区分监听端口与节点 ID。
4. 都不保证。此前同步调用和 send 自身可能等待，join/get 也会等待未完成结果；非 Async 回调不绑定 business 组，耗时回调需明确执行器。
5. 通知原发送端 A 的连接，当前后端不自动重发。Executor 是任务执行接口，可引用已有线程池，由实现决定线程使用方式，不等于新建线程。
6. 不会。Future 反映生产者投递结果，消费者写库是后续独立事务，失败处理与重试由消费侧负责。
7. 无条件删除本身线程安全，但不能识别旧回调，需 remove(userId, oldChannel) 原子比较删除。同步只协调同 JVM 的相关调用，不覆盖其他节点。
8. 当前不能自动延长。有效 Refresh 可以调用刷新接口取得新凭证，无需重新输入密码，但客户端自动刷新和 WebSocket 重连流程尚未完成。
9. 不共享。每个 Topic-partition 有自己的日志与 offset；并发双路发布可能产生不同相对顺序，仍需业务级序号与处理协议协调。
10. 生产者幂等只保护协议重试造成的重复追加；数据库事务提交和消费位移提交分开，前者成功、后者未提交时崩溃，恢复后仍会重读，因此消费者副作用还需幂等。
11. 调用方请求再次进入普通消息入口时会新生成；Kafka 内部重传和消费者重读保留原消息 ID。当前错误回调只返回错误，不会自己触发客户端重新发送。
12. 能，近七天够一页且页尾排序明确时直接返回；不足、异常或同毫秒截断时查 MySQL。不能直接跳到七天前，否则会漏掉热区内未缓存的消息。授权 RPC 仍执行，缓存够一页也不是同步完整性的证明。
13. 前者主要是事务原子性，后者是事务隔离性。事务也不替代业务唯一约束和状态条件，不能据此宣称不会重复入账。
14. 不能。移除与 Kafka 投递分离，数据库补扫会重新加入未完成任务，也可能产生重复事件；还需要状态、版本、执行租约、稳定消息编号和补偿配合。
15. 代码先将本次要求解析为有效口味，保留来源；本次覆盖不自动永久修改长期档案，摘要和历史消息不能让模型把旧默认值恢复成当前条件。
