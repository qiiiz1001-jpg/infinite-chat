## 本篇目标

理解两个问题：这个 IM 项目如何划分服务？用户提交邮箱和密码后，登录凭证如何生成，又如何在后续请求中被验证？

按学过黑马点评的基础讲解，常规分层、CRUD 和参数注解只点到为止。本篇作为已有代码导读；从第 02 篇起，按原始文档的实现顺序同步补工程，进度见[原文与代码对照](进度-原文与代码对照.md)。

## 1. 先确定项目边界

文档按微服务架构设计，使用 Maven 多模块组织代码。当前是六个应用模块，加一个 Common 公共库：

| 模块 | 负责什么 | 当前工程情况 |
|---|---|---|
| UserService | 用户、联系人、群组、会话与权限 | 已补齐原文章节实现 |
| AiService | AI 对话、知识检索、工具与会话总结 | 基础实现及 IM 集成已补齐 |

| GateWay、RedPacketService | HTTP 网关、红包与测试账务 | 已补齐原文章节实现 |

模块清单见[父 pom.xml](../../pom.xml)。多模块是构建组织方式；微服务还要看独立运行、部署和通信边界。本次 Controller 到 ServiceImpl 属于用户服务内部调用，文档里的 RealTimeService 通过 Feign 调用 AiService 才是跨服务调用。

当前代码按原文章节补齐，最新落地与纠偏情况见[进度记录](进度-原文与代码对照.md)。登录流程已通过 H2 和模拟 Redis 的真实 HTTP 测试，尚未连接实际 MySQL/Redis 联调。

## 2. 场景：一个已注册用户进行密码登录

用户提交邮箱和密码，希望得到后续访问接口使用的凭证。

```text
POST /api/user/login/password
    ↓
UserController.loginPassword
    ↓
UserServiceImpl.loginPassword
    ↓ 按邮箱查用户、比较密码摘要
createJwt
    ↓ 生成 Access Token 和 Refresh Token，分别保存到 Redis
返回用户资料和两类 Token
```

当前用户服务端口是 8104。这条链路访问 MySQL 和 Redis，不调用其他微服务，也不经过 AI 模块。

## 3. 跟着请求打开代码

### 第一步：从接口进入登录业务

打开 [UserController.java](../../UserService/src/main/java/cn/qingliao/userservice/controller/UserController.java)，搜索 `loginPassword`。

确认接口地址后，直接进入 [UserServiceImpl.java](../../UserService/src/main/java/cn/qingliao/userservice/service/impl/UserServiceImpl.java) 的同名方法。登录路径在 [AuthenticationConfig.java](../../Common/src/main/java/cn/qingliao/common/security/AuthenticationConfig.java) 中放行，不要求先持有登录凭证。

业务顺序只有四步：

1. `getUser(email)` 按邮箱查询用户，不存在就抛业务异常。
2. 按注册时相同的规则计算密码摘要，与数据库值比较。
3. 将公开资料复制进登录响应对象。
4. 调用 `createJwt` 签发并保存凭证。

这里不必继续展开 DTO、Mapper 和响应包装。注意现有实现使用固定盐 MD5，已补用户 state 检查以拒绝禁用账号；固定盐摘要仍需改进；不能将现有密码摘要视为完善的生产密码方案。

### 第二步：看登录成功后保存了什么

仍在 [UserServiceImpl.java](../../UserService/src/main/java/cn/qingliao/userservice/service/impl/UserServiceImpl.java)，搜索 `createJwt`，再按需看 [JwtUtil.java](../../Common/src/main/java/cn/qingliao/common/utils/JwtUtil.java) 的 `generate`。

`generate` 将用户 ID、签发和过期时间写入 JWT，并签名；`createJwt` 负责把两类 JWT 放进响应，同时保存到 Redis。

| 凭证 | 当前有效期 | Redis key | 用途 |
|---|---|---|---|
| Access Token | 30 分钟 | `access:token:{userId}` | 调用受保护接口 |
| Refresh Token | 7 天 | `refresh:token:{userId}` | 申请新凭证 |

具体期限见 [CommonConstant.java](../../Common/src/main/java/cn/qingliao/common/constant/CommonConstant.java)。第 03 篇已按原文将 JWT 与凭证常量从 UserService 迁到 Common，供实时服务复用。

和黑马点评常见的“随机 Token 对应 Redis 登录信息”相比，这里多了 JWT 自身的验签与过期校验，但仍保留 Redis 中的当前有效凭证。

### 第三步：确认后续请求怎么认出这个用户

打开 [AuthenticationConfig.java](../../Common/src/main/java/cn/qingliao/common/security/AuthenticationConfig.java)，搜索 `preHandle`，先看 Access Token 分支：

```text
读取请求头 Access-Token
    ↓
JwtUtil.parse：验签并检查有效期
    ↓
从载荷取出 userId
    ↓
读取 access:token:{userId}
    ↓
请求中的 Token 与 Redis 当前值相同，才放行
```

因此，JWT 能解析并不代表这次请求一定有效。Redis 中的凭证已删除或被其他值替换，同样会被拒绝。Refresh Token 分支及刷新接口后续按相关原文改动一起分析。

## 4. 这条链路值得深入的三个点

**为什么 JWT 之外还保存 Redis？** 当前设计需要控制有效登录状态，支撑退出和凭证替换。收益是服务端可主动使凭证失效，代价是受保护请求仍依赖 Redis，不能直接称为完全无状态认证。

**Redis key 如何影响多端登录？** 当前 key 只有 userId，没有设备维度。后续登录会覆盖现有值，设计倾向于单会话限制。支持多端时，还要一起考虑设备标识、刷新范围和退出范围。

**两类 Token 是否一起更新成功？** `createJwt` 中的两次 Redis SET 独立执行。第一次成功、第二次失败，可能留下不一致的凭证状态；刷新时的并发覆盖也需要进一步分析。当前没有在这里实现整对原子更新。

## 本篇自查

- 能否从登录入口定位到查用户、签发 Token、后续鉴权这几个关键方法？
- 为什么这里既用 JWT，也用 Redis？相比黑马点评的登录方案，区别在哪里？
- 如果支持手机和电脑同时登录，或者 Redis 写入中途失败，现有代码需要怎样调整？

## 自查解答

**1. 主流程对应这些方法。** UserController.loginPassword 接收请求，UserServiceImpl.loginPassword 调用 getUser 查询用户并比较密码摘要，再调用 createJwt；JwtUtil.generate 生成 JWT，createJwt 写入 Redis；后续受保护请求进入 AuthenticationConfig 中的 preHandle 核对签名、有效期和 Redis 当前值。

**2. JWT 与 Redis 承担不同职责。** JWT 自身可以校验签名和到期时间，Redis 记录当前有效凭证，便于退出和替换。相比随机 Token 加 Redis 登录信息，凭证结构不同，但当前方案仍依赖服务端状态，并非完全无状态认证。

**3. 多端与失败窗口需要分别处理。** 多端可按 userId 加设备或会话 ID 管理凭证，同时调整刷新与退出范围。两次 Redis SET 可考虑用 Lua 或事务保证同一存储实例内的整对更新；并发刷新还需校验旧凭证和处理覆盖，不能只合并两次写入就认为全部问题已解决。
