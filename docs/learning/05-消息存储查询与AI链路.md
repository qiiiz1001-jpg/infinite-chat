## 场景一：A 给 B 发消息，B 断线后补拉

```text
握手认证 → 绑定 Channel → 校验会话权限 → 分配消息 ID/时间
                            ↓
                  Kafka store / push 两个 Topic
                    ↓                  ↓
        OfflineDataService           每个实时节点消费
          MySQL 幂等 INSERT          找本机在线 Channel
             ↓ 提交后                   ↓
        Redis 最近消息索引             在线投递
             ↓
         历史查询 / 离线补拉
```

1. 打开 [WebSocketHandler](../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/websocket/WebSocketHandler.java)，看 `channelRead0`。发送者取自已认证连接，忽略客户端冒充的 senderId；消息 ID、时间由服务器生成。红包消息必须走红包服务，客户端不能直接发 type=3 伪造。
2. 追 [SessionAccessController](../../UserService/src/main/java/cn/qingliao/userservice/controller/SessionAccessController.java) 的 `canSend`：检查用户、会话状态、双方成员关系，单聊按原文的方向规则检查好友状态：A 拉黑 B 时，A 仍可发给 B，B 不能发给 A；删除关系与失效成员仍被拒绝。网关认证成功不能替代业务授权。
3. 看 [ConsumerMessageService](../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/consumer/ConsumerMessageService.java)：每个实时节点有独立推送消费组，先广播到节点，再过滤本机连接。若所有节点用同一组，分区可能把消息交给没有目标连接的节点。
4. 看 [ConsumerOfflineService](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/consumer/ConsumerOfflineService.java) → [MessageServiceImpl](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/service/impl/MessageServiceImpl.java) 的 `saveMessageToMySQL` → [MessageMapper](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/mapper/MessageMapper.java)。同一个服务端 messageId 重复消费不会覆盖原文，缓存更新放在事务提交后。
5. 看 `getHistoryMessages`：确认 CurrentUser 属于会话；以 `(createdTime,messageId)` 游标翻页。按原文先查近七天 Redis，够一页且页尾排序明确时直接返回，不执行消息表查询；不足、异常或页尾同毫秒截断时，按原始游标回源 MySQL。七天前直接查库。
6. 看 `getOfflineMessages` 和 [ConnectionStateService](../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/websocket/ConnectionStateService.java)：断线记录时间，登录响应带离线时间，客户端据此补拉。当前补拉没有分页，大量离线消息需要继续优化。

### 历史查询：Redis 必须实际挡住消息表查询

原文范围：9.6.6，`getHistoryMessages` → `getMessagesFromRedisBefore` / `getMessagesFromMySQLBefore`。2026-10-31 已修正此前“先查库再合并缓存”的偏离。

```text
校验会话成员身份、分页参数
  → beforeTime 在七天前？
      ├─ 是：MySQL 按 (createdTime, messageId) 查一页
      └─ 否：Redis session:{sessionId} ZSET，按 score 倒序取 limit+1 条
               → 按消息 ID 去重、过滤游标、按时间和 ID 排序
               ├─ 足够一页且未截断同毫秒并列组：直接返回，消息表 SELECT=0
               └─ 不足 / 异常 / 格式错误 / 并列组截断：MySQL 按原始游标查一页
```

例如本页要 20 条，Redis 可返回符合条件的 20 条，就走缓存；只有 8 条时，数据库从本次请求的 beforeTime/beforeMessageId 查询完整 20 条，不能直接跳到七天前。这样能补到七天内尚未缓存的记录，也能自然跨冷热边界。回源返回数据库这一页，不再把两套结果无条件合并。会话授权仍调用用户服务；“零查库”仅指本次不查消息表，不代表所有服务都不访问数据库。

ZSET 同 score 按 JSON 字节顺序排列，并不按 messageId；多取一条发现页尾仍在并列组时，回源保持复合游标顺序。小并列组全部取回则可在内存排序后直接返回。

保留原文的异步缓存边界：缓存凑够一页不证明近期记录绝无同步缺口，不能宣称强一致。当前没有增加页缓存或完整覆盖区间协议。回源与命中是不同分支，不再用每次查库来掩盖这个限制。

### 离线补拉：恢复原文 9.6.5 的冷热拆分

`getOfflineMessages` 用当前认证用户查所属会话，逐会话调用 `getMessagesAfter`：

```text
offlineTime 在最近七天 → Redis 取该时间之后的消息
offlineTime 早于七天   → Redis 取热区 + MySQL 取 (offlineTime, 七天边界) 冷区
                         → 按 ID 去重，按时间、ID 正序返回
Redis 为空/异常/坏数据 → MySQL 按原始 offlineTime 回源
```

冷热分界毫秒放进 Redis 范围，避免原文冷区、热区都用严格比较而漏掉边界。正常热区命中不查消息表；跨区只查冷区。非空缓存仍可能有异步同步缺口，这是原文架构的边界，不把它说成强一致。接口仍没有离线分页。

登录按原文 9.6.4 使用 Redis `getAndDelete` 原子取走离线时间，第二次登录不会重复拿到旧记录。若首次登录响应丢失，没有客户端确认重发协议；这是课程方案现有的限制。

### 答疑：幂等和“幂等锁”是同一个东西吗？

**幂等是业务效果：同一次操作重复处理，仍保持一次处理的业务结果。锁是并发控制：同一时间只允许一个执行者进入。**只加锁、不检查是否已完成，前一个释放后，后一个仍可重复执行业务。

```text
锁只控制排队：请求 1 加锁 -> 执行业务 -> 释放 -> 请求 2 加锁 -> 又执行
幂等还要识别：请求 1 处理 M100 -> 留下成功结果 -> 重试 M100 关联已有结果
```

“幂等锁”通常是用业务操作 ID 构造 key，借 Redis SET NX 等原子占位限制同一操作并发执行的叫法，不是 Java 固定语法。完整幂等还需考虑成功记录、失败重试和占位过期；占位失效后仍应能判断该操作是否已完成。

你正在看的消息存储没有显式加 Redis 幂等锁，而是依靠 `message_id` 主键与 Mapper 中 `ON DUPLICATE KEY UPDATE message_id=message_id`：首次插入，重复 ID 不新增、不覆盖数据库正文。这是数据库幂等，不等于锁住整个消费方法。它只识别相同服务端 messageId，不能识别生成了新 ID 的客户端重试。

## Canal 与一致性边界

目标：看懂数据库提交后，谁把消息变更传到 Java，Java 在哪个线程更新 Redis，以及失败后重新读取什么。Canal 默认关闭；原有 afterCommit 缓存同步仍工作。

```text
存储消费者 → MySQL 提交
                  ├→ afterCommit → Redis（原有同步路径）
                  └→ binlog → Canal Server（独立服务）
                                   ↑ 拉取变更 / 发送确认
                     OfflineDataService JVM
                       CanalClient 的 canal-consumer 线程
                                   ↓
                         解析 message INSERT → Redis
```

**第一步：配置开关与连接。** [application.yml](../../OfflineDataService/src/main/resources/application.yml) 的 `canal.enabled` 默认 false；[CanalConfig](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/config/CanalConfig.java) 和 [CanalClient](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/client/CanalClient.java) 都要求它为 true 才注册。启用后，CanalConfig 的 `@Bean canalConnector()` 创建官方连接器：

```java
CanalConnector connector = CanalConnectors.newSingleConnector(
        new InetSocketAddress(canalHost, canalPort),
        destination, username, password);
connector.connect();
connector.subscribe(filter);
connector.rollback();
return connector;
```

连接的是 Canal Server 的 11111 端口，不是 MySQL。destination=example 指 Canal 服务端配置的逻辑实例；filter 限定数据库/表，当前订阅 Qingliao.message。初始 rollback 用于重置未确认的读取进度，不会回滚数据库。连接器作为 Bean 注入 CanalClient；MySQL 日志采集由外部 Canal Server 完成，Java 类不直接读取 MySQL 日志文件。

**第二步：启动后台线程。** CanalClient 实现 CommandLineRunner，Spring Boot 启动阶段会调用 run。run 创建名为 canal-consumer 的守护线程，以 `this::process` 指定线程任务，然后 start；run 自身即可返回。之后消费循环、解析与 Redis 操作在这个线程执行，不依赖 HTTP 请求触发。守护线程不会单独阻止 JVM 退出。只有启用该组件才有这条线程。

**第三步：process 循环拉取。** 连接失效时 reconnectCanal，空闲超过30秒走代码中的心跳分支；普通循环调用 `getWithoutAck(1000)`，取得包含 batchId 和 entries 的批次。这里 Message 是 Canal 的批次包装，不是单条聊天消息；1000 是拉取批量参数，也不表示每次恰好有1000条聊天记录。没有数据就休眠5秒，有数据才继续处理。

```text
process 循环
  → 检查连接，需要时重连
  → 检查心跳分支
  → getWithoutAck(1000)
      ├─ 无数据：休眠5秒 → 下一轮
      └─ 有数据：handleMessage(entries)
                    ├─ 正常结束：ack(batchId) → 下一轮
                    └─ 抛异常：rollback(batchId)
                                  → 外层等待后重试
```

getWithoutAck 表示先取数据、不自动确认；不是拉到就算业务成功。ack 确认的是这批变更已按当前客户端逻辑处理，不是聊天接收方已读。

**第四步：handleMessage 解析与筛选。** 跳过事务开始/结束标记，将 entry.storeValue 解析为 RowChange；只保留 message 表的 INSERT。一个变更事件可能包含多行 RowData，每行的 afterColumns 是插入后的字段和值。当前 UPDATE、DELETE 不执行缓存变更，跳过不算异常。

```text
Canal Message（一批）
  └─ entries（多个事件）
       └─ RowChange（一项变更）
            └─ rowDatas（涉及多行）
                 └─ afterColumns：message_id、session_id、content……
```

**第五步：转换消息并写 Redis。** handleInsert 将字段列表变成 Map，例如 `message_id → "1001"`；buildMessageFromMap 转为 MessageResponse，组装消息 ID、会话、发送者、正文等；buildMessageFromMap 将 SQL 日期转为实体时间，并复用 [MessageResponses](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/utils/MessageResponses.java) 组装响应；storeMessageToRedis 使用毫秒时间戳与统一的 Hutool JSON 序列化，然后：

```text
key    = session:会话ID，例如 session:88
类型   = ZSET
member = 完整消息对象的 JSON
score  = 消息创建时间的毫秒值

写入 → 删除七天前的成员 → 将整个 key 的 TTL 设置为八天
```

score 用来按消息时间排序和清理旧成员；TTL 用来让整个会话缓存过期，二者用途不同。

**第六步：成功确认、失败重读。** handleMessage 正常返回后才 ack(batchId)。若某条 Redis 操作失败，异常向外传播，safeRollback(batchId) 回退该批次读取进度，再由外层 catch 等待重试。等待间隔递增并限制在60秒；达到代码里的重试计数阈值后等待60秒，再继续尝试，不是永久丢弃这一批。

```text
批次包含 M1、M2、M3
  M1 写 Redis 成功
  M2 写 Redis 抛异常
     → 整批未确认，回退 Canal 读取位置
     → 重读时 M1 也可能再执行，M3 尚未执行

rollback 不撤销 M1 已执行的 Redis 写入，也不撤销 MySQL 提交。
```

ZSET 只对完全相同的 member 去重。当前 afterCommit 与 Canal 已共用响应转换器和 JSON 库，文本及红包的相同数据库记录会生成相同 member，相关契约测试已通过；已有旧格式成员不会自动清理，不能泛化成“只要 messageId 相同就一定自动去重”。ack/rollback 的批次语义见 [Canal 官方 ClientAPI](https://github.com/alibaba/canal/wiki/ClientAPI)。

**其余辅助方法。** reconnectCanal 断开、重连并重新订阅；sendHeartbeat 中调用 ack(-1)，代码意图是保活，不是确认某条聊天消息，实际保活效果尚未经真实环境验证。stop 带 @PreDestroy，Spring 销毁组件时中断后台线程并断开连接。初始 connector.connect 在 Bean 创建阶段执行，连接失败可能直接导致启动失败，不会自动进入尚未启动的 process 重试循环。

Canal 这段没有再次写 MySQL，也没有调用实时服务给 B 推送；职责是消费数据库变更并更新消息缓存。它不能替代 Kafka 落库，也不保证 MySQL 与 Redis 强一致。当前真实 Canal 环境尚未联调，此处是按源码梳理运行逻辑。

普通消息双 Topic 发送并非原子事务；一边成功一边失败时存在补偿窗口。当前数据库去重以服务器 messageId 为准，客户端重试同一个 clientMessageId 仍可能得到新 ID。接口成功、Kafka 确认、持久化成功也没有统一为客户端端到端 ACK 协议，这些是面试可讨论的改进点。

## 本篇自查

1. 为什么实时推送节点不能共用一个消费组，而离线持久化要共用一组？
2. 为什么分页不能只传 beforeTime？数据库幂等是否解决客户端重复发送？
3. AI 调用怎样接入现有聊天链？还存在哪些失败窗口？
4. Canal 拉到批次是否立即确认？处理一半失败时 rollback 会撤销哪些业务数据？
5. Redis 命中是否还查消息表？不够一页为什么不直接查七天前？

## 自查解答

1. 推送要让持有目标 Channel 的节点收到消息，所以每节点独立组；落库是相同业务的一次处理，多实例共享组分摊分区，再用数据库幂等应对重投。
2. 同毫秒可能有多条消息，只按时间排除整个时间点会漏数据；加 ID 决定同时间顺序。数据库仅对同一服务端 ID 去重，客户端重试会分配新 ID，仍需请求 ID 去重与 ACK 机制。
3. AI 请求进入固定组，回答生成后复用 store/push；原消息已存而 AI 未生成、模型调用后缓存前崩溃、双 Topic 部分成功都可能发生。缓存与重试缩小窗口，不等于全局严格一次。
4. 不会，handleMessage 正常返回后才 ack。rollback 回退 Canal 批次读取进度，不撤销已提交的 MySQL 记录或已执行的 Redis 写入，重读时可能再次处理批次中已经写入缓存的消息。

5. 够一页且页尾无排序歧义时不查消息表；不足、失败或同毫秒截断时回源。回源保留原始游标，否则会跳过七天内缺失的缓存记录；授权 RPC 仍执行。
