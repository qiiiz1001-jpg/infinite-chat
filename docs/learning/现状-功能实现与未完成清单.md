## 2. 明确还未完成的内容

| 范围 | 已有机制 | 仍缺什么 |
|---|---|---|
| 普通消息重试 | 数据库按服务端 messageId 去重 | 按 clientMessageId 的请求级幂等；客户端重发仍可能产生新消息 |
| 普通消息可靠性 | 双 Topic 异步发送、异常提示、独立消费 | 双路可靠发布与补偿闭环、端到端持久化/送达 ACK；不能称为全局严格一次 |
| 通知可靠性 | 群通知在提交后发送，独立通知表 | 通用 outbox 与持续重放；联系人通知还存在事务内发送窗口 |
| 离线补拉 | 按离线时间查询所属会话 | 分页、可靠客户端已确认游标，以及进程崩溃等场景的完整补齐机制 |
| Token 更新 | 两类 Token 的基本刷新流程 | 旧 Refresh 比较与整对凭证更新的原子操作、并发刷新协议；详见 A03 |
| 多端与踢连接 | 用户级当前凭证、本节点连接替换、入站帧检查旧凭证 | 设备级独立会话、跨节点主动即时踢连接；当前退出不保证所有方向立刻停止 |
| 密码与上传 | 现有摘要比对、对象路径与签名 | 固定盐 MD5 升级；上传内容/大小等完整校验、审核与对象生命周期 |
| 群管理扩展 | 群主/管理员/成员权限规则 | 群主转让、解散、管理员任命等接口；枚举里有角色不等于有管理接口 |
| 红包完整性 | 本地事务、唯一约束、Redis 记录与补偿 | 发送请求长期幂等、支付接入、完整对账审计、Redis 灾难恢复等；当前只用测试余额 |
| Agent 后续 | 一次性任务、确认、补偿与固定消息编号 | 周期提醒、多渠道通知、新功能真实中间件/模型联调、端到端送达 ACK；队列至少一次投递仍可能重复推送 |
| 客户端 | 简洁 Web 演示页、浏览器子协议鉴权、历史与测试红包展示 | 完整产品前端、自动刷新重试与带新凭证重连流程 |
| 性能与运维 | 部署模板、部分指标代码 | 实际压测和容量数据、外部环境故障演练与运行验证；不能编造 QPS 或连接数 |

表中的“仍缺什么”是明确的边界清单，不表示当前要把所有生产功能一次做完。面试时可以把它们作为设计取舍与下一步改进，但不能描述为既有实现。

## 4. 怎么理解学习文档中的话

- “当前方法调用了……”应能从源码找到，作为已有机制解释。
- “尚未实现”“仍有失败窗口”是当前限制，不是已经修好的能力。
- “可以用 Lua / outbox / 设备会话……”是后续设计，除非另有实现与验证记录，不能作为现有功能。
- “测试通过”只证明相应场景的断言通过，不能扩大为所有真实环境和故障组合都通过。

2. 没有。当前是读取、校验旧 Refresh，再分别执行两次 SET；Lua 是明确标注的改进思路。
3. 不是。模板、局部测试和真实环境联调是不同证据，需要分别记录，不能互相替代。
