对应原文“初始化数据库”。看懂一条聊天消息如何关联用户、会话和成员，并把本阶段 SQL 落入工程。好友、红包表先认识职责，具体实现留到原文对应章节。

## 1. 先看表之间的业务关系

| 主线 | 表 | 负责什么 |
|---|---|---|
| 用户 | user | 账号、密码摘要、昵称与状态 |
| 聊天 | session、user_session、message | 会话本身、成员关系、聊天内容 |
| 好友 | friend、apply_friend | 当前关系与好友申请状态 |
| 红包 | red_packet、red_packet_receive | 红包本身与领取记录 |
| 余额 | user_balance、balance_log | 当前余额与金额变动流水 |

这一节重点看聊天三张表。原文虽然提前创建了好友和红包相关表，但不代表相应业务已经完成。

## 2. 场景：A 给 B 发送一条消息

假设 A、B 已经属于会话 2001，数据关系应当是：

```text
session：2001，type=0（单聊）
    ↓
user_session：(A, 2001)、(B, 2001)
    ↓
message：发送者 A，session_id=2001，content="你好"
```

这是模型示例，当前没有执行插入，也还没有实现网络推送。接下来依次在 [01-init.sql](../../database/01-init.sql) 搜索下列三个建表位置。

### 第一步：session 表表达“这是哪段会话”

搜索 `-- 会话表`，定位 session 的建表语句。

`session_id` 标识会话，`type` 区分单聊与群聊，`name` 可以保存群名称等展示信息。单聊和群聊共享这个模型，后续消息都通过 session_id 归到会话下。

### 第二步：user_session 表表达“哪些人属于会话”

搜索 `user_session`，重点看复合主键 `(user_id, session_id)` 和 `idx_session_id`。

- 按 user_id 查：得到用户加入的会话。
- 按 session_id 查：得到会话成员，后续推送要用到。
- role、status：表达成员在会话中的角色和关系状态。

复合主键约束同一用户、同一会话只能有一条关系，并支持以 user_id 为前缀的查询；反向按 session_id 查询，因此另建索引。

成员表也为后续权限检查提供依据：客户端传了 session_id，不代表发送者有权向这个会话发消息。当前只是建立数据模型，校验逻辑后面补。

### 第三步：message 表表达“会话里发生了什么”

搜索 `message` 的建表语句，先关注 `message_id`、`sender_id`、`session_id`、`type`、`content`、`created_time`。

消息没有为每个接收者分别保存一份内容。它归属一个会话，接收者由成员关系确定，这样同一套结构可以承接单聊与群聊。

`idx_session_time(session_id, created_time)` 面向“查询某会话的一段历史消息”。后续做分页和补拉时，还要处理同一时间的多条消息、游标和重复边界，不能把时间戳当成唯一标识。

## 3. 两个实现细节先记住

**用户 ID 由谁生成？** 表中 user_id 没有 AUTO_INCREMENT。打开 [UserServiceImpl.java](../../UserService/src/main/java/cn/qingliao/userservice/service/impl/UserServiceImpl.java)，搜索 `register`：当前调用 Snowflake 生成 ID，再插入 user。原文注释写“自增”，与这段代码不符，本次只修正了 SQL 注释。

**余额和流水为什么分开？** user_balance 保存当前值，balance_log 保存业务变动；金额都以“分”存入 BIGINT。后续红包实现要保证扣款、入账、流水和消息之间的业务一致性，本阶段只是预建表。

## 本篇自查

1. 为什么消息关联 session_id，而不是只保存 sender_id 和 receiver_id？
2. user_session 已经有复合主键，为什么仍要给 session_id 单独建索引？
3. 用户 ID 是数据库自增的吗？表建好了，是否就说明聊天和红包功能已经完成？

## 自查解答

**1. 会话是单聊与群聊共同的业务容器。** 消息归属会话，接收者通过成员关系确定。群聊不必为每个接收者重复保存相同正文；后续仍需在发送和查询时校验成员权限。

**2. 两个索引服务不同查询方向。** `(user_id, session_id)` 的前缀是 user_id，适合按用户查会话；只按 session_id 查成员不能同样有效地利用此前缀，因此另建索引。同时，复合主键保证关系不重复。

**3. 当前由应用生成。** 注册逻辑调用 Snowflake，SQL 没有 AUTO_INCREMENT。建表只完成持久化模型，长连接、鉴权、消息分发、消费存储及红包一致性仍需后续实现与验证。
