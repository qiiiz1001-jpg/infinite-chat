## 本篇目标

覆盖原文第 13 章。围绕一个问题阅读：Redis 已经抢到了，为什么数据库余额仍要异步处理，怎样避免重复加钱？

## 场景一：发送红包

假设 A=1001，在群 8001 发送总额 10.00 元、3 份普通红包，红包 ID=9001，A 原余额为 100.00 元。以下数字与时间为教学示例，不代表真实运行数据；本项目使用测试余额，本篇只核对现有实现。

### 1. 先看完整流程：事务内准备，提交后开放领取

```text
POST /api/chat/redPacket/send
    -> RedPacketController.sendRedPacket
    -> 短时防重复提交、操作者身份检查
    -> RedPacketServiceImpl.sendRedPacket，进入数据库事务
         -> validateSendRequest：参数、金额精度与份数
         -> validateSendPermission：发送资格，群聊取得成员快照
         -> 元精确转分：10.00 -> 1000
         -> deductSenderBalance：余额够才原子扣减
         -> createRedPacket：写红包主记录
         -> recordBalanceLog：写负金额流水
         -> initRedPacketCache：Redis grant.ready=0、成员快照、金额 List
         -> sendRedPacketMessage -> sendMessageKafka
              保存待发消息、published=0，注册 afterCommit
    |
    +-- 回滚 -> 数据库扣款/红包/流水一起回滚
    |           afterCompletion 尝试删除临时 Redis Key
    |
    +-- 提交 -> afterCommit -> ready=1 -> publishPending
                   -> store-topic：持久化聊天红包消息
                   -> message-topic：推送聊天红包卡片
                   -> redpacket-creation-topic：登记红包过期任务
                   -> 都成功后 published=1
```

上图是按当前方法调用顺序整理的源码流程；预分配发生在 initRedPacketCache 中，位于扣款、写红包和流水之后。Redis 与 Kafka 不参加这个 MySQL 本地事务，后续依靠门禁、回调、稳定 ID 和补偿缩小失败窗口。

### 2. 从 Controller 到权限校验

先打开 [RedPacketController.java](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/controller/RedPacketController.java) 的 sendRedPacket，再进入 [RedPacketServiceImpl.java](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/service/impl/RedPacketServiceImpl.java) 同名方法。

Controller 上的 RequireActor 通过公共身份检查，约束请求 senderId 与登录用户一致。PreventDuplicateSubmit(expireSeconds=3) 由 [PreventDuplicateSubmitAspect](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/aspect/PreventDuplicateSubmitAspect.java) 使用 Redis setIfAbsent 挡短时间重复提交；它没有提供长期请求 ID 幂等，不能承诺同一次发送在任意时间重试都只扣一次。

Service 的 validateSendRequest 检查金额、份数和会话类型；[RedPacketValidationServiceImpl.validateSendPermission](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/service/impl/RedPacketValidationServiceImpl.java) 经 Feign 检查用户及会话资格：单聊校验双方、关系与会话且只支持普通红包；群聊确认发送者是成员，取得成员 ID 列表，并要求红包份数不超过该列表人数。

成员快照就是本次查回的成员 ID 列表，之后写入 Redis allow 集合供领取脚本判断，不是 Redis 自动持续跟随群成员变化。

### 3. 金额先转成整数分，之后再计算和存储

```java
Long totalAmount = body.getTotalAmount()
        .multiply(BigDecimal.valueOf(100))
        .longValueExact();
```

```text
HTTP 入参：BigDecimal 10.00 元
    -> 服务端转换：1000 分（Long）
    -> MySQL 余额、红包金额、流水：都用分
    -> Redis 金额池、Lua：都用分
    -> 返回展示金额时再按接口约定转为元
```

longValueExact 要求换算后可以精确成为整数，拒绝带零头分的数值或越界值。当前校验错误提示写“最多两位小数”，实际判定看能否精确换算为分；例如 1.230 可精确成为 123 分，1.231 则不能。避免把 double 带入金额运算。

份数必须为正，群红包还要求不超过发送时的群成员数；已移除此前额外加入、原文没有规定的 500 份固定上限。每份为 1 至 20000 分，总额必须能按上下限分完；算法层会严格核对金额与份数边界，不能只把平均值四舍五入后小于等于 200 元当成最终保证。

### 4. MySQL 事务里同步扣余额、记红包和流水

deductSenderBalance 的条件更新可理解为：

```sql
UPDATE user_balance
SET balance = balance - 1000
WHERE user_id = 1001
  AND balance >= 1000;
```

上面 1001 是示例发送者 ID；实际 SQL 由 MyBatis-Plus 构造。不先查余额再无条件写回新值，而是让数据库原子判断足额并扣减，更新不到记录就抛异常。

```text
同一数据库事务
    +-- user_balance：10000 -> 9000 分
    +-- red_packet：ID=9001，总额=1000 分，份数=3，状态=未领完
    +-- balance_log：变动=-1000 分，关联红包 9001

后续步骤失败抛异常 -> 这些数据库修改一起回滚
```

这里只扣发送者；接收者的入账是领取后的事件处理，下一场景再追。

### 5. 预分配金额：领取时从金额池取一份

进入当前实际调用的五参数 initRedPacketCache(packetId, request, amount, count, memberIds)，它调用 [RedPacketAlgorithm](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/util/RedPacketAlgorithm.java)：

```text
普通红包 allocateNormalRedPacket(1000, 3)
    base=333，remainder=1
    -> [334, 333, 333] 分
    -> 总和 1000 分，份额最大差 1 分

拼手气 allocateRandomRedPacket
    -> 每轮根据剩余金额、剩余份数计算可行上下界
    -> 随机取一份，扣减剩余金额
    -> 最后一份使用剩余金额，再打乱顺序
    -> 总和保持不变，每份不越界
```

随机算法循环次数有限，不靠不断重抽碰运气；它为后续份额留足最小金额，也限制后续仍能在最大金额内分完。第一遍先掌握守恒与上下界，不必逐行背公式。

类中还有一个只接收红包 ID、类型、总额、份数的旧重载；当前 sendRedPacket 调用的是五参数版本，带 ready 门禁、成员快照与回滚清理。

### 6. Redis 三种主要数据分别管什么

Key 由 [RedisKeyConstant.java](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/constant/RedisKeyConstant.java) 构造：

```text
红包 9001 的 Redis 数据
|
+-- redpacket:9001:pool（List）
|     ["334", "333", "333"]：每个元素是一份金额，单位分
|
+-- redpacket:9001:allow（Set，群聊）
|     发红包时取得的群成员 ID：领取资格快照
|
+-- redpacket:9001:grant（Hash）
      ready=0              数据库尚未提交，领取脚本不放行
      sessionType=1        群聊
      senderId=A           发送者
      expiresAt=...        红包业务到期时间
      message=...          准备好的红包聊天消息 JSON
      published=0          消息投递流程尚未全部完成
```

grant 的 message/published 由后续 sendMessageKafka 补写。三个 Key 的当前初始化 TTL 为 25 小时，红包业务期限是 24 小时；领取脚本还检查 expiresAt，不能把缓存仍存在理解成仍可领。

grant 是红包领取的服务端控制信息，名称不是 Java 授权框架。领取入口 [receive-redpacket.lua](../../RedPacketService/src/main/resources/lua/receive-redpacket.lua) 会检查 ready，未等于 1 时拒绝领取。

### 7. 为什么 Redis 先准备，却不能马上让人领取

```text
数据库事务尚未提交
    +-- 扣款/红包/流水：尚未成为已提交结果
    +-- Redis 金额池：已准备好
    +-- grant.ready=0：领取脚本拒绝
    |
    +-- 提交成功 -> ready=1 -> 允许满足条件的用户领取
    |
    +-- 回滚 -> afterCompletion 删除 grant、allow、pool、records
                清理失败记日志，不能说 Redis 自动随 MySQL 回滚
```

回滚清理回调在五参数 initRedPacketCache 中注册。即使客户端知道红包 ID，ready 门禁也防止它在发送事务提交前抢走临时池中的金额。

**这次的疑点：事务“提交后”和“完成后”有什么区别？**

| 回调 | 触发时机 | 这里做什么 |
|---|---|---|
| afterCommit() | 数据库成功提交后 | 设置 ready=1，尝试发布消息 |
| afterCompletion(status) | 提交或回滚等完成结果之后 | 仅在 status != STATUS_COMMITTED 时清理临时 Redis Key |

```text
正常提交：数据库提交 -> afterCommit 发布 -> afterCompletion(COMMITTED)
                                          条件不成立，不删除 Redis

正常回滚：数据库回滚 -> 不执行 afterCommit -> afterCompletion(ROLLED_BACK)
                                          条件成立，尝试删除 Redis
```

afterCompletion 不是“只在回滚后执行”；删除操作还受里面的 if 条件控制。注册回调时不会立即运行这段逻辑，由 Spring 事务管理器在对应时机触发；after 也不自动表示新开线程。本项目发布回调直接调用 publish.run()。参考 [Spring TransactionSynchronization](https://docs.spring.io/spring-framework/docs/6.2.x/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html)。

### 8. 真正发 Kafka 的位置：publishPending

```text
sendRedPacketMessage
    -> 组装 type=3 的红包聊天消息，body 含红包 ID、封面文案
    -> sendMessageKafka
         -> messageId 固定使用红包 ID
         -> clientMessageId 保留客户端原值，不覆盖
         -> 将消息存入 grant，published=0
         -> 注册 afterCommit 回调
    |
    v
数据库提交成功
    -> 回调设置 ready=1
    -> publishPending(packetId)
         -> 确认数据库红包存在且仍未领完
         -> 读取 grant 中的待发消息
         -> store-topic，等待本次 Kafka 发送结果
         -> message-topic，等待本次 Kafka 发送结果
         -> redpacket-creation-topic，等待发送结果
         -> 全部完成后 published=1
```

原文 13.4.3 将调用方的 clientMessageId 传到红包聊天消息。现已恢复原样保留：例如客户端传 `client-packet-123`，存储、推送以及补发载荷都保持该值。稳定 messageId 与 grant 中缓存的完整消息承担补发幂等，不需要改写客户端关联 ID；这不等于已实现发送请求幂等。

sendMessageKafka 的名字不能当成“这行执行时已经投递成功”；在当前发送事务内，它主要准备待投递内容和提交回调。实际 publishPending 使用 join 等待发送结果，不能把它描述为完全不等待网络的发送流程。

**这个方法具体往 Redis 存什么？**它复用 initRedPacketCache 已创建的 Hash `redpacket:<红包ID>:grant`，补写两项：

```text
redpacket:9001:grant（同一个 Hash）
    ready=0、发送者、会话类型、到期时间：前面的初始化已经写好
    |
    +-- message：完整红包聊天消息 JSON
    |     包含 messageId=9001、sessionId、senderId、type=3、createdTime
    |     body 包含 redPacketId=9001 和红包封面文案
    |
    +-- published=0：投递流程尚未全部完成
```

金额份额仍在另一个 pool List，不是写进这里的 message。保存完整待发 JSON 后，提交回调或修复任务都能用同一内容发布；只保存 Runnable 在进程内，重启后无法靠它恢复。这个 Redis 记录有保留期限，不是永久可靠事务消息表。

正常外层有事务同步时，此方法注册 afterCommit，然后返回红包 ID；它返回不代表消息已进 Kafka。没有事务同步时，源码的 else 分支会直接执行 publish.run()。

sendRedPacket 方法末尾构造了一个局部 creationEvent，但没有直接发送它；当前真正发布创建事件的是 publishPending，并使用数据库红包原创建时间，补发不会因此重算一轮 24 小时。

```text
store-topic               -> 保存群聊/单聊中的红包消息
message-topic             -> 推送聊天红包卡片
redpacket-creation-topic  -> 红包过期任务登记
```

**这次的疑点：三次 Kafka 发送分别由谁处理？**同一个 Kafka 客户端向三个 Topic 投递，完成三个不同任务：

| Topic | 消费入口 | 具体用途 |
|---|---|---|
| store-topic | [ConsumerOfflineService.consume](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/consumer/ConsumerOfflineService.java) | 调用 MessageServiceImpl 保存聊天中的红包消息到 message 表，供历史与离线查询 |
| message-topic | [ConsumerMessageService.consume](../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/consumer/ConsumerMessageService.java) | 找会话成员的在线 Channel，回显、推送红包卡片 |
| redpacket-creation-topic | [DelayTaskEnqueuer.handleRedPacketCreation](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/consumer/DelayTaskEnqueuer.java) | 根据红包 ID、原创建时间算 24 小时到期时间，登记到 redpacket-expire-zset，供后续到期处理 |

前两次发送相同的红包聊天消息 JSON，key 为 sessionId；第三次发送红包创建事件，主要是 redPacketId、createTime，key 为红包 ID。

store-topic 保存的是聊天 message，不是首次创建 red_packet 或扣发送者余额，后两项在前面的 MySQL 事务里已经完成。创建事件用于登记到期检查，也不代表立即执行退款。

源码按顺序发送并 join 等待各次投递结果；消费者各自推进。published=1 表示三路发送完成，不表示聊天已经落库、客户端已经收到或退款业务已经执行。

ready 与 published 是不同状态：ready 表示数据库已提交、领取门禁打开；published 表示上述消息投递流程完成。ready=1、published=0 可以发生，不能把它们当同一开关。

### 9. 提交后发送失败，后续如何补发

[RedPacketRepairJob.repair](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/scheduler/RedPacketRepairJob.java) 的 retryUnpublished 扫描 grant，发现 published 不等于 1 就调用 publishPending。实际可补发还依赖红包状态和 Redis 中保留的消息内容。

```text
数据库已提交
    -> store 已投递，push 或创建事件投递失败
    -> published 仍为 0，记录错误
    -> 后续修复任务再次 publishPending
         +-- 聊天存储：同一红包 ID 作为 messageId，重复 INSERT 可去重
         +-- 在线推送：可能再次回显，客户端仍需关联消息 ID
```

三次发送不是一个 Kafka 原子事务。稳定红包 ID 解决的是补发同一红包消息时的存储去重，不解决用户重新调用发送接口又创建新红包的长期请求幂等。补偿依赖 Redis 保留的数据，也不能替代完整账本恢复。

当前实现已修正原文先发消息再提交可能暴露未提交红包的顺序：先通过 ready 隔离临时金额池，数据库提交后再发布消息。本文按这套已有代码讲解，未修改原始课程资料或新增业务实现。

## 场景二：B 领取，Kafka 重投同一个事件

本场景要分清两个完成点：Redis 确定领取资格和金额，MySQL 消费事务完成余额入账。领取接口没有等待消费者入账。

```text
POST /api/chat/redPacket/receive（userId、redPacketId）
    → ActorGuard 核对 userId 与当前登录身份
    → RedPacketController.receiveRedPacket
    → RedPacketServiceImpl.receiveRedPacket
         ↓
    Lua：授权 → 重复领取及原金额 → 既有终态/到期 → ready → LPOP → HSET 领取记录
         ↓ 成功返回 {金额分, 是否最后一份}
    topic-redpacket-receive 领取事件，send(...).join()
         ├─ 接口返回领取结果（不等待数据库入账）
         └─ RedPacketConsumer.handleRedPacketReceive
                → RedPacketServiceImpl.handleRedPacketReceive
                → MySQL 事务：唯一领取记录 + 余额增加 + 流水
                → 提交后 Redis credit-ack 标记入账完成

    若领取的是最后一份，接口另发 topic-redpacket-completed
         → RedPacketConsumer.handleRedPacketCompleted
         → 服务层 CAS 将红包 0 改为 1，并清理 Redis/ZSET
```

### 1. 请求只指定领哪个红包，金额由服务器决定

从 [RedPacketController.receiveRedPacket](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/controller/RedPacketController.java) 进入 [RedPacketServiceImpl.receiveRedPacket](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/service/impl/RedPacketServiceImpl.java)。请求只有 userId、redPacketId；[ActorGuard](../../Common/src/main/java/cn/qingliao/common/security/ActorGuard.java) 核对外部请求的操作人身份，客户端不能决定自己领多少。

ActorGuard 是本项目定义的 Spring AOP 切面（`@Aspect`），拦截类上标有 `@RequireActor` 的方法调用，Controller 不必手动调用它。它通过 CurrentUser.id() 获取认证后写入 request attribute 的用户 ID，反射读取 DTO 中的 userId、senderId 等操作人字段，比较一致才 point.proceed()，不一致则抛异常。例如登录 B 却提交 userId=A，会被拒绝。它核对“操作人是不是自己”，是否有资格领取仍由后续 Lua 检查；经服务端认证的内部调用走代码中的放行分支。

服务把 pool、records、state、grant、allow 五个 Key，以及 userId、当前毫秒时间传给 [receive-redpacket.lua](../../RedPacketService/src/main/resources/lua/receive-redpacket.lua)。

### 2. Lua 一次完成校验、取钱和记结果

| 执行顺序 | 检查或修改 | 目的 |
|---|---|---|
| 1 | 单聊只允许 receiverId；群聊检查 allow Set | 群资格取发红包时的成员快照，不是每次领取都查数据库最新成员 |
| 2 | HEXISTS records userId，优先返回已领取及当前状态 | 已领用户不再弹出金额；Java 仍可读原金额，grant 过期不能遮蔽领取记录 |
| 3 | 已有终态优先；无终态时再用 expiresAt 判断到期 | 已领完不会仅因时钟到期变成已过期；新的到期领取被拒绝 |
| 4 | grant.ready 必须为 1 | 只保护新领取的 LPOP，发送事务尚未提交不能取钱 |
| 5 | LPOP pool | 取走发红包时已分配好的一份金额，不在领取时重新随机 |
| 6 | HSET records userId amount；另记领取时间 | 保存谁领了多少，供重复请求与补偿使用 |
| 7 | LLEN pool | 判断是否最后一份，返回金额与 completed 标识 |

```text
原来 pool=[200, 350, 450] 分，B 尚未领取
    → LPOP 得到 200
    → pool=[350, 450]
    → records：B=200
    → 返回 {200, 0}

B 再次请求
    → HEXISTS records B 为真
    → 返回已领取，不再 LPOP；Java 读取原金额供展示
```

这些动作在同一 Lua 脚本里执行，其他 Redis 命令不能插入中间，避免同一用户并发两次都通过“未领取”检查。Lua 不能把 MySQL/Kafka 也放进同一事务。

源码 Lua 的 RECORD_TTL 数值是 `7 * 24 * 60 * 60`，即七天；同一行“25H”注释与数值不符，按实际数值理解。到期检查早于重复检查，因此已领用户在红包到期后再请求，也可能先得到“已过期”。

### 3. Java 解析结果，发领取事件

Lua 返回无权、已领取、领完/过期、未找到等结果时，Java 分别拒绝或返回已有状态；未找到分支会查询数据库，不能一律当作还能领取。

成功时，Java 将整数分转为元用于响应，并发送包含 userId、redPacketId、receivedAmount、receiveTime 的事件到 `topic-redpacket-receive`，key 为红包 ID。

`send(...).join()` 等待生产者投递结果，不等待消费者完成 MySQL 入账。Kafka 投递成功后接口才正常返回本次成功结果；若投递失败，Redis 中的领取不会回滚，后续由补偿任务恢复。

### 4. 消费者事务入账，再确认

[RedPacketConsumer.handleRedPacketReceive](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/consumer/RedPacketConsumer.java) 解析并校验事件，调用 `handleRedPacketReceive`：

```text
开启 MySQL 事务
    → INSERT IGNORE red_packet_receive
         ├─ 插入 1 行：加领取者余额、写 TYPE_RECEIVE 流水
         └─ 插入 0 行：已存在领取记录，跳过加钱
    → 注册 markReceiptAcknowledged 提交回调
提交成功
    → HSET redpacket:{红包ID}:credit-ack 用户ID 1，保留七天
```

数据库 [RedPacketReceiveMapper](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/mapper/RedPacketReceiveMapper.java) 使用 INSERT IGNORE，配合 `(red_packet_id,receiver_id)` **唯一索引**决定谁执行余额副作用；余额、记录、流水在同一事务。只有该领取记录首次插入才加钱。并发重复事件仅检查处理结果，不会再次入账。

唯一索引来自 [02-business-upgrade.sql](../../database/02-business-upgrade.sql)。[FinancialSchemaVerifier](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/config/FinancialSchemaVerifier.java) 启动即检查，缺失则拒绝启动；不能只看 Java 写了 INSERT IGNORE 就认为幂等成立。

金融消费异常会抛出，使用 [FinancialKafkaErrorConfig](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/config/FinancialKafkaErrorConfig.java) 持续重试，防止账务失败但消息被跳过确认。代价是故障消息会阻塞对应分区，需要监控和人工处理方案。

这里的 credit-ack 是业务自己写的 Redis 入账标记，不是 Kafka 消费位移提交。放在 afterCommit 才能说明数据库已提交；提交后写标记失败会带来重复补发，由数据库唯一索引兜住。

markReceiptAcknowledged 是本项目在 RedPacketServiceImpl 内定义的 private 辅助方法，可理解为“标记这条领取记录已入账”。内部 Runnable 仅封装 HSET 和七天过期设置，并不会自动开启线程；有事务同步时注册 afterCommit，等提交成功再 acknowledge.run()，回滚不执行，无事务同步时才直接 run()。重复事件的 INSERT IGNORE 返回 0 分支也会调用它，为已有入账记录补写确认。它不负责加钱，也不是防重复入账的裁决者。

### 5. 最后一份与失败补偿

领取最后一份时，接口另外发送 `topic-redpacket-completed`，由消费者调用 `handleRedPacketCompleted`：CAS 把数据库状态从 0 改为 1，Redis state 写 1，删除金额池、保留领取记录、移除 ZSET。这个事件负责红包结束状态，领取事件负责给具体用户入账；两个 Topic 的消费完成顺序不作保证。

[RedPacketRepairJob.retryReceipts](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/scheduler/RedPacketRepairJob.java) 扫描 records，发现用户没有 credit-ack 就重发领取事件。因此 Redis 抢到金额后进程退出、Kafka 投递失败，或者数据库提交后确认标记没写上，都可在记录保留窗口内补偿；数据库唯一索引避免重复加钱。它也会检查金额池已空而数据库尚未结束的红包，补做结束处理。

## 场景三：未领完过期了，第一次退款事务失败

### 1. 谁发过期事件，谁消费

```text
发红包事务提交后，publishPending 发创建事件
    ↓ redpacket-creation-topic
DelayTaskEnqueuer.handleRedPacketCreation
    → ZSET：member=红包 ID，score=原创建时间 + 24 小时
    ↓ 等待到期
ExpirationDispatcher.dispatch（每秒调度）
    → Lua 批量取出并移除已到期的 ID
    → redpacket-expiration-topic，消息内容就是红包 ID 字符串
    ↓
ExpirationTaskExecutor.handleRedPacketExpiration(String redPacketId)
    → 转成 Long
    → RedPacketServiceImpl.handleRedPacketExpiration(id)
    → 关闭领取、计算剩余金额、退款
```

入口分别是 [DelayTaskEnqueuer](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/consumer/DelayTaskEnqueuer.java)、[ExpirationDispatcher](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/scheduler/ExpirationDispatcher.java) 和 [ExpirationTaskExecutor](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/consumer/ExpirationTaskExecutor.java)。Kafka 运送事件，ZSET 保存到期时间；消费者不会拿到创建事件后睡眠 24 小时。

过期消费者共用固定消费组，多个红包服务实例分担任务即可；退款操作依赖共享数据库与 Redis，不需要像在线推送一样每个节点各消费一遍。

这里调度使用 **score，不是 TTL**。登记相当于 `ZADD redpacket-expire-zset 到期毫秒时间戳 红包ID`；每秒调度执行 [RedisConfig.scanExpiredRedPacketsScript](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/config/RedisConfig.java) 中的 Lua，用 Redis TIME 获取当前时间，再 `ZRANGEBYSCORE key -inf 当前时间 LIMIT 0 500` 取一批到期 ID，随后 ZREM 删除这些成员并返回。查询与删除在同一脚本内原子执行，发送 Kafka 在脚本返回后进行。

score 是成员的排序分数，这里约定存到期时间；Redis 不会因为 score 小于当前时间就自动删除成员。TTL 则用于金额池等缓存的到期清理，初始化保留 25 小时，区别于红包的 24 小时业务期限；缓存自动删除不会替我们执行退款。

### 2. 退款事务具体做什么

读 [RedPacketServiceImpl.handleRedPacketExpiration](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/service/impl/RedPacketServiceImpl.java) 与 [freeze-refund.lua](../../RedPacketService/src/main/resources/lua/freeze-refund.lua)。方法有 `@Transactional`，顺序如下：

```text
查询红包，不存在就返回
    ↓
CAS：UPDATE red_packet SET status=2 WHERE red_packet_id=? AND status=0
    ├─ 更新 0 行：没有抢到处理资格，直接返回，不再次入账
    └─ 更新 1 行：本事务继续；此时尚未提交
         ↓
Redis state 写 2（已过期），领取脚本据此拒绝继续领取
         ↓
Lua 封盘：保存剩余金额结果，然后删除 pool
         ↓
剩余金额 > 0：发送者余额增加 + 写 TYPE_REFUND 退款流水
         ↓
领取记录保留 7 天，清理 ZSET 中的任务
         ↓
MySQL 提交：status=2、退款余额、退款流水一起生效
```

这里使用条件 UPDATE 抢占状态，不是先执行 `SELECT ... FOR UPDATE`。并发处理同一红包时，数据库更新会竞争同一行；前一个事务提交后，后一个不能再把 status=0 改成 2。前一个回滚则状态恢复，后续可重试。

对照方法阅读时，抓住以下几段即可：

| 方法中的代码 | 业务含义 |
|---|---|
| selectById | 获取红包及发送者；不存在就退出 |
| eq(status, 0).set(status, 2) | 只允许尚未结束的红包进入本次退款事务；UPDATE 返回影响行数 |
| update(null, cas) == 0 分支 | 若查到已过期，清理 ZSET 后返回；若已领完或不存在，直接返回。两种情况都不再退款 |
| 获取 poolKey / recordsKey / stateKey | 三个变量是 Redis Key 字符串，分别指向剩余金额列表、领取记录 Hash、终态标记 |
| SET stateKey 2，TTL 25 小时 | 先记录“过期”，让领取脚本拒绝领取；再删除金额池，避免空池被误判为领完 |
| execute(calculateRemainAmountScript, Arrays.asList(...)) | 执行封盘 Lua；列表第一项作为 KEYS[1] 金额池，第二项作为 KEYS[2] 已冻结的退款金额 |
| addBalance + recordBalanceLog | 以整数分增加发送者余额，并记录 TYPE_REFUND 流水 |
| expire(recordsKey, 168, HOURS) + ZREM | 保留领取记录七天，移除到期任务；不在这里立即删除领取记录 |

“墓碑”只是源码注释对 state 标记的称呼，不是另一个 Redis 机制。score 负责挑出到期任务，state=2 负责告诉领取逻辑红包已经过期；这里的 25 小时 TTL 只负责以后清理该标记。

余额增加委托 [UserBalanceMapper.credit](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/mapper/UserBalanceMapper.java)：余额行不存在则插入，存在则用 `balance=balance+amount` 在数据库中累加。没有先把余额查到 Java、加完再覆盖回数据库。

`@Transactional` 保护的是本地 MySQL 修改，Redis 不随之回滚。正常调用时，方法体执行结束后才由 Spring 事务拦截器尝试提交，因此方法内最后的“处理完成”日志也不能单独证明数据库已经提交。

例如发 10 元、已领取 6 元，pool 中剩下 `[100, 200, 100]` 分，退款就是 400 分；已领取的 600 分不退回。Redis 金额池到期自动删除不等于退款，退款必须执行数据库加余额与写流水。

### 3. Redis 已删金额池，数据库退款却失败怎么办

Lua 用 `redpacket:{红包ID}:refund-amount` 保存封盘结果，保留 7 天：

```text
第一次：pool=[100,200,100]
    → 保存 refund-amount=400，删除 pool
    → 数据库退款失败，MySQL 事务回滚，红包状态恢复为 0
      Redis 的封盘结果不会随 MySQL 回滚

重试：pool 已经不存在
    → Lua 先查到 refund-amount=400，直接返回原结果
    → 再执行数据库退款事务
    → 提交后 status=2，此后重复事件不能再次加余额
```

保存封盘结果解决“失败后重试还能知道退多少钱”；数据库状态条件与事务解决“同一笔退款不会重复入账”。两者一起才构成这条链路的幂等保护。

### 4. 当前失败后由谁补偿

当前 `ExpirationTaskExecutor` 的 `catch (Exception)` **只记录日志，没有重新抛出异常**，因此本处业务失败不会交给 Kafka 容器的异常处理器重试。不能把上一节领取入账的持续重试结论套到这个消费者上。

[RedPacketRepairJob.repair](../../RedPacketService/src/main/java/cn/qingliao/redpacketservice/scheduler/RedPacketRepairJob.java) 默认每轮结束后间隔 30 秒执行，扫描数据库中“status=0 且创建已满 24 小时”的红包，再调用同一个过期处理方法。它也补偿 ZSET 已移除但 Kafka 投递失败等情况；依赖调度开启、任务能运行以及退款依据仍保留。

当前服务方法本身没有再次核对创建时间是否已满 24 小时，到期筛选在调度器和数据库补偿扫描中完成。过期处理可能稍晚于到期时刻，领取 Lua 自身也检查 expiresAt，并不完全依赖调度及时关闭领取。

### 5. repair 怎样找到三类漏处理任务

它不是重放所有请求，也不是只读 Kafka 失败消息，而是对照已有状态寻找未完成工作：

| 执行顺序 | 从哪里找依据 | 判断和动作 |
|---|---|---|
| retryUnpublished | Redis grant Hash | published 不为 1，调用 publishPending；还需数据库红包 status=0、message 内容存在，才实际补发三路事件 |
| retryReceipts | Redis records 与 credit-ack | 有领取记录但无入账确认，重发领取事件；数据库唯一索引防重复加钱 |
| 到期扫描 | MySQL red_packet | status=0 且 created_time 已满 24 小时，按创建时间取最早最多 100 条，直接调用退款方法 |

**为什么有数据库已提交、消息未完成的情况？** `@Transactional` 在这里管理本地 MySQL 事务，没有把 Redis、Kafka 一起纳入同一个原子提交。发送红包先提交扣余额、红包记录、流水，提交成功后才在 afterCommit 中发布消息。afterCommit 的发送失败不能撤销已经完成的数据库提交；当前发布回调还会捕获异常并留待补偿。即使 Kafka 调用写在事务方法体内，也不能仅靠这个注解让 Kafka 与数据库一起回滚。

```text
MySQL 事务：扣余额 + 写红包 + 写流水 → COMMIT 成功
                                              ↓
afterCommit：发 store → 发 push → 发 creation → published=1
                         ↑ 此处失败或进程退出
数据库已经提交，无法由原事务回滚；后续从 published!=1 找到待完成任务。
```

**会不会扫描到正在正常发布的红包？会。** published=0 只表示“尚未记录全部投递完成”，不是“已经判定失败”，也不是发布锁：

```text
请求线程                           补偿线程
MySQL 提交
afterCommit 开始发布，published=0
正在等 Kafka 返回                  扫描到 published=0
                                   publishPending 同一红包
原发布继续                         补发也可能继续
    → 存在重复投递
```

提交前 Redis grant 就可能被扫描到，但补偿的 publishPending 先查数据库：正常事务隔离下，其他线程尚未提交的新红包查不到，会跳过；提交后两个发布入口没有共用互斥锁，可能同时投递。ShedLock 用于补偿任务之间的协调，不会自动锁住用户请求的 afterCommit 发布。

补偿重新执行的是发布，不会再次执行发送红包的扣余额或创建红包事务。聊天存储用稳定 messageId 去重，领取入账用唯一索引，退款用 CAS；在线推送仍可能重复，不能概括为所有副作用都完全幂等。若进一步减少发布并发，可考虑带恢复机制的发布状态抢占或共享互斥；这属于改进方向，当前没有实现。也不能在发送前简单把 published 改为 1，否则中途退出会让任务被误认为已完成。

对照 RedPacketRepairJob 阅读，前两段都是 Redis SCAN：先找匹配格式的 Key，再读每个 Key 中的业务状态；第三段才是数据库条件查询。`SCAN ... COUNT 100` 是每批遍历工作量提示，游标循环会继续扫描，不代表本轮最多处理 100 个红包；SQL `LIMIT 100` 才是这次查询最多取 100 条。

```text
第一类：retryUnpublished
    SCAN redpacket:*:grant
        → 例如 redpacket:123:grant
        → HGET published：为 1 跳过，否则 publishPending(123)
        → 校验数据库 status=0、message 存在
        → 补发 store、push、creation 三路事件，全部投递成功再写 published=1

第二类：retryReceipts
    SCAN redpacket:*:records
        → 例如 records={B:200,C:350}，credit-ack={B:1}
        → B 有确认，跳过
        → C 无确认，用金额 350 和保存的领取时间重建领取事件
        → Kafka 消费者尝试入账；若此前已入账，唯一索引拦住重复加钱

第三类：repair 内的 MySQL 查询
    SELECT ... FROM red_packet
    WHERE status=0 AND created_time <= 当前时间减24小时
    ORDER BY created_time ASC LIMIT 100
        → 对每条结果直接 handleRedPacketExpiration
        → 不依赖 ZSET 中还留着任务，也不需要重发过期 Kafka 事件
```

`key.split(":")[1]` 从 `redpacket:123:grant` 或 `redpacket:123:records` 中取出红包 ID `123`。第二类扫描中的 item.getKey() 是领取用户 ID，item.getValue() 是领取金额（分）。没有 credit-ack 只表示“缺少入账确认”，也可能是数据库已提交但确认缓存写失败，因此补偿不能无条件再次加钱。

```text
第一次退款失败
    ├─ MySQL 回滚：status=0，余额和流水修改撤销
    └─ Redis 保留：state=2，refund-amount=400，pool 已删除
          ↓
repair 查询到数据库仍未结束且已到期
    → 再次调用 handleRedPacketExpiration
    → CAS 成功，Lua 直接返回保存的 400
    → 退款余额与流水提交，status=2
          ↓
以后重复调用：CAS 更新 0 行，不再退款
```

retryReceipts 还会检查“有领取记录、金额池已空、数据库仍为 0”的红包，补做领完或过期处理。正常到期调度经过 ZSET 与 Kafka；数据库兜底则直接调用服务方法，绕过丢失的到期事件。

三段在一个 try 内依次执行，前段抛出异常会结束本轮，后面的工作等待下一轮再尝试；默认 30 秒是调度间隔，不是退款完成时限。金额池初始化只保留 25 小时，封盘结果及领取记录保留七天：如果未能及时封盘而金额池已被清理，或 Redis 数据丢失、封盘结果超期，仅靠数据库状态无法还原全部应退金额。补偿依赖数据与执行条件，不能推导为任何灾难下都不丢。

### 6. 红包详情查询是另一条读链路

`getRedPacketDetail` 和 `getRedPacketBasicInfo` 会执行 checkReadable：从 CurrentUser 取当前身份，发送者直接通过；其他用户通过 UserService 检查会话成员资格，不通过则拒绝。通过后才查询详情或基本信息。红包 ID 只是定位资源，不能替代查看权限；此检查不承担退款或补偿职责。

## 面试中需要守住的表述

可以说：用 Lua 控制领取并发，用数据库唯一索引与本地事务防重复入账，用延迟任务、状态检查和补偿缩小跨组件失败窗口。

不能说：实现了生产级资金系统或全局严格一次。当前是测试余额；没有支付渠道、完整对账审计、发送请求长期幂等、Redis 全量丢失后的恢复方案。3 秒防重复提交只是短时限流式保护，不是支付级请求幂等。Redis AOF 与有限保留期也不是永不丢失的承诺。

5. 为什么余额足够的条件必须放进扣款 UPDATE？普通红包 10 元分 3 份如何保证守恒？
6. afterCompletion 成功提交后也会执行，为什么不会删掉正常红包？sendMessageKafka 往哪个 Redis 数据结构写入哪两项？
7. 当前过期消费者退款失败后，是否会直接触发 Kafka 异常重试？谁负责补偿？
8. 领取接口返回成功是否代表余额已入账？Redis 领取记录与数据库唯一索引分别防什么重复？
9. afterCommit 发消息失败为什么不能回滚已提交的扣款？published=0 是否一定代表失败，会不会与正常发布并发？

10. 已领用户在红包到期或 grant 过期后再次点击，应直接丢掉原金额吗？已领完之后到达过期时刻会改成已过期吗？

## 自查解答

1. Redis 控制抢领竞争与即时返回；数据库唯一索引防消息重投导致余额副作用重复。两者保护不同资源，任一层都不能代替另一层。
2. 第一次删除后数据库事务若回滚，第二次池已空，会丢掉原应退金额。冻结脚本先保留退款结果，让重试得到相同金额，再由数据库状态防重复退款。
3. 没有。它们改善提交顺序和可重试性，但仍依赖数据保留与基础设施；Redis 灾难性丢失、补偿窗口外故障、发送请求重试等需要更完整账本、事务消息和对账恢复方案。
4. 它准备稳定消息 ID、Redis 待发内容并注册提交回调，publishPending 才执行三路发送。ready 是提交后领取门禁，published 是消息投递流程完成标记；一个为 1 不代表另一个必为 1。
5. 避免并发请求先查都足额、随后超额扣减；数据库条件判断与扣减一起原子完成。1000 分除以 3 得基础 333 分，余 1 分给一份，结果为 334、333、333 分，总和不变。
6. 清理受 status != STATUS_COMMITTED 条件控制，正常提交时不执行删除。它向已有 grant Hash 补写 message 待发 JSON 与 published=0，不负责向 pool 写金额份额。
7. 不会。该消费者捕获异常后只记日志；默认间隔 30 秒运行的 RedPacketRepairJob 扫描数据库中已到期且 status=0 的红包，再调用退款方法。封盘金额需仍在保留窗口内。
8. 不代表；接口等待领取事件投递，数据库入账由消费者异步完成。Lua 中的领取记录防同一用户再次从金额池取钱；数据库唯一索引防重复事件再次增加余额。
9. afterCommit 在本地 MySQL 已提交后执行，Redis/Kafka 没有加入同一个原子事务，后续发送失败不能撤销先前提交。published=0 也可能是正常发布尚未完成，当前无发布互斥，补偿可能并发重发；存储端去重与业务幂等承接重复，在线推送仍可能重复。

10. 不应。领取记录仍在时优先返回已领取状态，Java 从 records 读取原金额；已有“已领完”终态优先于时钟到期。只有新的领取才继续检查到期与 ready 门禁。
