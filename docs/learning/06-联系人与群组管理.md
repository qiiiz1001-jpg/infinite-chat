## 场景一：A 申请 B，通过后建立单聊

假设 A=1001、B=2002，申请 ID=9001，通过后生成会话 ID=99。下面的 ID 与时间都是讲解示例，不表示数据库已有这些数据。本次根据当前源码扩充讲解，未启动服务或执行真实 Kafka/Redis/MySQL 联调。

```text
A 发送申请
    -> apply_friend：9001，A -> B，未读
    +-> 系统通知：告诉 B 有新申请
    +-> 延迟任务：安排 24 小时后检查

B 接受
    -> 条件更新申请：未读/已读 -> 已通过
    -> friend：A -> B、B -> A 两行
    -> session：会话 99 一行
    -> user_session：A 属于 99、B 属于 99 两行
    -> HTTP 响应返回会话信息，系统通知告诉 A 有新会话
```

### 1. 四张表分别回答什么问题

| 表 | 记录什么 | 示例 |
|---|---|---|
| apply_friend | 谁向谁申请、附言、状态和时间 | A 申请 B，尚未处理 |
| friend | 我与某人的好友关系及状态 | A -> B，B -> A，各一行 |
| session | 聊天容器 | 单聊会话 99 |
| user_session | 谁属于哪个聊天容器 | A -> 99，B -> 99 |

friend 有方向，便于表达某一方自己的关系状态，例如 A 拉黑 B。session 是双方共享的聊天容器，消息按 sessionId 归属；有好友行不等于已经创建并授权了会话成员关系。

### 2. A 发申请：先有申请，尚未成为好友

按 [ContactController.java](../../UserService/src/main/java/cn/qingliao/userservice/controller/ContactController.java) 的 `sendFriendRequest` → [ApplyFriendServiceImpl.java](../../UserService/src/main/java/cn/qingliao/userservice/service/impl/ApplyFriendServiceImpl.java) 的同名方法阅读。

```text
POST /api/contact/1001/friend/2002
    -> ContactController.sendFriendRequest
    -> ApplyFriendServiceImpl.sendFriendRequest
        -> 双方用户是否存在、是否添加自己、是否已有关系行
        -> 查询 senderId=A、receiverId=B 的已有申请
            +-- 没有：handleNewFriendApplication
            |         新建申请，状态 UNREAD=0，生成申请 ID
            +-- 已通过：拒绝重复添加
            +-- 其他状态：handleExistingFriendApplication
                      复用申请 ID，更新附言、状态和 createdTime
        -> sendFriendApplicationNotification：通知 B
        -> registerExpirationTask：发布到期任务注册事件
```

当前发送方法只要查到 A -> B 的 friend 行就会拒绝，不是只检查 NORMAL 状态。申请重发分支也可能复用未读或已读记录；不要把它写成只有拒绝、过期后才能重新发。

路径中的 userId 还受类上的 RequireActor 与 [ActorGuard](../../Common/src/main/java/cn/qingliao/common/security/ActorGuard.java) 检查，必须与当前登录身份一致，不能随意改路径冒充 A。

通知和到期事件是两个用途：系统通知让 B 的界面知道有申请；创建事件让延迟链路知道何时处理申请。它们都不等于已经创建 friend/session。

### 3. B 接受：实际还经过一个状态分发入口

不是从 Controller 直接跳到 handleFriendRequest：

```text
ContactController.modifyFriendApplicationStatus
    -> ApplyFriendServiceImpl.modifyApplicationStatus
        +-- ACCEPTED=1 -> handleAcceptApplication
        |                  -> 找 A -> B 的申请
        |                  -> handleFriendRequest(申请, B, true)
        +-- REJECTED=2 -> handleRejectApplication
        |                  -> handleFriendRequest(申请, B, false)
        +-- READ=3     -> handleReadApplication -> markAsRead
```

handleFriendRequest 先确认操作者是申请接收者，并要求状态是未读或已读。已读只表示看过，不代表接受。

```text
未读 0 -------> 已读 3
   |               |
   +---------------+----> 通过 1
   +---------------+----> 拒绝 2
   +---------------+----> 过期 4（另需满 24 小时）
```

### 4. CAS 在这里就是带旧状态条件的数据库更新

CAS 即 Compare And Swap（比较并交换）：比较当前值是否符合预期，符合才改成新值，比较和修改作为一个原子操作完成。这里借用这一思想做 SQL 条件更新，不是另外创建了一个 CAS 类。

**图 1：CAS 判定图。**比较与修改在同一条数据库 UPDATE 中完成。

```text
handleFriendRequest：尝试处理申请 9001
    |
    v
数据库检查：ID=9001，且当前 status IN (0, 3)？
    |
    +-- 是 --> 改为新状态：通过 1 / 拒绝 2
    |          返回 updated=true
    |              |
    |              +-- 接受申请 --> 继续创建好友、会话
    |              +-- 拒绝申请 --> 结束处理
    |
    +-- 否 --> 本次不修改，updated=false
               不再创建好友、会话
```

handleFriendRequest 的 LambdaUpdateWrapper 相当于以下 SQL；这是按源码条件写的示意，参数以实际请求为准：

```sql
UPDATE apply_friend
SET status = 1, updated_time = NOW()
WHERE apply_friend_id = 9001
  AND status IN (0, 3);
```

这里不需要记新的 CAS 工具类。关键是数据库原子判断并修改：只有申请仍待处理才更新。前面的查询不能代替 UPDATE 中的条件，因为查询之后状态仍可能被其他请求改变。

**图 2：两个接受请求的并发时序。**下面假设请求 1 最终提交成功。

```text
时间向下       接受请求 1           数据库申请 9001          接受请求 2
   |          查询状态 ----------> 待处理 <--------------- 查询状态
   |          查到待处理                                  查到待处理
   |
   |          条件 UPDATE -------> 待处理 -> 已通过
   |          updated=true
   |          创建关系、会话
   |          提交数据库事务
   |
   |                              已通过 <--------------- 条件 UPDATE
   |                                                      条件不满足
   |                                                      updated=false
   v                                                      不创建关系、会话

两个请求都可能通过前面的 Java 查询检查；数据库 UPDATE 的旧状态条件决定谁能继续。
```

过期任务也竞争同一条待处理记录，因此不能在已经通过后再无条件覆盖成过期。CAS 这里是条件更新的业务用法，和前面数据库唯一主键防重复插入是两种不同手段。

### 5. 真正建立好友、会话：FriendServiceImpl.addFriend

继续进入 [FriendServiceImpl.java](../../UserService/src/main/java/cn/qingliao/userservice/service/impl/FriendServiceImpl.java) 的 addFriend：

```text
addFriend(B, A)
    -> createFriendRelations：两条 friend
    -> createSession：一条 type=0 的 session
    -> createUserSessions：两条 user_session
    -> sendNewSessionNotification：向申请者 A 发系统通知
    -> 返回会话信息，Controller 将结果返回 B
```

modifyApplicationStatus 外层已有数据库事务，addFriend 也声明事务；当前这条正常调用链中的申请状态、关系、会话及成员修改参与同一数据库事务，失败需要一起回滚。不能只根据同类内部调用的方法上有注解，就认定内部调用额外开启了事务。

好友的删除、拉黑、解除拉黑仍看 FriendServiceImpl 的对应方法；发消息还会经过会话授权，不能只靠前端是否显示发送按钮。

原文 13.4.6 的单聊校验明确拉黑方向：A 拉黑 B，仅阻止 B → A，A → B 仍允许；双方互相拉黑则两个方向都拒绝。2026-10-31 已修正普通消息入口此前“双向必须 status=0”的额外限制，与红包使用的方向规则保持一致。成员、会话、用户状态检查仍先后执行，不能用拉黑方向规则绕过会话权限。

## 延迟任务读哪里

### 1. 为什么中间用 ZSET

创建申请时 registerExpirationTask 计算到期时间，并发布创建事件。当前链路用 Kafka 运送事件、Redis ZSET 保存等待到期的 ID；不是 Kafka 收到记录后自动等待 24 小时。

**图 3：24 小时过期的组件与触发流程。**两段 Kafka 是运送事件，ZSET 保存等待检查的任务。

```text
【立即登记】
创建 / 重发申请
    |
    v
ApplyFriendServiceImpl.registerExpirationTask
    | 计算 expireTime = 当前时间 + 24 小时
    v
Kafka：friend-request-creation-topic
    | Kafka 监听容器调用消费者
    v
FriendRequestExpirationEnqueuer.enqueueExpirationTask
    | ZADD：member=申请 ID，score=expireTime
    v
Redis ZSET：friend-request-expire-zset
    | 保存这些任务，不主动触发到期回调
    |
【未来调度】
Spring 定时任务：@Scheduled(fixedRate=1000)
    |
    v
FriendRequestExpirationDispatcher.dispatch
    | 执行 RedisConfig 中的 Lua
    +------> Redis ZSET：筛选 score <= 当前时间的 ID，并移除
    | <----- 返回本批已取走的 ID
    v
Kafka：friend-request-expiration-topic
    | Kafka 监听容器调用消费者
    v
FriendRequestExpirationExecutor.executeExpiration
    | 查询当前申请，再执行条件 UPDATE
    v
MySQL：ID 对应的申请仍待处理，且 createdTime 已满 24 小时？
    +-- 是 --> 标记 EXPIRED=4
    +-- 否 --> 不修改：可能已接受、已拒绝、已过期或刚重发
```

ZSET 按 score 排序，定时任务能批量找到到期 ID。时间戳是排序依据，不是给每个 member 设置 Redis TTL；到期状态也不是靠 Redis 自动删除 Key 来完成。

### 2. 三个组件的分工

| 文件与方法 | 一句话职责 |
|---|---|
| [FriendRequestExpirationEnqueuer.enqueueExpirationTask](../../UserService/src/main/java/cn/qingliao/userservice/consumer/FriendRequestExpirationEnqueuer.java) | 消费创建事件，执行 ZADD 注册到期时间 |
| [FriendRequestExpirationDispatcher.dispatch](../../UserService/src/main/java/cn/qingliao/userservice/scheduler/FriendRequestExpirationDispatcher.java) | 定时取走已到期 ID，投递过期事件 |
| [FriendRequestExpirationExecutor.executeExpiration](../../UserService/src/main/java/cn/qingliao/userservice/consumer/FriendRequestExpirationExecutor.java) | 消费过期事件，按状态、创建时间条件更新数据库 |

代码入口对照图 3：创建入口在 handleNewFriendApplication / handleExistingFriendApplication，二者都会调用 registerExpirationTask；Lua Bean 的方法名是 RedisConfig.scanExpiredFriendRequestsScript。

创建消费者由 Kafka 监听容器触发，调度器由 Spring 定时任务触发，最终执行消费者再由另一条 Kafka 监听触发；这些类不是同一个调用线程从上到下依次直调。Dispatcher 调用 redisTemplate.execute 时，参数 "0" 使 Lua 使用 Redis 自己的当前时间，"500" 是本批最多取出的数量。

**图 4：ZSET 如何筛出到期任务。**下面把毫秒时间戳显示成可读时间，便于比较。

```text
假设 Redis 当前时间为周二 10:00

申请 ID（member）       到期时间（score）       本轮处理
9001                   周二 09:59             取出并移除 --+
9002                   周二 10:00             取出并移除 --+--> 发过期事件
9003                   周二 10:05             保留，等后续扫描

Lua 的一次原子执行：按时间筛选 -> 移除本批 ID -> 返回这些 ID
```

Dispatcher 使用的 Lua 在 [RedisConfig.java](../../UserService/src/main/java/cn/qingliao/userservice/config/RedisConfig.java)。ZRANGEBYSCORE 与 ZREM 放进同一脚本，使本次选择和移除在 Redis 内原子执行，避免并发取走同一批记录。

ShedLock 的 Redis 配置在 [ShedLockConfig.java](../../UserService/src/main/java/cn/qingliao/userservice/config/ShedLockConfig.java)。多个 UserService 实例会竞争同名调度锁，正常租期内限制调度重复执行；它不是每条申请的业务幂等记录，任务超出锁租期也不能据此保证绝无重叠。

### 3. 为什么旧事件不能只按申请 ID 直接置过期

同一申请重发时复用 ID，但 createdTime 重设。假设：

**图 5：重发申请与旧到期事件的时间线。**

```text
周一 10:00    创建申请 9001
    |         createdTime = 周一 10:00
    |         原计划周二 10:00 到期
    v
周二 09:00    重发申请 9001，复用同一个 ID
    |         createdTime = 周二 09:00
    |         重新登记计划：周三 09:00 到期
    v
周二 10:00    假设旧到期事件仍然到达 Executor
    |         数据库当前 createdTime 仅过去 1 小时
    |         不满足满 24 小时条件 -> 不修改
    v
周三 09:00后  新到期事件 / 数据库兜底扫描再次检查
              若仍待处理且已满 24 小时 -> 可以置为过期
```

Executor 不仅查询后检查时间，最终 UPDATE 也带 createdTime <= 当前时间减 24 小时、状态 IN(未读,已读) 的条件。这样即便检查后又发生重发、接受，也不能仅凭过时查询无条件修改。

### 4. 取走 ZSET 之后，Kafka 发送失败怎么办

**图 6：正常处理与失败补偿。**数据库扫描是独立任务，正常链路成功时也会运行。

```text
Dispatcher 的 Lua 已从 ZSET 取出并移除申请 ID
    |
    +-- 过期事件送达并处理 --> executeExpiration --> 条件更新 MySQL
    |
    +-- 进程退出 / Kafka 投递失败 / 执行消费失败
          |
          v
       申请可能仍在数据库中待处理，ZSET 中已经没有这个任务

独立的 Spring 定时任务：@Scheduled(fixedDelay=60000)
    | 每轮结束后间隔 60 秒再次执行，不依赖上面报告失败
    v
FriendRequestExpirationExecutor.repairExpiredRequests
    |
    v
直接扫描 MySQL：仍待处理 + createdTime 已满 24 小时
    +-- 满足 --> 更新为过期
    +-- 不满足 --> 不修改，不影响已处理或刚重发的申请
```

当前发送与消费者异常主要记录日志，不能把它们描述为完整的事件重投保障；好友过期能靠数据库扫描补偿。它会有调度延迟，不保证 24 小时到达的瞬间状态立即改变；接受申请入口当前也没有额外的严格截止时间判断。

已有 member 再 ZADD 会更新 score；返回 false 可表示没有新增 member，不能只根据 Enqueuer 的“注册失败”日志断定更新时间失败。这是当前日志用词的限制，本次答疑未修改源码。

### 5. 通知链与数据库事务的边界

[NotificationServiceImpl.java](../../UserService/src/main/java/cn/qingliao/userservice/service/impl/NotificationServiceImpl.java) 向 system-notification-topic 发申请/新会话通知。实时消费者推送，离线消费者单独存储；不走普通文本消息的 Long ID 契约。

这条好友申请、接受链中的通知发送目前发生在事务方法内，不是统一 afterCommit 投递。可能出现通知先到但数据库尚未提交、事务回滚但通知已发出，或数据库成功而异步通知失败。没有通用事务消息表与可持续重放机制，不能声称关系变更与通知强一致；数据库过期扫描也不负责补发所有即时通知。

## 场景二：建群、拉人、踢人、退群

从 [GroupController](../../UserService/src/main/java/cn/qingliao/userservice/controller/GroupController.java) 进入 [GroupServiceImpl](../../UserService/src/main/java/cn/qingliao/userservice/service/impl/GroupServiceImpl.java)。顺序读 `createGroup → inviteGroup → kick → exitGroup → members/groups`，不用逐行看分页包装。

### 1. 群的数据仍然是 session 与 user_session

假设 A 邀请好友 B、C 建立群 8001；ID 是讲解示例。群使用 type=1 的 session，不会给每对群成员创建单聊，也不会自动让 B、C 互相成为好友。

```text
session：8001，type=1，status=0
    |
    +-- user_session：(A, 8001)，role=0，群主
    +-- user_session：(B, 8001)，role=2，普通成员
    +-- user_session：(C, 8001)，role=2，普通成员

聊天消息的 sessionId=8001
实时推送按这个会话查询成员，不需要为 A-B、A-C、B-C 各建会话。
```

role=1 是管理员。当前代码有管理员权限分支，但没有群主转让、解散、管理员任命接口；不要仅凭角色值存在，就认定这些操作已有 HTTP 入口。

### 2. 建群：createGroup 创建群会话和成员行

```text
POST /api/group
    -> GroupController.create
    -> GroupServiceImpl.createGroup
        -> CurrentUser.id：取得真实创建者 A
        -> activeUser：确认创建者可用
        -> eligibleFriends：按 A 的好友关系筛选、去重
        -> 有效好友为空则拒绝建群
        -> 新建 session：type=1、status=0
        -> add：插入 A，role=0
        -> add：插入有效好友，role=2
        -> notifyMembers：登记提交后的系统通知
        -> 返回群 ID、名称和成员列表
```

eligibleFriends 在当前实现中检查被邀请用户可用，并查询操作者到对方的 friend.status=0；它没有额外核对反向好友状态。过滤后至少有一名有效好友。已恢复原文的成员昵称拼接群名（截前 16 字符）、默认头像，以及 sessionType/avatar/failedMemberIds 返回；有效成员、非法成员与通知失败成员按实际处理结果组装。此前额外加的单次 100 人、群总数 500 人限制已移除，不能再把它们当作原文要求。红包份数同样没有额外的 500 份限制，仍校验金额、正整数份数及群成员数。

### 3. 谁在操作、他是什么角色，来源不同

```text
当前登录身份                         当前群角色
JWT/Redis 认证                        数据库 user_session
    -> 服务端 request attribute          -> 按 sessionId + actor 查询
    -> CurrentUser.id()                   -> 读取 role
             |                                  |
             +--------------+-------------------+
                            v
                  用真实身份与真实角色判断权限
```

actor 来自 [CurrentUser](../../Common/src/main/java/cn/qingliao/common/security/CurrentUser.java)，不是直接相信 DTO 的 creatorId、inviterId、operatorId。[ActorGuard](../../Common/src/main/java/cn/qingliao/common/security/ActorGuard.java) 还会检查这些声明的操作者字段，拒绝与登录身份不一致的请求。群角色从数据库取，前端传 role 不能让自己变管理员。

### 4. 成员变更为什么先 lock 群会话行

inviteGroup、kick、exit 都在数据库事务中先调用 lock(sessionId)。lock 进入 [SessionMapper.selectForUpdate](../../UserService/src/main/java/cn/qingliao/userservice/mapper/SessionMapper.java)：

```sql
SELECT * FROM `session` WHERE session_id = #{sessionId} FOR UPDATE
```

同一群的修改都先竞争这一行，锁保持到事务提交或回滚；对同一行再执行 FOR UPDATE 的其他事务要等待。不同群使用不同行，可以分别处理。参考 [MySQL 锁定读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

```text
群 8001 原有 A、D，A 和管理员 D 同时邀请好友 C

事务 A                         事务 D
锁 session 8001 成功           尝试锁 session 8001 -> 等待
查询已有成员，不包含 C
新增 C
提交，释放锁
                               拿到锁
                               再查已有成员，已包含 C
                               标为已在群内，不重复插入
```

锁的是共同的 session 行，起到同群成员修改的共同入口作用。它不会自动把所有 user_session 行和普通查询全部锁住；要依赖这些修改路径都遵守“先锁群，再查权限/人数、改成员”的约定。

与前面的 CAS 比较：申请处理靠带旧状态条件的 UPDATE 争取一次处理资格；这里是先用 FOR UPDATE 排队，再完成一组查询、判断与修改。两者都在数据库层协调，不局限于某个 JVM。

### 5. 拉人：inviteGroup 先锁，再检查角色、好友和已有成员

```text
POST /api/group/invite -> inviteGroup
    -> lock(sessionId)：锁群会话，确认有效群
    -> membership：操作者必须是群成员
    -> role 只能是 0、1：群主或管理员
    -> eligibleFriends：筛操作者的有效好友并去重
    -> 查询已有有效成员
    -> 逐个处理候选人
         +-- 已在群中 -> 记入 failedIds
         +-- 可以加入 -> 插入 user_session，role=2，记入 successIds
    -> 没有任何新增则报错
    -> 向本次新加入的成员登记完整新群会话通知
    -> 返回成功、失败 ID 列表
```

服务端重新检查成员身份与已有关系，不依赖前端筛选。邀请通知的 body 包含 sessionName、avatar、creatorId、membersCount，人数为所有新增完成后的值。

### 6. 踢人和退群：删除对应的成员关系

踢人入口是 `POST /api/group/kick → kick`，检查顺序为锁群、验证操作者成员身份和角色、检查每个目标角色，再删除有权移除的 user_session 记录。目标列表不能为空。

canKick 的权限矩阵：

| 操作者 | 群主 0 | 管理员 1 | 普通成员 2 |
|---|---|---|---|
| 群主 0 | 不可踢 | 可踢 | 可踢 |
| 管理员 1 | 不可踢 | 不可踢 | 可踢 |
| 普通成员 2 | 不可踢 | 不可踢 | 不可踢 |

```text
主动退群：POST /api/group/exit -> exit
    -> 锁群
    -> CurrentUser.id 取得退群用户
    -> 确认仍是成员
    -> 若 role=0：拒绝直接退出
    -> 删除这个用户在该群的 user_session
    -> 登记成员离开通知
```

改变的是用户对该群的成员资格，其账户、其他群的成员记录并不因此消失。发消息时还要经过会话成员授权，不能只依赖前端移除群入口。

### 7. 踢人与主动退出的通知接收者不同

```text
原成员：A、B、C
    |
    +-- 保存 before=[A,B,C]
    +-- 删除 B 的成员关系
    +-- 提交后向 before 中的用户发通知
         -> 供 A、C 刷新成员列表
         -> 供 B 获知已被移出、更新群入口
```

如果删除后只向剩下的 A、C 通知，被移出的 B 就收不到这次状态变化。邀请只给本次新成员发送 103 新会话通知；主动退出按原文给剩余成员发 104 通知，body.operatorId 显式为 null。踢人 body.operatorId 为实际操作者。

### 8. 通知在数据库提交后发出

notifyMembers 先整理通知，再注册 TransactionSynchronization.afterCommit。建群响应需要 failedMemberIds 时，提交后对每个通知有界等待确认（最多 5 秒），通知失败被加入返回列表，但已提交成员不回滚；其他群通知异步记录失败。

```text
事务内：锁群 -> 检查权限 -> 修改成员 -> 注册 afterCommit
    |
    +-- 回滚 --> 成员修改回滚，不执行提交后的发送
    |
    +-- 提交成功 --> 释放事务持有的锁，执行 afterCommit
                      -> Kafka system-notification-topic
                      -> 实时通知推送 / 离线通知存储
```

这样能让通知在数据提交后发布，但提交后进程退出或投递失败仍可能丢通知；当前没有通用 outbox 重放机制，不能声称成员修改与通知强一致。这与上面好友链路在事务方法内直接发送通知的实现不同。

### 9. 查询入口只抓权限范围

| 方法 | 重点 |
|---|---|
| members | 先要求当前用户属于该会话，再分页读取有效成员和角色 |
| groups | 只允许查询当前用户自己的群列表，过滤有效群会话 |
| count | 先验证当前用户成员身份，再统计有效成员 |

分页响应已完整填充 pageSize/pageNum/pages/hasNext/hasPrevious；groups 按用户加入时间倒序做数据库分页，返回原文 name/memberCount/createdTime，并保留此前 sessionName/membersCount 别名。普通 DTO 组装不逐行展开。第一遍优先追 `createGroup → inviteGroup → lock → kick/exit → notifyMembers`。

### 答疑：通知由谁消费？收到后重查成员还是改本地缓存？

**数据库先改变，通知再告知客户端。**退群、踢人先删除 user_session 并提交，通知不是等客户端收到后才修改成员。后续发送消息的会话授权也查服务端成员关系，页面即使未刷新也不能仅凭旧界面获得发送权限。

```text
UserService：删除群成员关系 -> 事务提交 -> 发系统通知
    |
    v
Kafka：system-notification-topic
    +-- SystemNotificationConsumer（各实时节点独立组）
    |     -> 按 receiverId 查本机 Channel -> 推给在线客户端
    |
    +-- NotificationStoreConsumer（通知存储组）
          -> 存入 MySQL system_notification，供通知接口查询
```

推送入口：[SystemNotificationConsumer.consumeSystemNotification](../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/consumer/SystemNotificationConsumer.java)。它只取 receiverId、查 Channel、发送通知，不会查询群成员或修改前端缓存。存储入口是 [NotificationStoreConsumer.consume](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/consumer/NotificationStoreConsumer.java)。

当前 `GET /api/group/{sessionId}/members → GroupServiceImpl.members` 直接通过 Mapper 查询 MySQL 的 user_session，再批量查询 user 补昵称头像，没有该方法维护的 Redis 成员缓存；方法内的 HashMap 只是本次请求组装响应的临时对象。

退群通知包含群 ID、type=104、退出者 ID 列表，body.operatorId=null 表示主动退出，客户端可以据此定位变化。前端有两种可选实现：

```text
仍在群中的 A、C 收到通知
    +-- 使本地列表失效，再请求成员接口 -> 后端查 MySQL -> 更新页面
    +-- 按 memberIds 直接修改本地列表 -> 重连或必要时再与服务端校准

被踢出的 B 收到踢人通知（主动退群者由退出接口结果更新本地状态）
    -> 应移除或禁用对应群入口、发送状态
    -> 重新查询该群成员会被成员身份检查拒绝
```

本次在当前工程中未找到对应前端通知处理代码，以上是可选客户端处理方式，不代表已实现自动刷新或本地缓存。发通知也不能保证所有客户端立刻收到；后端数据库与权限判定不依赖客户端先更新页面。

## 通知为什么单独处理

[NotificationServiceImpl](../../UserService/src/main/java/cn/qingliao/userservice/service/impl/NotificationServiceImpl.java) 生成系统通知，进入独立 Topic；实时节点由 [SystemNotificationConsumer](../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/consumer/SystemNotificationConsumer.java) 推送，离线侧由 [NotificationStoreConsumer](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/consumer/NotificationStoreConsumer.java) 落 `system_notification`。

通知 ID 是字符串，聊天 ID 是 Long。分开消费和存储可避免把 msg_ 开头通知当数字解析。通知查询、已读走 [NotificationController](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/controller/NotificationController.java)，按当前用户过滤。

### 答疑：业务表已修改，为什么还要 system_notification？

这张表是**用户的通知收件箱**：记录接收者、通知内容、时间和已读状态。业务表记录当前事实，通知表记录“需要让这个用户知道的变化”。

```text
群主把离线的 B 移出群
    -> user_session 删除 B：立即改变 B 的群资格
    -> 系统通知进入 Kafka
         +-- 在线推送：B 没连接，跳过本次推送
         +-- 通知存储：保存“你被移出群”的通知

B 之后登录
    -> 查群列表：得到当前状态，不再包含这个群
    -> 查通知列表：可以知道发生了什么
```

通知不是等客户端收到后再修改成员数据库；好友申请通知也不会自动创建好友关系，B 点击接受仍需发起单独的业务请求。客户端依据通知更新界面，与后端修改业务表是不同动作。

当前 `GET /api/message/notifications` 查询自己的通知，`POST /api/message/notifications/{messageId}/read` 标记自己的通知已读。read_flag 及表结构见 [02-business-upgrade.sql](../../database/02-business-upgrade.sql)。当前列表返回通知 payload，没有额外返回 read_flag 或未读计数；不能据此宣称完整前端通知中心已经实现。

通知成功进入 Kafka 并被存储消费者处理后才会出现在表里。这张表不是投递前写入的 outbox，不能补偿根本没有成功投递的通知。

## 本篇自查

1. 好友关系为什么双向存储，和 session 有什么区别？
2. 两人同时处理申请、两管理员同时变更成员，分别怎么控制？
3. afterCommit 发送通知是否等于通知不会丢？
4. 已经查询到申请待处理，为什么 UPDATE 还要带状态条件？
5. ZSET 到期任务取走后丢失，当前靠什么补偿？重发后的旧事件如何避免误伤？
6. 群成员行在 user_session，为什么邀请、踢人、退群却先锁 session？锁能自动拦住所有成员表写入吗？
7. 踢人、退群为什么向变更前的名单通知？当前已有管理员任命或群主转让接口吗？

## 自查解答

1. 好友行表达“我与对方”的关系与状态；会话表达消息属于哪个容器，成员表表达谁能访问。双向行支持双方关系检查，不能以任意一行存在代替全部授权。
2. 申请靠待处理状态的条件更新竞争一次；成员变更先锁同一会话行，再读当前角色和成员、执行变更。单实例 synchronized 不能替代跨实例数据库约束与锁。
3. 不能。它保证通知发生在提交之后，但提交成功到发送完成之间仍会崩溃。可用同事务写 outbox，再由任务可靠投递与消费端去重。
4. 查询与更新之间可能有其他请求改变状态；条件更新在数据库中争取一次处理资格，只有更新成功才能继续建立关系和会话。
5. Executor 的数据库兜底扫描按时间、状态补过期；旧事件执行时重新检查当前 createdTime，最终 UPDATE 再带时间条件，防止把未满新 24 小时的申请提前终止。
6. 用同群的 session 行作为共同锁入口，让遵守约定的成员变更在同一个数据库中排队，保护角色、人数等复合判断。不会自动拦截所有 user_session 写入，其他相关写路径也需遵守入口约定。
7. 被移出的用户也需要收到通知更新界面。当前有角色权限判断，但没有管理员任命、群主转让或解散的 HTTP 接口，群主不能直接退出。
