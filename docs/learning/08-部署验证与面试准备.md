## 一次完整演示的顺序

1. 格式检查与全模块测试打包；产物使用 target-maven，隔离 VS Code Java 插件的 target。
2. 随机本机凭证 → MySQL 初始化与升级 → Redis/Kafka/MinIO → 五个基础应用。
3. 演示用户通过网关登录，按 nettyUri 连接；双端消息、历史查询、断线补拉。
4. 创建好友申请、接收方通过、建群拉人与踢人；检查伪造 operatorId 被拒绝。
5. 发送并领取测试红包，核对记录、余额、流水；重复请求与消费不可重复加钱。
6. 配置模型与 PgVector 后，再验证机器人回答、会话总结；最后再开 Canal、Nacos 与监控。

登录与心跳脚本：[smoke-api.ps1](../../tools/smoke-api.ps1)。它不会替代红包和故障验证。环境检查：[preflight.ps1](../../tools/preflight.ps1)。本次实际通过的范围、未运行部分见[验证记录](../verification.md)。

## 面试怎么准备，别先背技术名词

先用 90 秒讲完整链路：用户登录拿到凭证与实时节点地址；HTTP 经网关认证，WebSocket 在握手处认证；消息进入 Kafka，分别持久化与实时推送；历史与离线查询以 MySQL 为依据，Redis 保留近期索引；关系和群成员决定权限；红包用 Lua 和数据库幂等处理并发；AI 回复复用普通聊天通道。

然后每条链准备一个“问题 → 取舍 → 证据 → 限制”的例子：

- 推送采用每节点消费组，是为让目标连接节点收到消息；代价是每节点都消费，规模增大后可改为用户所在节点的定向路由。
- 历史查询近七天优先 Redis，够一页且页尾排序明确则不查消息表，不足或异常才回源，冷数据直接查库；复合游标和同毫秒并列截断回源避免分页漏消息。行为测试包含命中零消息表查询，但没有压测，不能虚构缓存命中率和吞吐提升。
- 红包领取唯一索引使重复消费不重复入账，有并发与回滚测试；Redis、Kafka、DB 之间不是全局事务。
- 一致性哈希减少扩容迁移，测试验证实例乱序稳定和扩容影响；不能承诺扩容后连接自动无感迁移。

没有压测就不写 QPS、百万连接或降低延迟百分比；未实际操作的内容可以描述为项目实现与设计，不能编造上线经历。当前原文恢复和修正有辅助工具参与，你需要能独立解释关键方法、修改业务条件并复现测试后，再按自己的贡献组织简历。

## IM 与另一个 AI 项目怎么区分

IM 主线突出长连接、消息可靠性、会话权限和异步账务；本工程 AiService 是集成能力。另一独立 AI 工程只有在你能展示不同的核心业务、独立改动与验证时，才适合作为第二个项目。不能把同一套聊天/RAG 代码换名重复包装。后续学习另一个工程时，再基于实际差异决定简历写法。

1. 编译通过、测试通过与外部整体联调通过有什么区别？
2. 面试官问“你怎么证明不重复加钱”，拿什么回答？
3. 如何判断两个项目是否值得分别放进简历？

## 自查解答

1. 编译证明源码依赖可解析；测试在既定场景、替身和测试数据库下验证断言；整体联调还要确认实际 MySQL/Redis/Kafka/模型、网络地址和异常行为。每种证据都有范围。
2. 展示唯一索引、首次插入才加余额的分支与同一数据库事务，再给出并发重复事件、流水失败回滚、重试成功的测试。补充实际 Redis/Kafka/MySQL 尚待验证，避免把局部事务说成全球严格一次。
3. 看核心业务链、技术难点、个人独立贡献和可展示成果是否不同。仅部署方式或名称不同不足以构成两个有说服力的项目。
