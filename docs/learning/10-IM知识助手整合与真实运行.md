# 10：IM 知识助手整合与真实运行

## 本篇目标

把普通聊天、机器人问答和会话总结放在同一产品中理解，能说明每条链的数据来源和失败位置。本篇对应原文第 7～10 章在最终工程上的整合扩展；保留原有消息、红包实现，按 2026-11-17 的新目标升级 AI 模块。

## 具体业务场景

团队成员把项目资料上传到会话知识库，再在对应会话询问“红包过期退款如何避免重复”；本人助手会话还可以使用个人资料。另一个入口总结最近 24 小时的讨论。前者读取用户明确上传并授权的资料，后者读取授权会话记录，两者不会自动互相灌库。上传与权限升级见[第 12 篇](12-个人与会话知识库上传和权限检索.md)。

## 分步流程与入口

1. 用户登录后建立长连接。[握手鉴权](../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/websocket/WebSocketAuthHeader.java) 同时检查 JWT 和 Redis 当前凭证；浏览器使用子协议，服务端选定 im 协议，不把凭证放进 URL。
2. [消息入口](../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/websocket/WebSocketHandler.java) 从连接取身份、查会话权限，并把消息分到存储、推送和可选 AI 请求链。普通消息不等待模型生成。
3. [AI 消费者](../../RealTimeService/src/main/java/cn/qingliao/realtimeservice/consumer/AiReplyConsumer.java) 使用固定组分摊请求，缓存稳定的回复消息后复用存储/推送 Topic。它区别于各实时节点独立组的广播推送。
4. [AI 装配](../../AiService/src/main/java/cn/qingliao/aiservice/ai/AiChatService.java)组合模型、Redis 记忆、绑定身份的工具、MCP 和 Skill。[ScopedKnowledge](../../AiService/src/main/java/cn/qingliao/aiservice/knowledge/ScopedKnowledge.java)使用相同范围过滤的向量/关键词查询，再做 RRF 和精排，最多 20 条融合候选、5 条最终上下文；当前用户入口不查询旧课程示例库。
5. [聊天入口](../../AiService/src/main/java/cn/qingliao/aiservice/controller/AiChatController.java)验证会话，[资料入口](../../AiService/src/main/java/cn/qingliao/aiservice/knowledge/KnowledgeController.java)按登录身份验证上传、预览、删除与检索。普通同步调用在 finally 清理监控上下文；流式构造也在原线程清理，资料工具身份不依赖线程局部变量。
6. [会话总结](../../OfflineDataService/src/main/java/cn/qingliao/offlinedataservice/service/impl/MessageServiceImpl.java) 先检查成员，再按时间读取聊天记录并调用内部总结服务。总结不会自动成为原会话的新消息，也不是知识库检索。

```text
用户消息 → 可信身份/会话检查 → 存储 Topic + 推送 Topic
                       └─ AI 请求 Topic → 记忆/检索/工具 → 回复 → 存储/推送
聊天总结 → 授权时间范围 → 原聊天记录 → 模型总结
```

## 关键设计与边界

消息标识用于落库和展示去重，不能只靠消费组避免重复。AI 缓存前仍可能发生模型已调用但结果未保存的故障窗口。个人资料只在本人助手上下文使用，会话资料仅当前有效成员可读；两路查询都在 SQL 中过滤范围，资料版本变化会切换记忆。Skill 是提示规程，不能代替授权和强制状态流。旧共享维护入口已停用，受限课程评测另要求维护者登录。

本次 MySQL、Redis、Kafka、Nacos、MinIO 与 PostgreSQL 已实际运行，验证了双节点消息、群聊、历史查询、红包并发和失败退款。BM25 真实 SQL 已验证。模型按安排稍后联调，infra 模式明确返回系统提示或 503；详细结论见 [运行交付记录](../../../../../简历/面试准备/两个项目运行与交付说明-2026-11-17.md)。不能把这些测试说成真实模型质量评测。

## 本篇自查

1. 为什么推送每节点一个组，AI 请求却采用固定组？
2. 资料问答和会话总结分别读什么？
3. 当前已经验证什么，模型阶段还要验证什么？

## 自查解答

1. 推送各节点要看到事件并过滤本机连接；AI 请求要分摊，避免每个实时节点重复调用模型。
2. 前者读当前范围内 READY 的用户上传资料与隔离后的记忆；后者在授权后读指定会话与时间范围的聊天记录，不自动把它们导入知识库。
3. 已验证真实中间件和控制流程，未验证真实模型答案质量、外部 MCP 返回与 Ragas 分数。后续要补实际向量化、精排、问答、总结和工具调用。
